# 第3章：インデックスの種類と使い分け

通常のBツリーインデックス以外にも、検索要件やデータ特性に合わせてさまざまなインデックスの活用手法・バリエーションが存在します。

## 1. 一意インデックス (Unique Index)

カラムの値に重複がないことを保証するインデックスです。
- **特徴：** `PRIMARY KEY` や `UNIQUE` 制約を定義すると、RDBMSによって自動的に作成されます。
- **メリット：** データの整合性を担保するだけでなく、オプティマイザが「検索結果は最大1件である」と確信できるため、最も効率的な実行計画（Index Unique Scan）が選択されます。

## 2. カバリングインデックス (Covering Index / Index Only Scan)

SQLの `WHERE` 句だけでなく、**`SELECT` 句や `ORDER BY` 句で必要なすべてのカラムをインデックスに含める**設計手法です。

- **仕組み：** 必要なデータがすべてインデックスのリーフブロック内に揃っているため、**テーブル本体へのアクセス（ディスクI/O）を完全に省略**できます。実行計画では `Index Only Scan`（または `Using index`）と表示されます。
- **注意点：** 含めるカラムを増やしすぎるとインデックスの肥大化や更新コスト増を招くため、実行頻度が極めて高いクリティカルなクエリに限定して適用します。

## 3. 関数インデックス (Function-Based Index / Expression Index)

カラムの値そのものではなく、**関数や計算式を適用した結果**に対して作成するインデックスです。

- **用途：** アプリケーションの改修が難しく、`WHERE UPPER(email) = 'TEST@EXAMPLE.COM'` や `WHERE TO_CHAR(created_at, 'YYYY-MM') = '2026-11'` のようなSQLを高速化したい場合に使用します。
- **注意点：** インデックス定義時の関数式と、SQLの `WHERE` 句の記述が完全に一致している必要があります。

## 4. 部分インデックス (Partial Index)

テーブルの全行ではなく、**特定の条件（`WHERE` 句）を満たす行だけ**を対象に作成するインデックスです（PostgreSQL, SQLite, SQL Serverなどで利用可能）。

- **用途：** 例えば「1,000万件の注文データのうち、未処理ステータス（`status = 'PENDING'`）の1,000件だけを頻繁に検索する」といったケースに有効です。
- **メリット：** インデックスのサイズを極小化でき、処理済みのレコードに対する更新オーバーヘッドを完全にゼロにできます。

## 5. 本章のまとめ
- 主キーや一意制約には自動的に一意インデックスが張られ、最速の検索パスを提供する。
- テーブルアクセス自体を省く「カバリングインデックス」は、I/O削減において絶大な効果を発揮する。
- 検索対象が一部に偏っている場合は、部分インデックスを活用することでサイズと更新負荷を最小限に抑えられる。
