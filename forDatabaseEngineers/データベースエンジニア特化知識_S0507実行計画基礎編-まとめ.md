# 第6章：DBA調査フローとまとめ 〜実務で活かすチェックリスト〜

---

## 1. スロークエリ初動調査フロー
性能劣化やクエリ遅延のアラートを検知した際、DBAが実行計画を起点に切り分ける標準手順です。

```text
[ スロークエリの検知 ]
          │
          ▼
┌───────────────────────────┐
│ ① 実行計画の取得          │ ── EXPLAIN PLAN / DISPLAY_CURSOR
└─────────────┬─────────────┘
          │
          ▼
┌───────────────────────────┐
│ ② ボトルネック箇所の特定   │ ── Cost、Time、アクセスパスを確認
└─────────────┬─────────────┘
          │
     ┌────┴─────────────────────────┐
     ▼                              ▼
【アクセスパスの異常】         【結合方式・順序の異常】
・意図しない Full Scan         ・大量行に対する Nested Loops
・暗黙の型変換 / 関数ラップ     ・不適切な駆動表の選定
     │                              │
     ▼                              ▼
┌───────────────────────────────────────────────────────────┐
│ ③ 見積もり（Rows）と実測件数の比較                       │
│    ── 乖離大：統計情報の陳腐化（DBMS_STATS 収集へ）        │
│    ── 乖離小：SQL構文・インデックス設計の見直しへ         │
└───────────────────────────────────────────────────────────┘
```

## 2. 実行計画レビュー・チェックリスト
開発レビュー時やトラブル調査時に活用できるクイックチェックリストです。

**アクセスパス関連**：

- [ ] 大規模テーブルに対して、意図しない TABLE ACCESS FULL が発生していないか？

- [ ] Predicate Information のフィルターに、型変換（TO_NUMBER 等）や関数適用が紛れ込んでいないか？

- [ ] インデックスの活用が filter ではなく、効率的な access として評価されているか？

**結合・アルゴリズム関連**：

- [ ] 駆動表（Outer）は十分に件数が絞り込まれているか？

- [ ] NESTED LOOPS の被駆動表（Inner）の結合キーに適切なインデックスが存在するか？

- [ ] 中〜大規模データ同士の結合において、HASH JOIN が適切に選ばれているか？

**見積もり・統計情報関連**：

- [ ] 実行計画の推定行数（Rows）と、実際の抽出件数に極端な乖離（数桁以上）がないか？

- [ ] 対象テーブルの統計情報は直近で正しく更新されているか？

## 3. 本書のまとめ
**実行計画はDBの「航海図」**：

SQLは「何が欲しいか（What）」だけを伝える言語であり、「どう探すか（How）」を決めるのはオプティマイザです。

**勘ではなくエビデンスで語る**：

クエリをむやみに書き換えるのではなく、実行計画を出力して「どこにボトルネック（無駄なI/Oやループ）があるのか」を論理的に突き止めます。

**統計情報がすべてを左右する**：

オプティマイザは統計情報という「地図」を信じて計画を作ります。統計情報が古ければ、どんなに優秀なDBでも誤ったルートを選択します。

## 4. DBAを目指すための次のステップ
本書で実行計画の基本構造を掴んだ後は、以下の実務領域へ学習を広げていくのがおすすめです。

**実測値の採取（ランタイム統計）**：

事前見積もりだけでなく、実際に実行されたステップごとの時間やI/Oを追う（Oracleの V$SQL_PLAN_STATISTICS_ALL や DBMS_XPLAN.DISPLAY_CURSOR(format=>'ALLSTATS LAST')、PostgreSQLの EXPLAIN ANALYZE）。

**待機イベント（Wait Events）の分析**：

クエリが「CPU処理」で詰まっているのか、「ディスク読込（db file sequential read / db file scattered read）」で待たされているのかを切り分ける。

**実行計画の固定・計画管理**：

システム更新やデータ量変動によって急に実行計画が変わってしまう事故を防ぐ仕組み（SQL Plan Baseline 等）の運用。
