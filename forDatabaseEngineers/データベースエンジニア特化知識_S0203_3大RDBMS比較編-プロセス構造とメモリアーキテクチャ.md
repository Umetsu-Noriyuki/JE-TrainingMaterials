# 第2章：プロセス構造とメモリアーキテクチャの違い

アプリケーションからデータベースへ接続（コネクションを確立）したとき、OSの内部ではどのようにメモリやCPUが割り当てられるのでしょうか？
3大RDBMSは、大きく **「マルチプロセス型」** と **「マルチスレッド型」** の2つのアーキテクチャに分かれており、これが同時接続数が増えた際のサーバーの挙動に直結します。

## 1. マルチプロセス vs マルチスレッド

```text
【マルチプロセス型（PostgreSQL / Oracle※）】
  クライアント1 ──> [ OSプロセス A ] (専用メモリ確保) ──┐
  クライアント2 ──> [ OSプロセス B ] (専用メモリ確保) ──┼──> [ 共有メモリ領域 ]
  クライアント3 ──> [ OSプロセス C ] (専用メモリ確保) ──┘    (データキャッシュ等)
  ※ 1接続ごとにOSプロセスが1つ立ち上がる（Oracleは共有サーバー構成も選択可）。
  ※ プロセス間が独立しているため堅牢だが、接続数が増えるとメモリとコンテキストスイッチの負荷が高い。


【マルチスレッド型（MySQL）】
  クライアント1 ──> ( スレッド a ) ──┐
  クライアント2 ──> ( スレッド b ) ──┼──> [ 単一の mysqld プロセス ]
  クライアント3 ──> ( スレッド c ) ──┘      └── [ 共有メモリ (InnoDB Buffer Pool) ]
  ※ 1つの巨大なプロセスの中に、接続ごとの軽量なスレッドが生成される。
  ※ 接続の生成・破棄が極めて高速で、大量の同時接続に強い。
```

### ① PostgreSQL（完全なマルチプロセス型）
- クライアントが接続するたびに、`postgres` というOSプロセスが `fork()` によって1つ生成されます。
- 各プロセスは独立したメモリ空間を持つため、万が一1つのセッションでバグが起きても他のセッションへ波及しにくいという堅牢性があります。
- 一方で、**同時接続数が数百〜数千に達すると、OSのメモリ枯渇やCPUのプロセス切り替え（コンテキストスイッチ）のオーバーヘッドが急増し、急激に性能が劣化**します。

### ② MySQL（マルチスレッド型）
- OS上では原則として単一の `mysqld` プロセスだけが動作し、クライアント接続ごとに内部の「スレッド」が割り当てられます。
- スレッドはプロセスに比べて生成コストとメモリ消費量が極めて小さいため、Webアプリケーションから頻繁に接続・切断を繰り返すようなワークロードでも軽快に動作します。

### ③ Oracle Database（マルチプロセス基本 ＋ 共有サーバー対応）
- デフォルト（専用サーバー構成）ではPostgreSQLと同じく1接続＝1サーバープロセス（Windows版はスレッド）ですが、大規模環境向けに少数のプロセスで多数の接続をさばく「共有サーバー構成（MTS）」も標準で備えています。

## 2. メモリ構造の比較（共有メモリとセッションメモリ）

RDBMSのメモリは大きく **「全セッションで共有する領域（データキャッシュなど）」** と **「各接続が個別に使用する作業領域（ソートやハッシュ結合用）」** の2種類に分かれます。

| メモリ区分 | Oracle Database | PostgreSQL | MySQL (InnoDB) |
| :--- | :--- | :--- | :--- |
| 共有メモリ全体名称 | **SGA** (System Global Area) | Shared Memory | グローバルバッファ |
| データキャッシュ（最重要） | Database Buffer Cache | `shared_buffers` | `innodb_buffer_pool_size` |
| トランザクションログ用バッファ | Redo Log Buffer | `wal_buffers` | `innodb_log_buffer_size` |
| セッション個別メモリ全体 | **PGA** (Program Global Area) | ローカルメモリ | スレッドバッファ |
| ソート・ハッシュ作業領域 | PGA内（自動管理） | `work_mem`（接続×操作ごとに確保） | `sort_buffer_size` / `join_buffer_size` |

### メモリチューニングの決定的な違い（要注意ポイント！）
- **MySQL (`innodb_buffer_pool_size`)：**

  OSのファイルシステムキャッシュに頼らず、InnoDB自身がデータを丸ごとメモリに抱え込む設計です。DB専用サーバーであれば、**搭載物理メモリの 60%〜75%** を割り当てるのがセオリーです。

- **PostgreSQL (`shared_buffers` と `work_mem`)：**

  PostgreSQLは自身の `shared_buffers` と、OS側のファイルキャッシュ（ページキャッシュ）の「2段階」でキャッシュを利用する設計です。そのため、`shared_buffers` は **物理メモリの 25%〜40%** 程度に抑えるのが定石です。
  また、ソート用メモリである `work_mem` は「1接続あたり」ではなく **「1クエリ内のソート・ハッシュ操作1つあたり」** に確保されるため、大きく設定しすぎると同時実行時に一発でOOM Killer（メモリ不足による強制終了）を引き起こします。

## 3. コネクションプーリングの重要性

特に **PostgreSQL** や **Oracle** を採用するシステムでは、アプリケーション側（HikariCPなど）やミドルウェア（PgBouncer / RDS Proxyなど）で **コネクションプーリング（接続の使い回し）** を導入することが必須の設計要件となります。

```text
【コネクションプーリングによる接続数の制御】

  [ Webサーバー群 (1000リクエスト) ]
          │
          ▼  (一時的に待機・順番待ち)
  [ コネクションプール (最大接続数を 50 に制限) ]
          │
          ▼  (確立済みの50本のプロセスだけを高速に使い回す)
  [ PostgreSQL / Oracle (50プロセスで安定稼働) ]
```

---

## 4. 本章のまとめ

-  **PostgreSQL** はマルチプロセス型であり、接続数の増加に弱いため、コネクションプーリングの導入と `work_mem` の慎重なサイジングが不可欠である。

-  **MySQL** はマルチスレッド型で接続のオーバーヘッドが小さく、物理メモリの大部分（60〜75%）を `innodb_buffer_pool_size` に割り当ててパフォーマンスを引き出す。

-  **Oracle** はSGA（共有）とPGA（個別）の明確なメモリ分離と自動管理機能を備え、大規模接続にも対応できる柔軟なアーキテクチャを持つ。
