# 第1章：3大RDBMSの誕生背景とライセンス・選定基準

システム開発の初期フェーズで必ず直面するのが「どのRDBMSを採用すべきか？」という技術選定です。
Oracle Database、PostgreSQL、MySQLは、それぞれ異なる思想と歴史的背景のもとで進化してきたため、得意領域とライセンス上の制約が大きく異なります。

## 1. 3大RDBMSの思想と進化の歴史

```text
【3大RDBMSのポジショニングと設計思想】

  [ Oracle Database ] ── 商用DBの絶対王者（エンタープライズ・基幹系）
    ・思想：「どんな大規模・高負荷・障害が起きても絶対にデータを守り、止めない」
    ・強み：圧倒的な機能網羅性、RACによるアクティブ-アクティブ構成、手厚い公式サポート

  [ PostgreSQL ]      ── 最も先進的な高機能OSS（機能性・標準SQL準拠）
    ・思想：「Oracleに匹敵する高度な機能と標準SQLへの厳格な準拠をOSSで実現する」
    ・強み：複雑な分析クエリ、地理空間情報(PostGIS)、JSONB、豊富な拡張機能

  [ MySQL ]           ── Webサービスの標準OSS（シンプル・高速・スケールアウト）
    ・思想：「Webシステムで求められる単純な読み書きを、とにかく軽く・速く捌く」
    ・強み：シンプルな運用、レプリケーションの容易さ、Web系フレームワークとの親和性
```

**💡 DBA用語メモ：OSS（オープンソースソフトウェア）と商用サポート**
-  PostgreSQLやMySQLはソースコードが公開されているOSSですが、エンタープライズ企業向けに有償のテクニカルサポートを提供するベンダー（EDB社やOracle社など）も存在します。
-  また、近年はAWS（Amazon RDS / Aurora）やGoogle Cloud（Cloud SQL / AlloyDB）といったマネージドクラウドサービスの普及により、クラウド基盤側で高可用性やバックアップが補完されるケースが増えています。

## 2. ライセンス体系とコストの罠

技術的な機能差以上に、プロジェクトの予算や法務リスクに直結するのがライセンスの違いです。

| 比較項目 | Oracle Database | PostgreSQL | MySQL |
| :--- | :--- | :--- | :--- |
| 基本種別 | 商用ソフトウェア（プロプライエタリ） | オープンソース（OSS） | オープンソース（OSS） / 商用版あり |
| ライセンス形態 | プロセッサ単位（CPUコア数課金）または Named User Plus | PostgreSQL License（BSD/MITに近い極めて緩やかなライセンス） | デュアルライセンス（GPLv2 または 商用ライセンス） |
| 商用利用・改変 | 有償ライセンス購入が必須 | 完全無料（改変・再配布・商用組み込みも自由） | Webサービス等のバックエンド利用は無料（※配布製品への組み込みは注意） |
| クラウド利用時の注意 | AWS RDS等では「ライセンス込み（LI）」か「持ち込み（BYOL）」を選択。CPUコア数で高額化しやすい | RDS / Aurora等でライセンス費用ゼロ（インフラ利用料のみ） | RDS / Aurora等でライセンス費用ゼロ（インフラ利用料のみ） |

### 実務でよくある「ライセンス事故」
- **Oracleの仮想化環境（VMware等）での課金ルール：**

  物理サーバー上の1つの仮想マシン（VM）だけにOracleをインストールしていても、同じクラスタ内の別ホストへライブマイグレーション（移動）できる構成になっている場合、**クラスタ内の全物理CPUコア分のライセンス費用を請求される**ケースがあります。

- **MySQLのGPLライセンスの誤解：**

  自社のWebサービスの裏側（サーバーサイド）でMySQLを動かすだけであれば、GPLのソースコード公開義務は発生しません。問題になるのは、MySQLのライブラリを組み込んだパッケージソフトを顧客に販売・配布する場合です（その場合は商用ライセンスの購入が必要になります）。

## 3. システム要件に基づく選定基準（どう使い分けるか？）

現代のクラウドネイティブ環境では、ライセンスコストとクラウドサービス（Amazon Aurora等）の充実度から、新規開発では **PostgreSQL または MySQL** が選ばれるケースが主流です。

```text
【現場でのRDBMS選定フローチャート】

  Q1. 既存の基幹システムがOracleで、PL/SQL資産やRAC等の高度機能が必須か？
   ├── YES ──> [ Oracle Database ]（または移行コストを精査してPostgreSQLへ）
   └── NO  ──> Q2へ

  Q2. 複雑な集計・分析クエリ、地理空間データ、厳密なデータ整合性や拡張性が重視されるか？
   ├── YES ──> [ PostgreSQL ]（金融・業務系・データ分析基盤・新規Web全般に強い）
   └── NO  ──> Q3へ

  Q3. 単純なCRUD中心のWebアプリで、圧倒的な実績とシンプルな運用・レプリケーションを重視するか？
   ├── YES ──> [ MySQL ]（ECサイト・SNS・CMS・マイクロサービスに強い）
   └── NO  ──> 要件に応じてPostgreSQL / MySQLを比較検討
```

---

## 4. 本章のまとめ

-  **Oracle** は圧倒的な機能と堅牢性を持つエンタープライズの王者だが、CPUコア単位のライセンスコストと仮想化環境のルールに細心の注意が必要である。

-  **PostgreSQL** は最も制限の緩いOSSライセンスを持ち、標準SQLへの準拠度や複雑なクエリ処理・拡張性に優れた万能型RDBMSである。

-  **MySQL** はシンプルさと高速な読み書きを強みとし、Webサービス領域でデファクトスタンダードの地位を築いている。
