# 第3章：基本用語と物理動作 〜データの探し方と繋ぎ方〜

---

## 1. 実行計画の3大構成要素
実行計画を読み解く際、確認すべき要素は大きく以下の3つに集約されます。

1. **アクセスパス（Access Path）**：1つのテーブルからどうやって行を取り出すか？
2. **結合アルゴリズム（Join Method）**：複数テーブルをどのような手順で突き合わせるか？
3. **見積もり指標（Metrics）**：各処理の負荷や件数をどう予測しているか？

まずは、現場で最も頻出する「アクセスパス」と「結合アルゴリズム」の物理的な挙動を押さえましょう。

---

## 2. アクセスパス：データの探し方

### ① 全表走査（TABLE ACCESS FULL / Full Table Scan）
テーブルに割り当てられた全データブロックを、先頭から高水位標（High Water Mark）まで順に読み込みます。

```text
[ ストレージ / データブロック ]
[Block 1] ──> [Block 2] ──> [Block 3] ──> ... ──> [Block N] （全件読み取り）
```
**💡 DBA用語メモ：高水位標（High Water Mark / HWM）とは？**

-  そのテーブルで「過去に一度でもデータが書き込まれた最高地点（領域の境界線）」のことです。

-  DELETE 文で全データを削除してもこのHWMは下がらないため、中身が0件でもFull Scanを実行するとHWMまでの空ブロックをすべてスキャンしてしまい遅延の原因になります（初期化には TRUNCATE が使われる理由です）。


**物理動作の特性**：

-  マルチブロック読込（Multi-block I/O）：1回のディスクI/Oで複数ブロックをまとめて読み込めるため、スループットが高い。

**メリット**：
-  テーブル全体の大部分（数十％以上）を取得する場合や、集計処理（COUNT(*), SUM等）ではインデックスよりも高速。数十〜数百件程度の小さなテーブルなら、インデックスを引くより速い。

**デメリット / 注意点**：
-  数百万件の巨大テーブルから数件を抽出する際にFull Scanが発生すると、大量のディスクI/Oが発生し性能劣化の主因となる。


### ② 索引走査（INDEX SCAN）
B-Tree構造のインデックスをルートブロックからリーフブロックへと辿り、目的の行の物理アドレス（ROWID）を特定してテーブル本体にアクセスします。

```Plaintext
[ Root Block ]
        /        \
[ Branch ]    [ Branch ]
    /    \        /    \
[Leaf] [Leaf] [Leaf] [Leaf] ─── ROWIDで実データを参照 ───> [ Table Block ]
```

**💡 DBA用語メモ：ROWID（行ID）とは？**

-  データベース内部における「物理的な住所・番地」です（例：「ファイル番号4の、ブロック番号120の、5行目」）。
-  主キー（ID値など）とは異なり、ディスク上の物理配置を直接指すため、最速でテーブル本体の行へ到達できます。

**物理動作の特性**：

-  シングルブロック読込（Single-block I/O）：ピンポイントで必要なブロックのみを読み込む。

**代表的な走査方式**：

-  INDEX UNIQUE SCAN：主キーや一意制約（UNIQUE）列で検索し、最大1行を特定する最速のアクセスパス。

-  INDEX RANGE SCAN：非一意インデックスの検索や、範囲検索（<, >, BETWEEN等）で複数行を順番に読み取る。

**デメリット / 注意点**：

-  抽出件数がテーブル全体の数％〜十数％を超えると、ランダムアクセス（シングルブロックI/O）の回数が跳ね上がり、Full Scanよりも遅くなる場合がある。

-  インデックスを引いてROWIDを特定したあと、テーブルの実データを読みに行く動作（TABLE ACCESS BY INDEX ROWID）が必ずセットで発生する（カバリングインデックス等を除く）

## 3. 結合アルゴリズム：テーブルの繋ぎ方
複数テーブルを結合（JOIN）する際、オプティマイザはデータ件数やインデックスの有無に応じて以下の方式を選択します。

### ① ネステッドループ結合（NESTED LOOPS）
プログラミングにおける「二重ループ（for文のネスト）」と同じ動作です。

```Plaintext
for each row in 外部テーブル(駆動表 / Outer) {
    for each matching row in 内部テーブル(被駆動表 / Inner) {
        結合結果を出力;
    }
}
```

**特徴**：

-  最初に読み込む側を駆動表（Outer Table）、突き合わされる側を被駆動表（Inner Table）と呼ぶ。

-  駆動表から取得した1行ごとに、被駆動表のインデックスを都度検索する。

**得意なケース**：

-  駆動表が十分に絞り込まれており（数件〜数百件程度）、かつ被駆動表の結合キーにインデックスが存在する場合。

-  OLTP（オンライン処理）のように、最初の数行を即座に応答させたい（初速重視）ケースに最適。

苦手なケース：

-  駆動表の件数が数万件以上ある場合。被駆動表へのランダムアクセスが数万回発生し、処理時間が急増する。


### ② ハッシュ結合（HASH JOIN）
片方のテーブルからメモリ上に「ハッシュテーブル」を構築し、もう一方のテーブルを走査してハッシュ値を突き合わせます。

```Plaintext
[ビルド入力(小)] ──> [メモリ上のハッシュテーブル構築]
                                ▲
                                │ ハッシュ値で突合
                                │
[プローブ入力(大)] ── 順次読み込み (Probe) ──> 結合結果を出力
```

**特徴**：

-  小さい方のテーブルをビルド入力（Build Input）として読み込み、メモリ（PGA / Workarea）上にハッシュテーブルを作る。

-  大きい方のテーブル（プローブ入力 / Probe Input）を読み込みながら、ハッシュテーブルと合致する行を抽出する。

**得意なケース**：

-  中規模〜大規模テーブル同士の等価結合（=）。

-  結合キーにインデックスがなくても高速に処理できるため、バッチ処理やDWHに向いている。

**苦手なケース**：

-  メモリ不足。ハッシュテーブルが割り当てメモリに収まらない場合、一時表領域（ディスク）への書き出し（Temp Spill）が発生し、急激に遅くなる。

-  非等価結合（< や BETWEEN 等）には使用できない。


### ③ ソートマージ結合（SORT MERGE JOIN）
双方のテーブルを結合キーでソート（並び替え）した上で、先頭から順にマージ（突合）します。

**特徴**：

-  結合条件が範囲指定（a.id < b.id）の場合や、すでにインデックス等で双方がソートされている場合に選ばれる。

-  現在の商用環境では、等価結合であれば多くの場合Hash Joinの方が有利なため、選定頻度は下がる。

---

## 4. 方式比較まとめ
| 結合方式 | 前提条件 | 得意なデータ規模 | インデックスの必要性 | メモリ消費 |
|:---|:---|:---|:---|:---|
| Nested Loops | 任意の結合条件 | 小 × 中〜大（駆動表が少数）| 必須（被駆動表の結合列）|	極小
| Hash Join	| 等価結合（=）のみ | 中〜大 × 中〜大（大量データ同士）| 不要 | 中〜大（ハッシュテーブル用）
| Sort Merge | 任意の結合条件 | 中〜大 × 中〜大（非等価結合時など）| あればソート省略可	 | 中（ソート用領域）

---

## 5. 見積もり指標（Metrics）の基礎
実行計画の右側に出力される各数値の意味を把握しておきましょう。

**Rows（Cardinality）**：

-  そのステップを通過した結果、返されると予測されるレコード件数。この予測が実測とズレていると、オプティマイザの判断（結合方式の選定）が狂う。

**Cost**：

-  処理完了までにかかるディスクI/OやCPUリソースの相対的見積もり値。オプティマイザはこれが最も小さくなる経路を選択する。

**Bytes**：

-  そのステップで転送・処理される推定データ量（バイト数）。
