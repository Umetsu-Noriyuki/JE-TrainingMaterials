# 第4章：ポイントインタイムリカバリ（PITR）の内部構造

「毎日深夜3時にフルバックアップを取得しているシステムで、**14時55分に誤って `WHERE` 句なしの `DELETE` を実行してしまった**」とします。
もし深夜3時のフルバックアップしか持っていなければ、**約12時間分の売上・更新データがすべて消失**してしまいます。

この問題を解決し、**「14時54分59秒（誤操作の直前）」の状態までピンポイントで復元する技術**が **ポイントインタイムリカバリ（PITR：Point-In-Time Recovery）** です。

## 1. PITRを支える「トランザクションログ」の仕組み

RDBMSは、データの更新（`INSERT` / `UPDATE` / `DELETE` / `DDL`）が行われる際、データファイル本体に書き込むのと並行して、**「どのような変更が行われたか」という時系列の操作履歴**を専用のログファイルに記録しています。

- **Oracle Database：** REDOログ / アーカイブREDOログ
- **PostgreSQL：** WAL（Write-Ahead Logging） / アーカイブWAL
- **MySQL：** バイナリログ（Binary Log / binlog）

PITRを実現するためには、 **「定期的なベースバックアップ（フル）」** と、 **「継続的に別ストレージへ退避（アーカイブ）されたトランザクションログ」** の2つが揃っている必要があります。

---

## 2. PITRの復元フロー（リストア ＋ リカバリ）

データベースの復旧作業は、厳密には **「リストア（Restore）」** と **「リカバリ（Recovery）」** の2段階に分かれています。

```text
【PITR（時点指定復元）の2段階プロセス】
  状況：03:00にフルバックアップ取得。14:55に誤って全件DELETEを実行。
  目標：14:54:59 の状態へ復元する。

  [ 03:00 ]             [ 10:00 ]      [ 14:54:59 ]   [ 14:55:00 ]
  フルバックアップ      正常な更新     目標復旧時点   ★誤ったDELETE実行！
      │                     │               │               │
      ▼                     ▼               ▼               ▼
  ────●─────────────────────●───────────────●───────────────×────▶ 時間軸
      │                                     ▲               │
      │  ① リストア (Restore)                │               │
      │     03:00の物理ファイルを書き戻す     │               │
      │                                     │               │
      └─────────────────────────────────────┘               │
         ② リカバリ / ロールフォワード (Recovery)             │
            退避しておいたトランザクションログを               │
            「14:54:59」まで順番に再実行して追いつかせる！     └─ ここで再生をストップ！
                                                               （誤操作は適用しない）
```

### ステップ1：リストア（物理ファイルの書き戻し）

-  まずは起点となる「深夜3時のフルバックアップ」をディスク上に復元します。この時点ではデータベースは深夜3時の状態です。

### ステップ2：リカバリ／ロールフォワード（ログの再生）

-  深夜3時以降に蓄積されたトランザクションログ（アーカイブログ）をRDBMSに読み込ませ、3時00分〜14時54分59秒までに行われた変更履歴を高速に再実行（ロールフォワード）します。
-  誤操作（14時55分00秒）の直前で再生を停止することで、誤った `DELETE` だけが実行されなかった世界線を作り出します。
-  最後に、復元時点でコミットされていなかった中途半端なトランザクションを自動的にロールバックして整合性を保ち、DBをオープンします。

---

## 3. PITR運用における注意点
**トランザクションログの連続性が命：**
  フルバックアップから目標復旧時点までの間のトランザクションログが1ファイルでも欠損すると、その欠損時点より先へはロールフォワードできなくなります。ログのアーカイブ先ストレージ（S3など）の空き容量監視は極めて重要です。

**`TRUNCATE` や `DROP TABLE` もログに記録される：**
  `DELETE` だけでなく、`DROP TABLE` や `TRUNCATE` といったDDL操作もトランザクションログに記録されるため、その直前の時刻（ままたは DB内部の更新通し番号：SCN / LSN）を指定すれば復元可能です。

## 4. 本章のまとめ

-  PITRは「ベースとなるフルバックアップ」＋「継続退避されたトランザクションログ」の組み合わせで実現する。

-  復旧は、過去ファイルを戻す **リストア** と、ログを再生して時間を進める **リカバリ（ロールフォワード）** の2段階で行われ、誤操作の直前で再生を止めることでRPO数秒〜数分の復旧を可能にする。
