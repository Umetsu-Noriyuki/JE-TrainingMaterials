# 第4章：実行計画の読み順と実例 〜ツリー構造を読み解く〜

---

## 1. 実行計画の取得コマンド

まずは実機で実行計画を出力する最も基本的なコマンドを確認します（Oracle Databaseの例）。

```sql
-- 1. 実行計画を内部テーブルに生成
EXPLAIN PLAN FOR
SELECT c.customer_name, o.order_id, o.order_date, o.total_amount
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE c.customer_id = 100;

-- 2. 整形して画面表示
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY(format => 'TYPICAL'));
```

※ 他のDBでも基本的な考え方は同じです（PostgreSQL / MySQL の場合は EXPLAIN <SQL>;）。

---

## 2. 読み順を支配する「3つの鉄則」

実行計画は上から下へそのまま順番に処理されるわけではありません。木構造（親子関係）になっているため、以下のルールに沿って追う必要があります。

```Plaintext
【ルール1】「最もインデントが深いノード（最も右にあるノード）」から実行される
【ルール2】インデントが同じ階層の場合、「上にあるノード」から実行される
【ルール3】「子ノード」の結果を受け取って、そのすぐ外側の「親ノード」が動く
```

「最深部（葉ノード）から外側（根ノード）へ向かってデータが遡上していく」とイメージすると直感的に捉えやすくなります。

## 4. 処理順序のステップ・バイ・ステップ解説

上記の実行計画に「3つの鉄則」を適用すると、実際の処理順序は **③ → ② → ⑤ → ④ → ① → ⓪ **となります。

```Plaintext
[0] SELECT STATEMENT
└── [1] NESTED LOOPS ────────────────────── ⑤ 結合処理
      ├── [2] TABLE ACCESS (CUSTOMERS) ──── ② 行データの取得
      │     └── [3] INDEX UNIQUE SCAN ───── ① 最深部：主キー探索（駆動表）
      └── [4] TABLE ACCESS (ORDERS) ─────── ④ 行データの取得
            └── [5] INDEX RANGE SCAN ────── ③ インデックス範囲探索（被駆動表）
```

### ステップ①：Id 3（INDEX UNIQUE SCAN / PK_CUSTOMERS）
最もインデントが深いノードです（Id 3 と Id 5 が同階層ですが、上にある Id 3 が先行）。

主キーインデックス（B-Tree）を辿り、customer_id = 100 に合致する顧客レコードの物理アドレス（ROWID）を1件分特定します。

### ステップ②：Id 2（TABLE ACCESS BY INDEX ROWID / CUSTOMERS）
Id 3 の親ノードです。特定したROWIDを使って CUSTOMERS テーブルの実ブロックを直接参照し、customer_name などの必要な列データを取得します（駆動表の確定）。

### ステップ③：Id 5（INDEX RANGE SCAN / IDX_ORDERS_CUSTOMER_ID）
次に深いノードである Id 5 が動きます。

注文テーブルの外部キーインデックスを参照し、先ほど確定した顧客（ID=100）に紐づく注文データのROWID群（約100件）を範囲検索します。

### ステップ④：Id 4（TABLE ACCESS BY INDEX ROWID / ORDERS）
Id 5 で得られたROWID群をもとに、ORDERS テーブルの実ブロックへアクセスし、order_date や total_amount の列データを取得します。

### ステップ⑤：Id 1（NESTED LOOPS）
Id 2（顧客1件）と Id 4（注文100件）の結果を結合キーで突き合わせ、100件の結合レコードセットをメモリ上に生成します。

### ステップ⑥：Id 0（SELECT STATEMENT）
完成した結果セットをクライアント（呼び出し元）へ返却します。

ステップ①〜⑤を追うと同時に、**『Costが一番跳ね上がっている行はどこか？』『Rowsの数字が想定とズレているステップはないか？』**を見るのがDBAの視点です

## 5. 見落とし厳禁：Predicate Information の見方
実行計画の下部に表示される Predicate Information（述語情報）は、「条件式がどう評価されたか」を示す重要エリアです。

**access（アクセス述語）**：

インデックスの木構造を辿るために直接検索キーとして使われた条件（絞り込み効率が最も高い）。

例：access("C"."CUSTOMER_ID"=100)

**filter（フィルタ述語）**：

データを読み取った後、メモリ上で1行ずつ合致判定を行い、除外した条件。

インデックスを活用できずに filter 処理されている箇所は、ボトルネックの兆候となり得ます。
