# 第2章：物理バックアップと論理バックアップの仕組み

データベースからデータを退避するアプローチは、内部の取り扱い方によって **「物理バックアップ」** と **「論理バックアップ」** の2つに大別されます。両者は速度と柔軟性において真逆の特性を持っています。

## 1. 仕組みと内部動作の違い

```text
【物理バックアップ】OSレベルでバイナリファイルをそのままコピー
  +-----------------------+       ファイルコピー        +-----------------------+
  | DBデータファイル群      | ========================> | 物理バックアップファイル |
  | (.dbf / .ibd / base)  |    (RMAN / pg_basebackup   | (バイナリ・ブロック単位)|
  +-----------------------+     / スナップショット等)   +-----------------------+
   ※ 復元時はファイルを元の場所に書き戻すだけなので超高速！


【論理バックアップ】DBエンジン経由でデータを読み出し、SQL文やCSV等で出力
  +-----------------------+   SELECT * FROM ...         +-----------------------+
  | DBデータファイル群      |  ------------------------> | 論理ダンプファイル      |
  | (テーブル・インデックス)|  SQL文 / テキスト変換        | (CREATE / INSERT文等)  |
  +-----------------------+  <------------------------  +-----------------------+
   ※ 復元時はSQLを1文ずつ再実行し、インデックスも再構築するため時間がかかる！
```

### ① 物理バックアップ（Physical Backup）

**仕組み：**

RDBMSが管理しているデータファイルや制御ファイル、ブロック領域をOSレベルのファイル（バイナリ）のままコピーする方式です。

**代表ツール：**
-  Oracle `RMAN`
-  PostgreSQL `pg_basebackup`
-  MySQL `Percona XtraBackup`
-  クラウドのストレージスナップショット（RDS Snapshot等）

**特徴：**
-  **取得・復元が極めて高速：**
  データを解釈せずブロック単位でコピーするため、数TBの大規模DBでも現実的な時間（短いRTO）でリストア可能です。
-  **環境依存性が高い：**
  原則として、取得元と復元先で「OSの種類・CPUアーキテクチャ・RDBMSのメジャーバージョン」が完全に一致している必要があります。
-  **部分復元の難しさ：**
  バイナリファイル丸ごとのコピーであるため、「100個あるテーブルのうち、誤って消した1テーブルだけを戻す」といった柔軟な復元には手間がかかります（一度別インスタンスへ全体を復元してからデータを抜く必要があります）。

### ② 論理バックアップ（Logical Backup）
**仕組み：**

DBエンジンに対して `SELECT` 文を発行してデータを読み出し、`CREATE TABLE` 文や `INSERT` 文（あるいは `COPY` 形式のテキスト・バイナリ）のファイルとして書き出す方式です。

**代表ツール：**
-  Oracle Data Pump (`expdp/impdp`)
-  PostgreSQL `pg_dump / pg_restore`
-  MySQL `mysqldump`

**特徴：**
-  **柔軟性が極めて高い：**
  特定のテーブル単位・スキーマ単位でのバックアップやリストアが容易です。また、SQL文（テキスト）として出力されるため、異なるOS間や別バージョンへのメジャーバージョンアップ移行にも利用できます。
-  **復元（リストア）に時間がかかる：**
  リストア時には `INSERT` 文を大量に実行し、さらにインデックスの構築（ソートとBツリー生成）を一からやり直すため、データ量が増えると復元時間が指数関数的に長くなります。

---

## 2. 物理 vs 論理 比較表と使い分けの基準

| 比較項目 | 物理バックアップ | 論理バックアップ |
| :--- | :--- | :--- |
| バックアップ対象 | データファイル・ブロックそのもの | テーブル定義（DDL）と行データ（DML） |
| バックアップ速度 | 高速（ディスクの読み書き速度（I/O帯域）に依存） | 中〜低速（全件SELECTの負荷あり） |
| リストア速度 | 極めて高速（ファイル書き戻し） | 低速（INSERT再実行＋インデックス再作成） |
| 部分復元（1テーブルのみ） | 困難（一度全体復元が必要） | 容易（対象テーブルのみ指定して復元可） |
| 異バージョン・異OS移行 | 不可（同一環境が前提） | 可能 |
| 主な用途 | 本番環境全体の定期バックアップ、大規模DBの障害復旧 | 開発環境へのテストデータ移行、メンテナンス前の特定テーブル退避 |

---

## 3. 本章のまとめ

-  物理バックアップは「ファイル丸ごとコピー」。復元が超高速なため、本番DB全体の障害復旧（短いRTO）の主軸となる。

-  論理バックアップは「SQL文としての書き出し」。復元時にインデックス再作成などが走るため大規模DBの全体復旧には不向きだが、特定テーブルの退避や環境移行で絶大な威力を発揮する。
