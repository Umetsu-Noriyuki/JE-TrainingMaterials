# 第3章：取得方式の分類（フル・差分・増分バックアップ）

データ量が数百GB〜数TBに達するシステムでは、毎日すべてのデータをバックアップしていると「夜間バッチの時間内に終わらない」「ストレージコストが膨大になる」という問題に直面します。
これを解決するため、取得範囲を限定する **「差分バックアップ」** と **「増分バックアップ」** を組み合わせて運用します。

## 1. 3つの取得方式の仕組み

日曜日にフルバックアップを取得し、月曜〜水曜にデータが追加されたケースで比較します。

```text
【日曜〜水曜のデータ変化と、各方式のバックアップ対象範囲】

  日曜（ベース）: [ データA ]
  月曜（+B追加）: [ データA ] [ データB ]
  火曜（+C追加）: [ データA ] [ データB ] [ データC ]
  水曜（+D追加）: [ データA ] [ データB ] [ データC ] [ データD ]  <-- ここで障害発生！

--------------------------------------------------------------------------------
1. フルバックアップ（Full）: 毎回「すべて」を取得
   日曜: [ A ]
   月曜: [ A, B ]
   火曜: [ A, B, C ]
   水曜: [ A, B, C, D ]  ──> リストアは「水曜のフル」1つだけで完了！

2. 差分バックアップ（Differential）: 「最後のフル以降」の変更分をすべて取得
   日曜: [ A ] (フル)
   月曜:    [ B ]
   火曜:    [ B, C ]
   水曜:    [ B, C, D ]  ──> リストアは「日曜のフル」＋「水曜の差分」の2つを適用！

3. 増分バックアップ（Incremental）: 「前回のバックアップ以降」の変更分のみ取得
   日曜: [ A ] (フル)
   月曜:    [ B ]
   火曜:       [ C ]
   水曜:          [ D ]  ──> リストアは「日曜のフル」＋「月曜」＋「火曜」＋「水曜」を順番に適用！
```

## 2. 各方式のメリット・デメリット比較
方式取得時間・容量リストアの速度・手間リストア時のリスク（耐障害性）フルバックアップ大（毎回全データを取得するため時間・容量ともに最大）最速・最小（最新のフル1つを戻すだけ）低い（過去のバックアップが破損していても最新さえ無事ならOK）差分バックアップ中（次のフルが近づくにつれ、徐々にサイズが大きくなる）速い（最新のフル＋最新の差分の計2つを適用）中程度（途中の月曜・火曜の差分が破損していても復旧可能）増分バックアップ最小・最速（前回のバックアップからの純粋な差分のみ）遅い・複雑（フル＋その後のすべての増分を順番に適用）高い（途中の増分ファイルが1つでも破損・欠損すると、それ以降のデータは復元不可）

## 3. 実務での運用設計（世代管理とローテーション）
実務では、これらを組み合わせて1週間単位や1ヶ月単位のスケジュールを組むのが一般的です。

**典型的なスケジュール例（大規模DB）：**

-  毎週日曜 02:00： フルバックアップ（レベル0）を取得

-  月曜〜土曜 02:00： 増分バックアップ（または差分バックアップ）を取得

-  世代保持： 最低2世代（2週間分）を保持し、古い世代から自動削除

**クラウド（RDS / Aurora等）での挙動：**

AWS RDSの自動バックアップやスナップショットは、内部的に「初回のみフル、2回目以降は変更されたストレージブロックのみを保存する増分方式」で動作しています。ただし、復元時はクラウド基盤側で自動的にブロックを結合してくれるため、運用者は「任意の時点のスナップショット1つを指定するだけ」でフルバックアップと同じ感覚でリストアできます。

## 4. 本章のまとめ
-  フルはリストアが最速だが取得コストが高い。増分は取得が最速・最小だが、リストア時に全ファイルを順に適用する必要があり、途中の1つが欠けると復旧不能になるリスクを持つ。

-  差分はフルと増分の中間であり、「最新のフル＋最新の差分」の2ファイルで復元できるバランスの良さを持つ。
