# 第2章：実行計画とは何か？ 〜RDBMSの内部頭脳と探索メカニズム〜

---

## 1. 宣言型言語（SQL）の特性と存在意義
### 「What」と「How」の分離
JavaやPythonなどの手続き型言語では、処理の **手順（How）** をエンジニア自身が1行ずつコーディングします。

```text
【手続き型（Java等）】
1. リストの先頭からループを開始する
2. 各要素のIDをチェックする
3. 一致したら新リストへ追加し、ループを抜ける
```

---

一方、SQLは宣言型言語（非手続き型言語）です。「どのデータが欲しいか（What）」だけを記述し、
「ストレージのどこから、どの順序・アルゴリズムでデータを取り出すか（How）」は一切指示しません。

```SQL
/* 宣言型（SQL）：何を抽出したいかだけを定義 */
SELECT customer_name, order_date
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE c.customer_id = 100;
```

この「What」を「具体的なコンピュータの作業命令（How）」へと自動翻訳した作業設計図こそが実行計画（Execution Plan）です。

---

## 2. 実行計画の正体：ツリー構造（ノードの連鎖）
実行計画は、単なる文章ではなく演算子（オペレータ）が親子関係を持った木構造（ツリー構造）です。

各ノードは「データ読み出し（Scan）」「データ突き合わせ（Join）」「並び替え（Sort）」といった単一責務を持ちます。

子ノードが出力した行セットを、親ノードが順次受け取って処理を進めるパイプライン構造になっています。

```Plaintext
[SELECT STATEMENT] (最終結果の返却)
└── [NESTED LOOPS] (親: 2つのテーブルを結合)
      ├── [TABLE ACCESS BY INDEX ROWID on CUSTOMERS] (子1: 顧客を特定)
      │     └── [INDEX UNIQUE SCAN on PK_CUSTOMERS]
      └── [TABLE ACCESS BY INDEX ROWID on ORDERS]    (子2: 注文を特定)
            └── [INDEX RANGE SCAN on IDX_ORDERS_CUSTOMER_ID]
```

データベースエンジンは、このツリーの最深部の子ノードから順に処理を実行し、結果を返却します。

---

## 3. SQLが実行計画になるまでの3大フェーズ
クライアントからSQLが送信されてからデータが返るまで、DB内部では3つの処理フェーズを通過します。

```Plaintext
[クライアント]
      │ (SQL文)
      ▼
┌──────────────┐
│  ① パーサー   │ ── 構文解析・意味解析・共有プール確認
└──────┬───────┘
       │ (構文木)
       ▼
┌──────────────┐
│②オプティマイザ│ ── コスト計算・実行計画決定 ★ここが核心
└──────┬───────┘
       │ (実行計画)
       ▼
┌──────────────┐
│③エグゼキュータ│ ── バッファ/ストレージへの物理I/O・処理実行
└──────┬───────┘
       │ (結果行)
       ▼
[クライアント]
```

### ① 解析（パーサー / Parser）
**構文・意味チェック**：

-  文法ミスがないか、指定されたテーブルや列が存在し参照権限があるかを検証。

**共有プールの確認（ソフトパース vs ハードパース）**：

-  キャッシュ（共有プール）内に過去と同一の実行計画があれば再利用します（ソフトパース）。

-  なければ、次のオプティマイザが起動して新規作成します（ハードパース：CPU負荷の高い処理）。

### ② 最適化（オプティマイザ / Optimizer）
-  可能な探索経路（アクセスパス、結合順序、結合方式）の候補を複数シミュレーション。

-  後述するコストモデルに基づき、最も負荷が低いと算出した1つの計画を確定します。

### ③ 実行（エグゼキュータ / Executor）
-  決定された実行計画に沿ってメモリやディスクへ物理アクセスし、結果をクライアントへ返します。

---

## 4. コストベース・オプティマイザ（CBO）と「統計情報」
現代の主要RDBMS（Oracle、PostgreSQL、MySQL等）は、すべてCBO（Cost-Based Optimizer）を採用しています。

**💡コスト（Cost）とは？** ：
コストとは実行時間そのものではなく、「処理を完了するために必要なリソース消費量（ディスクI/O回数やCPU使用量）の相対的な推定値」です。

$$ \text{推定総コスト} ≒ (\text{推定I/Oブロック数} \times \text{重み}) + (\text{推定処理タスク数} \times \text{重み}) $$

オプティマイザは、シミュレーションした複数の実行計画ごとに推定総コストを算出し、その中で **「最小コスト」となる実行計画** を自動選択します。

**コスト計算の源泉「統計情報」**：
オプティマイザは未来を予知できるわけではありません。机上計算のために「テーブルやインデックスに関するカタログデータ（統計情報）」を参照します。

| 統計情報の項目 | 説明 | 影響するオプティマイザの判断 |
|:---|:---|:---|
| 行数（Num Rows）| テーブル全体のレコード件数 | Full Scanの基本負荷、結合の主駆動テーブル判定 |
| ブロック数（Blocks）| データを格納している領域サイズ | ディスクI/O発生量の見積もり |
| カーディナリティ（Cardinality）| 列に含まれるユニークな値の種類の多さ |インデックスで何件まで絞り込めるかの予測 |
| ヒストグラム（Histograms）| 列内のデータの偏り（分布状況）| 不等号検索や偏りのある特定値での絞り込み予測 |

## 5. DBA視点：なぜ実行計画がトラブルシュートの起点になるのか？

結論から言えば、 **「SQL文のテキストを見ただけでは、データベース内部の『物理的な挙動（ディスクI/Oやメモリ消費）』が一切わからないから」** です。

SQLは「何が欲しいか（What）」を指示するだけの言語であり、トラブルの真因（How）はすべてオプティマイザが選択した「実行計画」の中にしか現れません。

### ① コードだけでは物理的な挙動がわからない
```SQL
SELECT * FROM users WHERE status = 'ACTIVE';
```

上記のSQLを見ても、「速いか遅いか」は判断できません。

-  ACTIVE のデータが全体の0.01%なのか、90%なのか？

-  status 列にインデックスがあるのか？

-  DB内部で意図しない型変換が発生していないか？

これらはすべて実行計画を出力して初めて判明する物理的事実です。

### ② オプティマイザは「古い地図」に騙される
オプティマイザは「統計情報が正しい」という前提でコストを計算します。

**実態**：
バッチ処理で夜間に100万件のデータが追加された。

**統計情報**：
古い情報のまま（テーブル行数＝100件と記録されている）。

**結果**：
DBは「100件ならNested Loopsが最速」と誤認し、実際には100万行に対して巨大ループが発生してシステムが遅延・停止する。


### だからこそ「実行計画」が調査の起点になる
スロークエリが発生した際、「勘でSQLを書き換える」アプローチでは、オプティマイザがなぜその遅いルートを選んだのかという根本原因に辿り着けません。

実行計画を開くことで初めて、

-  「オプティマイザがどんな前提（統計情報・コスト見積もり）で動いたのか」

-  「どこで意図しない全表走査や巨大ループが発生しているのか」

というエビデンス（証拠）が白日の下に晒されます。
だからこそDBAは、コードを推測するのではなく、まず実行計画を手に入れて「オプティマイザの判断の矛盾」を論理的に読み解くことから調査を始めるのです。
