# 第1章：バックアップの目的と設計指標（RPO / RTO）

## 1. なぜ「冗長化」だけではデータを守れないのか？

クラウド（AWS RDS / Aurora など）のMulti-AZ構成や、オンプレミスのレプリケーション構成を導入している現場で、最も多い誤解が**「DBが冗長化されているからバックアップは不要（または軽視してよい）」**という思い込みです。

バックアップが守るべき障害は大きく3つに分類され、冗長化で防げるのはその一部に過ぎません。

```text
【障害の種類と、冗長化（レプリケーション）・バックアップの守備範囲】

  1. ハードウェア・インフラ障害（ディスク破損、サーバー故障）
     ├── 冗長化（Multi-AZ） ──> [ 守れる ] 自動フェイルオーバーで継続稼働
     └── バックアップ        ──> [ 守れる ] 新規サーバーへリストアして復旧

  2. 人的ミス・アプリのバグ（WHERE句なしのDELETE/UPDATE、誤ったDROP TABLE）
     ├── 冗長化（Multi-AZ） ──> [ 守れない！ ] 誤操作のSQLもレプリカへ即座に同期される
     └── バックアップ        ──> [ 守れる ] 誤操作が発生する前の時点へ復元

  3. 広域災害・ランサムウェア感染（データセンター被災、アカウント乗っ取り）
     ├── 冗長化（同一リージョン） ──> [ 守れない！ ] 同時に被災・暗号化される
     └── バックアップ（遠隔地保管）──> [ 守れる ] 別リージョン・別アカウントから復元
```

実務において最も発生頻度が高く、かつサービスに致命的なダメージを与えるのは「2. 人的ミス（論理障害）」です。冗長化構成は誤った DELETE 文さえも忠実に待機系へコピーしてしまうため、独立したバックアップの仕組みが不可欠となります。

## 2. 設計の要となる2つの重要指標：RPO と RTO
バックアップ方式を技術選定する前に、必ずビジネス要件（サービスレベル）として以下の2つの指標を定義する必要があります。

```Plaintext
【障害発生から復旧までのタイムラインと RPO / RTO】

  最後のバックアップ       障害発生（誤操作）              サービス再開
  取得時点                 (14:00)                         (14:30)
      │                       │                               │
      ▼                       ▼                               ▼
  ────●───────────────────────×───────────────────────────────●────▶ 時間軸
      │◄──── データ損失 ─────►│◄───────── ダウンタイム ───────►│
      │      (最大許容 = RPO) │          (最大許容 = RTO)     │
      │                       │                               │
      └─ 13:00に取得していた場合                               └─ 復旧作業に30分かかった場合
         RPO = 1時間                                             RTO = 30分
```

### ① RPO（Recovery Point Objective：目標復旧時点）
定義： 「障害発生時、いつの時点のデータまで戻せるようにするか？」（＝最大どれだけのデータ損失を許容できるか）

設計への影響：

RPO = 24時間（1日前の状態でよい）： 毎日深夜1回のフルバックアップのみで要件を満たせます。

RPO = 0〜数分（データ損失をほぼ許容できない）： 定期バックアップに加え、トランザクションログの継続的な退避（PITR）が必須になります。

### ② RTO（Recovery Time Objective：目標復旧時間）
定義： 「障害発生からどれくらいの時間内にシステムを復旧させるか？」（＝許容できる最大ダウンタイム）

設計への影響：

RTO = 1時間： 数TBのデータをSQLダンプから復元する（半日かかる）ような方式は採用できません。高速な物理バックアップやストレージスナップショットを選択する必要があります。

## 3. 本章のまとめ
冗長化（Multi-AZ・レプリケーション）はハードウェア障害対策であり、人的ミス（誤操作）からデータを守れるのはバックアップだけである。

バックアップ設計は技術ありきではなく、ビジネス要件である RPO（許容データ損失時間） と RTO（許容ダウンタイム） を基準に決定する。
