# 第5章：メンテナンス時のデータ退避とリストアのアンチパターン

本番環境でデータ修正パッチ（`UPDATE` / `DELETE`）を流す際や、緊急障害でリストアを行う際、現場のエンジニアがやりがちなミスが二次災害を引き起こします。ここでは実務で頻発するアンチパターンと正しい対処法を解説します。

## 1. 静止点（一貫性）を確保しない論理バックアップ

稼働中の本番データベースから論理バックアップ（ダンプ）を取得する際、オプションを指定せずに実行すると、**バックアップ取得中に他のユーザーが更新したデータと混ざり、テーブル間でデータの不整合が起きる**ケースがあります。

```text
【不整合が起きるメカニズム（例：10:00にダンプ開始）】
  10:00:00  ダンプ処理が「orders（注文親テーブル）」を読み取り完了（注文ID:500 は存在しない）
  10:00:01  アプリが新規注文（注文ID:500）を orders と order_details に INSERT・コミット！
  10:00:02  ダンプ処理が「order_details（注文明細テーブル）」を読み取り（注文ID:500 の明細が取れる！）
  ──> 結果：親レコードがない孤児レコードを含んだ「壊れたバックアップ」が出来上がる！
```

解決策： トランザクション分離レベル（Repeatable Read / Read Consistency）を利用した一貫性スナップショットオプションを必ず付与します。

```Bash
# MySQL (InnoDB): テーブルロックをかけずに開始時点の一貫したスナップショットを取得
mysqldump --single-transaction -u user -p dbname > backup.sql

# PostgreSQL: pg_dump はデフォルトで単一トランザクション内（REPEATABLE READ）で一貫性を保証
pg_dump -Fc -U user dbname > backup.dump
```

2. 本番メンテナンス時の「簡易テーブル退避」の罠
本番環境で数千件のレコードを更新するデータパッチを当てる際、対象テーブルだけを素早く退避するために `CREATE TABLE ... AS SELECT`（CTAS）を使うことは実務で非常に有効です。しかし、戻す際の考慮が抜けているケースが多発します。

NG例： 退避テーブルから本番テーブルへ INSERT で戻そうとして失敗する。

元のテーブルに AUTO_INCREMENT（シーケンス）、外部キー制約、トリガー、NOT NULL制約などが設定されており、単純な書き戻しでエラーになる。

退避テーブルを本番と同じスキーマ（本番データベース内）に作った結果、ストレージ容量を圧迫したり、誤って退避テーブル側を参照・削除したりする。

解決策（安全手順の鉄則）：

退避テーブル名には必ず作業日とチケット番号を付与する（例：bk_users_20261118_t1234）。

データパッチは必ず BEGIN; 〜 COMMIT; のトランザクション内で実行し、UPDATE / DELETE 実行直後に影響行数（ROW_COUNT）を確認してから COMMIT する（件数が想定と1件でも違えば即 ROLLBACK）。

戻し手順（リストアSQL）も作業前に作成し、検証環境でリハーサルしておく。

3. 本番環境へ直接「上書きリストア」してしまう事故
事象： 「14時にAさんが誤って customers テーブルの100件を削除してしまった。慌てて13時のバックアップを本番DBへ直接上書きリストアした。」

何が問題か？：

本番DB全体を13時の状態に巻き戻したため、13時〜14時の間に別ユーザーが正常に登録した「新規注文データ」や「決済データ」まで丸ごと消滅してしまいました（デグレード障害）。

解決策（別インスタンス復元 ＋ 差分抽出）：

部分的な人的ミスを復旧する場合は、本番DBに直接上書きしてはいけません。

バックアップから別の検証用（一時）DBインスタンスにリストアし、そこから失われた customers の100件だけを SELECT（またはダンプ）で抽出し、本番DBへ安全に INSERT で戻します。

```Plaintext
【正しい部分復旧の手順（本番影響ゼロ）】
  [ バックアップ ] ──(リストア)──> [ 一時復元用DB ]
                                         │
                                  失われた100件だけ抽出
                                         │
                                         ▼
                                   [ 本番DB ] へ INSERT で補完（他テーブルの最新データは守られる！）
```

4. 本章のまとめ
稼働中DBの論理バックアップは、必ず一貫性スナップショット（--single-transaction 等）を使用し、テーブル間の不整合を防ぐ。

特定テーブルの誤操作を復旧する際は、本番DBへ直接上書きリストアせず、一時インスタンスに復元してから必要なレコードだけを抜き出して補完するのが鉄則。
