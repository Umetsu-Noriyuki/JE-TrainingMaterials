# 第5章：よくあるトラブルと改善 〜現場のアンチパターンと乖離対策〜

---

## 1. インデックスが無効化される代表的アンチパターン
「インデックスを作成したのに使われない（TABLE ACCESS FULL になる）」という問題の多くは、WHERE句の記述方法に起因します。

### パターン①：暗黙の型変換（Implicit Type Conversion）
最も遭遇頻度が高く、見落としやすいアンチパターンです。列のデータ型と検索条件で渡すリテラルの型が一致していない場合に発生します。

**NG例（文字列型の列に数値を指定）**：
```sql
-- customer_code は VARCHAR2(10) 型
SELECT customer_id, customer_name
FROM customers
WHERE customer_code = 100;
```

**実行計画の挙動（採取データより）**：

```Plaintext
-------------------------------------------------------------------------------
| Id  | Operation         | Name      | Rows  | Bytes | Cost (%CPU)| Time     |
-------------------------------------------------------------------------------
|   0 | SELECT STATEMENT  |           |     1 |    22 |     3   (0)| 00:00:01 |
|*  1 |  TABLE ACCESS FULL| CUSTOMERS |     1 |    22 |     3   (0)| 00:00:01 |
-------------------------------------------------------------------------------
Predicate Information (identified by operation id):
---------------------------------------------------
  1 - filter(TO_NUMBER("CUSTOMER_CODE")=100)
```

**解説**：

RDBMSは型の優先順位に従い、テーブル列側を TO_NUMBER("CUSTOMER_CODE") と関数変換してしまいます。

インデックスツリーに登録されているキー値と一致しなくなるため、索引が使えず全表走査になります。

**OK例（型を厳密に合わせる）**：
```sql
SELECT customer_id, customer_name
FROM customers
WHERE customer_code = '000100'; -- 文字列リテラルとして渡す
```

これにより INDEX RANGE SCAN（または UNIQUE SCAN）へと改善されます。

### パターン②：条件列への関数・演算の適用
検索条件の「左辺（列側）」を加工してしまうケースです。

**NG例（日付列を関数で囲む）**：
```sql
  -- order_date 列にインデックスが存在する
  SELECT *
  FROM orders
  WHERE TRUNC(order_date) = DATE '2026-05-01';
```

**実行計画の挙動（採取データより）**：
```Plaintext
----------------------------------------------------------------------------
| Id  | Operation         | Name   | Rows  | Bytes | Cost (%CPU)| Time     |
----------------------------------------------------------------------------
|   0 | SELECT STATEMENT  |        |  1000 | 25000 |   152   (2)| 00:00:01 |
|*  1 |  TABLE ACCESS FULL| ORDERS |  1000 | 25000 |   152   (2)| 00:00:01 |
----------------------------------------------------------------------------
Predicate Information (identified by operation id):
---------------------------------------------------
  1 - filter(TRUNC(INTERNAL_FUNCTION("ORDER_DATE"))=DATE'2026-05-01')
```

**OK例（範囲指定に変更して左辺の列を無加工にする）**：
```sql
-- 左辺の列は加工せず、右辺の条件側を期間範囲にする
SELECT *
FROM orders
WHERE order_date >= DATE '2026-05-01'
  AND order_date <  DATE '2026-05-02';
```

order_date 列が無加工のまま保たれるため、INDEX RANGE SCAN が有効になります。

### パターン③：前方一致以外のLIKE検索
**NG例**：

WHERE customer_name LIKE '%佐藤%'（中間一致）、LIKE '%株式会社'（後方一致）

B-Treeインデックスは「辞書順（先頭から）」にソートされているため、先頭がワイルドカード（%）の場合はインデックスを辿ることができず、Full Scanになります。

**OK例**：

要件上可能な限り前方一致（WHERE customer_name LIKE '佐藤%'）を使用するか、頻出する場合は全文検索機能（Oracle Text等）の導入を検討します。

## 2. DBA視点の重大事故：「見積もり（Rows）」と「実測」の乖離
SQL構文に問題がなくても、オプティマイザの判断材料である「統計情報」が狂っている場合に深刻な性能障害が発生します。

**典型的な事故シナリオ**：

Nested Loops の暴走

**背景**：

大量バッチ処理により、夜間に orders テーブルへ100万件のデータが追加された。

統計情報の再収集が漏れており、DBのカタログ上は「行数＝100件」のまま記録されている。

**オプティマイザの誤判断**：

「抽出されるのは 1〜2 件だろう（Rows=1 見積もり）」と予測。

「数件なら最速」と判断し、Nested Loops Join を選択。

**実行時の大惨事**：

実際には条件に合致するデータが 50万件 存在していた。

被駆動表へのインデックス検索が 50万回 実行され、ランダムI/Oが跳ね上がり、クエリが何時間も終了しなくなる。

```Plaintext
【オプティマイザの脳内】
  「見積もり Rows = 1 だから、Nested Loops で一瞬で終わるはず！」
                            ↓↓
【実際の実行時】
  「実際は 50万行 あった……。50万回の二重ループが止まらない！（Hash Joinなら数秒で終わったのに）」
```

## 3. 見積もり乖離の調査と是正アプローチ
### ① 実行計画の「Rows」と「実際件数」を突き合わせる
スロークエリ調査時、実行計画の Rows カラムを確認し、実際にその条件で SELECT COUNT(*) を叩いた結果と比較します。

桁が2桁以上乖離している場合（例：見積もり 10件 / 実際 100,000件）、統計情報の陳腐化を疑います。

### ② 対策：統計情報の再収集
正しい「地図」をオプティマイザに渡すため、最新の統計情報を収集します。

```SQL
-- テーブル全体の統計情報を強制収集
EXEC DBMS_STATS.GATHER_TABLE_STATS(
    ownname          => USER,
    tabname          => 'ORDERS',
    estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
    cascade          => TRUE
);
```

### ③ 特定列の値の偏りには「ヒストグラム」
特定の値（例：ステータスが CANCELLED は全体の1%、COMPLETED は99%）に極端な偏りがある場合、均等分布を前提とした基本統計情報では見積もりが狂います。
この場合はヒストグラムを収集することで、特定リテラルに応じた精度の高い見積もりをオプティマイザに行わせることができます。
