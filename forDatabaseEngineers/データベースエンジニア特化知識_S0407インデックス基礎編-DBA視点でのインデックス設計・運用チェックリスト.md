# 第6章：DBA視点でのインデックス設計・運用チェックリスト

保守・運用の現場や、新規機能リリースのレビューにおいて、DBA（データベース管理者）は「検索が速くなるか」だけでなく「更新性能やシステム全体の安定性を損なわないか」という視点でインデックスを評価します。ここでは、実務で特に重要となる4つのチェックポイントを紹介します。

## 1. 1テーブルあたりのインデックス数は過剰になっていないか？

1つのテーブルに10個も20個もインデックスが作成されている状態は危険信号です。
- **DBAの視点：** インデックスが増えるほど、`INSERT` / `UPDATE` / `DELETE` 時のインデックスメンテナンスコストが増大します。目安として **1テーブルあたり3〜5個程度** に抑え、単一インデックスの乱立は複合インデックスへ統合できないか検討します。

## 2. カーディナリティが極端に低いカラムに単一インデックスを貼っていないか？

「性別（男/女）」や「削除フラグ（0/1）」のように、値の種類が2〜3種類しかないカラムへの単一インデックスは原則として逆効果です。
- **DBAの視点：** 全体の50%がヒットするような条件でインデックスを使うと、インデックスとテーブル本体のランダムI/Oが大量に発生し、フルテーブルスキャンよりもはるかに遅くなります（使われないゴミインデックスになる）。複合インデックスの一部として組み込むのが適切です。

## 3. 外部キー（FK）列にインデックスは作成されているか？

親テーブルの主キーには自動的にインデックスが作成されますが、子テーブル側の外部キー列には自動作成されないRDBMS（Oracle, PostgreSQLなど）が多く存在します。
- **DBAの視点：** 外部キーにインデックスがないと、親テーブルと子テーブルの `JOIN` が遅くなるだけでなく、親テーブルの行を更新・削除した際に**子テーブル全体にロックがかかり、深刻なブロッキング障害**を引き起こします。外部キーには原則インデックスを付与します。

## 4. 統計情報の更新と「未使用インデックス」の棚卸しは行われているか？

オプティマイザは「統計情報（テーブルの行数やデータの偏り）」をもとにインデックスを使うかどうかを判断します。
- **DBAの視点：**
  - 大量データ投入直後などに統計情報が古いと、インデックスがあるのにフルスキャンが選ばれる実行計画の劣化が発生します。定期的な統計情報収集（`ANALYZE` / `DBMS_STATS`）が稼働しているかを確認します。
  - また、過去の改修で使われなくなったインデックスを放置せず、システムビュー（`pg_stat_user_indexes` や `V$OBJECT_USAGE` など）で使用状況を監視し、不要なものは削除します。

---

## 研修のまとめ：持続可能なパフォーマンスを維持するために

本研修を通じて、インデックスの内部構造（B+Tree）の仕組みと、複合インデックスの設計原則、そしてインデックスを無効化してしまうSQLのアンチパターンについて学びました。

インデックスはデータベースの検索性能を劇的に引き上げる強力な武器ですが、同時に「更新処理のコスト」と「ストレージ・メモリ資源」を消費する両刃の剣でもあります。設計時には「どのクエリを速くしたいのか」という明確な根拠を持ち、必ず実行計画（`EXPLAIN`）で狙い通りのアクセスパスが選ばれているかを検証する習慣をつけてください。

本資料で学んだDBA視点のチェックポイントを活かし、データ量が増加しても破綻しない堅牢なシステム構築とパフォーマンスチューニングに役立ててください。
