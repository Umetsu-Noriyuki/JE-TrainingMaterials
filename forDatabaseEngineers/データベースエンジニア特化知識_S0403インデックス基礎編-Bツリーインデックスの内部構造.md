# 第2章：Bツリーインデックスの内部構造

主要なRDBMS（Oracle, PostgreSQL, MySQL/InnoDBなど）において、デフォルトかつ最も広く使われているインデックスの構造が **Bツリー（正確にはB+Tree：Balanced Tree）** です。

## 1. B+Treeの階層構造

**目的：データ量がどれだけ増えても、一定の少ないステップ数で目的のデータに到達する**
B+Treeは、データをソートされた状態で保持する木構造（ツリー構造）です。

- **ルートブロック（Root）：** 探索の起点となる最上位のノード（1つだけ存在）。
- **ブランチブロック（Branch）：** 目的の値が存在する範囲を絞り込むための分岐点となる中間ノード。
- **リーフブロック（Leaf）：** 最下層に位置するノード。ここに「インデックス列の値」と、実際のテーブル行が格納されている場所を示す「ポインタ（ROWIDや主キー値）」が格納されます。また、リーフ同士は双方向リストで繋がっており、範囲検索（`<`, `>`, `BETWEEN`）を高速に処理できます。

```text
           [ ルート ] (1〜1000)
            /        \
    [ブランチ]        [ブランチ]
    (1〜500)          (501〜1000)
     /     \            /      \
[リーフ]  [リーフ]  [リーフ]  [リーフ]  <-- 双方向リストで連結
 (値+ポインタ) ──> テーブル本体（ヒープ領域）へアクセス
```

**特徴（バランス木）**： データが数万件から数億件に増えても、木の深さ（階層）は通常 3〜4階層程度 に保たれます。つまり、わずか3〜4回のブロック読み込みで目的のポインタに到達できます。

---

## 2. 代表的なアクセスパス（データの読み取り方）
オプティマイザは、SQLの条件に応じて以下のアクセスパスを選択します。

**Full Table Scan（フルテーブルスキャン）**：

インデックスを使わず、テーブルの先頭から末尾まで全ブロックを読み込む方式。テーブルの大部分（例：全体の15〜20%以上）のデータを取得する場合は、インデックスを経由するより一括で読み込む方が高速になります。

**Index Unique Scan（インデックス一意スキャン）**：

主キー（PK）や一意制約（UNIQUE）が付いたインデックスに対し、= で1件だけをピンポイント検索する最速のアクセスパス。

**Index Range Scan（インデックス範囲スキャン）**：

非一意インデックスでの = 検索や、BETWEEN, >, <, 前方一致 LIKE 'ABC%' など、複数件ヒットする可能性がある場合にリーフブロックを順に辿る方式。

---

## 3. DBA視点：クラスタ化インデックスと非クラスタ化インデックス
RDBMSの製品によって、テーブル本体とインデックスの物理的な格納方法に大きな違いがあります。

**非クラスタ化インデックス（Oracle, PostgreSQLの標準）**：
テーブル本体（ヒープ表）とインデックスは完全に別の領域に保存されます。インデックスでポインタ（ROWID / CTID）を見つけた後、テーブル本体へデータを取りに行く「2段階のアクセス（Table Access by Index Rowid）」が発生します。

**クラスタ化インデックス（MySQL/InnoDB, SQL Serverの標準）**：
主キーのB+Treeのリーフブロックそのものに行データ全体が格納されます。主キーでの検索は極めて高速ですが、副次インデックス（セカンダリインデックス）はポインタとして「主キー値」を持つため、副次インデックス経由の検索では「副次インデックス探索 → 主キーインデックス探索」の2回のツリー探索が発生します。
