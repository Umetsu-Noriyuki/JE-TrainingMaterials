# 第1章：はじめに

---

## 1. 背景と目的

現代のWebシステムや基幹業務アプリケーションにおいて、システムの応答速度低下（パフォーマンス問題）の**約8〜9割はデータベースアクセス（SQL）に起因**します。

CPUやメモリを増強しても、非効率なクエリが1つ走るだけでディスクI/Oやキャッシュメモリが逼迫し、システム全体の遅延・停止を招くケースは珍しくありません。

これまでの開発では「期待通りのデータが取得できるか（結果の正しさ）」が焦点だったかもしれません。しかし、商用環境で大量データや高並行アクセスを扱うエンジニア、
そして **システムの安定稼働を担うデータベース管理者（DBA）** には、次の視点が不可欠です。

* **「このSQLを実行したとき、データベース内部のディスクやメモリはどう動いているのか？」**
* **「なぜ同じ結果を返すSQLなのに、書き方ひとつでミリ秒と数分という極端な差が生まれるのか？」**

ここでは、SQLの文法を理解した次のステップとして、データベースの内部挙動を可視化する最重要ツールである **「実行計画（Execution Plan）」** の読み解き方を体系化し、
勘に頼らない論理的なクエリ改善・障害調査の基礎力を養うことを目的としています。

## 2. 対象読者（前提知識）

本ドキュメントは、以下の前提を満たすメンバーを対象にしています。

| 項目 | 想定レベル・前提条件 |
| :--- | :--- |
| **必須の前提知識** | ・`SELECT`, `WHERE`, `ORDER BY`, `GROUP BY` などの基本構文が書ける・読める<br>・`INNER JOIN`, `LEFT JOIN` 等のテーブル結合を実際に組んだことがある<br>・「主キー（Primary Key）」や「インデックス（索引）」という用語・概念を知っている |
| **直面している課題** | ・SQLは書けるが、遅いときに「とりあえずインデックスを貼る」など勘で試行錯誤している<br>・スロークエリログを見ても、どこから調査に手を付ければよいかわからない |
| **目指す方向性** | ・「SQLを書く側」から「データベースの挙動を監視・設計・運用する側（DBA/インフラ/バックエンド主導）」へステップアップしたい |

※ 本書ではSQL文法の初歩的な解説は省略し、「データベース内部の挙動」に特化して解説します。

## 3. 本書で到達するゴール

全6章を通じて、以下の3段階のスキル習得を目指します。

```text
【レベル1：可視化】
  どんなSQLに対しても、自力で実行計画を出力し、木構造（ツリー）の処理順序を正しく追える。
      ↓
【レベル2：構造理解】
  「Full Table Scan」「Index Scan」「Nested Loops」「Hash Join」といった
  代表的なアクセスパスや結合方式の長所・短所を他者に説明できる。
      ↓
【レベル3：ボトルネック特定（DBA初歩）】
  遅いSQLの実行計画を見た際に、
  「意図しない全表走査が起きている」「行数の見積もりが実際と乖離している」
  といった問題箇所を論理的に指摘できる。
```

## 4. なぜ「勘」ではなく「実行計画」なのか？
パフォーマンス改善において初心者が陥りがちなのが「コードを眺めて勘で書き換える」アプローチです。

「サブクエリをJOINに書き換えたら速くなるかもしれない」

「WHERE句の条件順序を入れ替えたら変わるかもしれない」

しかし、現代のRDBMS（Oracle、PostgreSQL、MySQL等）では、条件句の順序を人間が入れ替えた程度では挙動は変わりません。 データベース内部の頭脳（オプティマイザ）がクエリを解析し、最も効率的だと判断したルートへ自動で再構成するためです。

```Plaintext
【勘によるアプローチ（非推奨）】
  遅いSQL ──> コードを適当に書き換え ──> たまたま速くなった？（原因不明・再発リスク大）

【論理的なアプローチ（DBAの標準手法）】
  遅いSQL ──> 実行計画を確認 ──> ボトルネック特定（例: 暗黙の型変換によるIndex無効化）
          ──> 根拠を持ったピンポイント是正 ──> 再度実行計画で改善を確認
```

「実行計画を読む」スキルは、言語やフレームワークが変わっても一生使えるエンジニアのコアスキルです。
次章では、まず「実行計画とは何か？」「DB内部でどう作られるのか？」のメカニズムへ進みます。
