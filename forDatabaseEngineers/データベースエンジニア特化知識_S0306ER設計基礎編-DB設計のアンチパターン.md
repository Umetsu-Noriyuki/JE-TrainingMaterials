# 第5章：DB設計のアンチパターン

データベース設計において、一見便利そうに見えても、後々の運用フェーズでSQLの複雑化や著しいパフォーマンス低下（実行計画の悪化）を引き起こす「アンチパターン」が存在します。ここでは、現場で遭遇しやすい代表的な設計の罠を解説します。

## 1. カンマ区切りリスト (Jaywalking)

1つのカラムに複数の値をカンマ区切りなどで格納する設計パターンです。第1正規形（1つのセルには1つの値）に違反しています。

- **例：** `account_id` = '1001, 1002, 1005'
- **引き起こす問題：**
  - **インデックスが使えない：** 特定のIDを検索する場合、`LIKE '%1002%'` のような中間一致検索が必須となり、フルテーブルスキャンが避けられません。
  - **JOINが困難：** カンマ区切りの文字列を別のテーブルと結合することは非常に困難で、RDBMSの本来の力を発揮できません。
- **解決策：** 交差テーブル（中間テーブル）を作成し、1行につき1つの値を持つように縦に展開（正規化）する設計へ修正します。

## 2. EAV (Entity-Attribute-Value)

「どんな属性でも保存できる柔軟なテーブル」を目指し、エンティティ（対象）、アトリビュート（属性名）、バリュー（属性値）の3カラムだけで構成する設計です。

- **例：** `(user_id=1, attr_name='age', attr_value='35')`, `(user_id=1, attr_name='job', attr_value='engineer')`
- **引き起こす問題：**
  - **データ型の喪失：** すべての値を文字列型（VARCHARなど）で保存せざるを得ないため、数値の範囲検索（`<`, `>`）や日付計算時に型変換が発生し、インデックスが効きません。
  - **SQLの肥大化：** 複数の属性を1行のレポートとして抽出したい場合、属性の数だけ同じテーブルを自己結合（Self JOIN）する必要があり、実行計画が複雑怪奇になります。
- **解決策：** 適切にカラムを定義したテーブルを設計する。属性が可変で予測不能な場合は、JSON型のカラムを活用する方が現代的かつ効率的です。

## 3. ポリモーフィック関連

1つのテーブルの「親」が複数存在し、それを「親テーブル名」と「親ID」の2つのカラムで管理する設計です。

- **例：** `コメント` テーブルが `親リソース種別='Article'` と `親ID=10` を持つ。（親が記事だったり、画像だったりする）
- **引き起こす問題：**
  - **外部キー制約（FK）が張れない：** 参照先が動的に変わるため、RDBMSの強力な機能であるFK制約を設定できません。結果として、親が存在しない「孤児レコード」が生まれやすくなります。
  - **実行計画への悪影響：** FKがないため、オプティマイザはテーブル間の正確な関係性を把握できず、最適な結合手法を選べないリスクが高まります。
- **解決策：** 親となるテーブルごとに別々の中間テーブルを設計する、あるいは親テーブルに共通のスーパークラス的なテーブルを設ける（クラステーブル継承）などを検討します。
