# 第2章：概念・論理・物理データモデル

データベースの設計（データモデリング）は、ビジネス要件から実際のRDBMS（リレーショナルデータベース管理システム）への実装に至るまで、抽象度に応じて3つの段階に分けて進められます。

## 1. 概念データモデル (Conceptual Data Model)

**目的：ビジネスの世界を整理する**
システム化の対象となる業務にどんなデータが存在し、どう関連しているかを大まかに洗い出した図です。

- **特徴：** 特定のデータベース製品（Oracle Databaseなど）には依存しません。
- **作業内容：** 主要なエンティティ（顧客、商品、注文など）の抽出と、リレーションの定義のみを行います。詳細なアトリビュート（カラム）までは網羅しません。

## 2. 論理データモデル (Logical Data Model)

**目的：データの矛盾や重複を排除し、RDBMSの構造に落とし込む**
概念データモデルをベースに、リレーショナルモデルの規則に従って設計を洗練させるER設計の心臓部となるフェーズです。

- **特徴：** まだ特定のデータベース製品には依存しません。
- **作業内容：**
  - すべてのアトリビュート（カラム）の洗い出し。
  - レコードを一意に特定する **主キー（Primary Key）** の決定。
  -  **正規化（Normalization）** によるデータの重複・矛盾の排除（※第3章で詳述）。
  - 「多対多」のリレーションシップを、交差テーブル（中間テーブル）を用いて解消する。

## 3. 物理データモデル (Physical Data Model)

**目的：特定のデータベース製品上で、整合性とパフォーマンスを確保する**
論理データモデルを、実際に稼働させるRDBMSの仕様に合わせて変換する最終フェーズです。保守・運用エンジニアが普段最も目にするのは、このモデルに基づいて構築されたスキーマです。

- **作業内容：**
  - **物理名の付与：** 「顧客」→ `CUSTOMERS` のように、アルファベットを用いた命名を行います。
  - **データ型の決定：** `VARCHAR2(50)`、`NUMBER(10,0)`、`DATE` など、製品固有の適切なデータ型とサイズを定義します。
  - **制約（Constraint）の定義：** `NOT NULL`、`UNIQUE`、外部キー（`FOREIGN KEY`）などを明記し、不正なデータが混入するのをデータベース側でブロックします。
  - **インデックス設計：** 検索パフォーマンスを向上させるため、どのカラムにインデックスを作成するかを設計します。

## 4. DBA視点：物理設計がオプティマイザに与える影響

物理データモデルの設計（制約やデータ型）は、単にデータを格納するためだけのものではありません。
**ここで定義された主キー、外部キー、NOT NULL制約などの情報は、RDBMSの「オプティマイザ」が実行計画を作成する際の重要なインプット（統計・メタデータ）になります。**

例えば、制約が正しく定義されていない（本当は一意なのにUNIQUE制約がない、等）場合、オプティマイザは「関連するレコードが複数存在するかもしれない」と保守的に判断し、最適なアクセスパスや結合順序を選択できなくなることがあります。物理設計の妥当性は、システムのパフォーマンスに直結します。
