# 第5章：インデックスが使われないアンチパターン

せっかく適切なインデックスを作成しても、SQLの書き方ひとつでオプティマイザがインデックスを使用できず、フルテーブルスキャン（全件走査）に陥るケースがあります。ここでは、現場で頻繁に発生する代表的なアンチパターンを解説します。

## 1. インデックス列に対する演算・関数の適用

`WHERE` 句の左辺（インデックスが張られているカラム）に計算式や関数を適用すると、元のインデックス値と一致しなくなるためインデックスが使われません。

**NG例：**
  ```sql
  SELECT * FROM orders WHERE price * 1.1 >= 11000;
  SELECT * FROM users WHERE SUBSTR(user_code, 1, 3) = 'JPN';
  ```

**解決策：** 右辺（比較対象の値）側で計算するか、前方一致検索に書き換えます。

```SQL
SELECT * FROM orders WHERE price >= 11000 / 1.1;
SELECT * FROM users WHERE user_code LIKE 'JPN%';
```

## 2. 暗黙の型変換 (Implicit Type Conversion)
カラムのデータ型と、検索条件で渡す値のデータ型が異なると、RDBMSが内部で自動的に型変換関数を挿入します。結果として「カラムに関数を適用した状態」と同じになり、インデックスが無効化されます。

**NG例：** customer_code が文字列型（VARCHAR）なのに、数値リテラルで検索している。

```SQL
-- 内部的に TO_NUMBER(customer_code) = 10025 のように変換される
SELECT * FROM customers WHERE customer_code = 10025;
```

**解決策：** 必ずテーブル定義と一致するデータ型（文字列ならシングルクォートで囲む）を指定します。

```SQL
SELECT * FROM customers WHERE customer_code = '10025';
```

## 3. 中間一致・後方一致の LIKE 検索
Bツリーインデックスは「文字列の先頭から順」に辞書順で並んでいるため、先頭が固定されていない検索ではツリーを辿ることができません。

**NG例：** WHERE item_name LIKE '%ノートPC%'（中間一致）、WHERE item_name LIKE '%PC'（後方一致）

**解決策：**

-  業務要件上可能であれば、前方一致（LIKE 'ノートPC%'）に限定する。

-  どうしても部分一致が必要な場合は、通常のBツリーではなく「全文検索インデックス（Full-Text Index / PGroongaなど）」の導入を検討する。

## 4. NULL検索（IS NULL / IS NOT NULL）や否定形（<>, NOT IN）
**特徴：**

- 多くのRDBMS（特にOracleの標準Bツリーなど）では、すべてがNULLの行はインデックスに格納されません。そのため WHERE col IS NULL ではインデックスが使われない場合があります。

-  WHERE status <> 'CANCELLED' のような否定形は「それ以外の膨大なデータを探す」処理になるため、オプティマイザがフルスキャンを選択しやすくなります。

**解決策：** 否定形ではなく肯定形（WHERE status IN ('NEW', 'SHIPPED')）で条件を指定します。
