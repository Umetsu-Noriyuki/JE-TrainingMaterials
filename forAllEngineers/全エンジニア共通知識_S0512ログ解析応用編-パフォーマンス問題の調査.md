### 3.1 パフォーマンス問題とは？

#### ① パフォーマンス問題とは？

パフォーマンス問題とは、システムの処理速度や応答性能が低下し、利用者に影響が出ている状態のこと。

例えば、次のような現象がある。

- Webページの表示に時間がかかる
- APIのレスポンスが遅い
- データベースの検索に時間がかかる
- アプリの操作に時間がかかる
- 大量のアクセスがあるとシステムが重くなる

システムが停止していなくても、処理が遅ければユーザーの利便性は低下する。

#### ② パフォーマンス問題が発生する原因

パフォーマンス問題には、さまざまな原因がある。

| 原因 | 具体例 |
|---|---|
| アプリケーション | 非効率な処理やループ |
| データベース | SQLの実行に時間がかかる |
| ネットワーク | 通信の遅延やタイムアウト |
| CPU | CPU使用率が高く、処理が追いつかない |
| メモリ | メモリ不足やメモリリーク |
| 外部サービス | 外部APIからの応答が遅い |

原因によって調査する対象が異なるため、最初から1つに決めつけないことが重要。

#### ③ パフォーマンスを確認する主な指標

パフォーマンス問題を調査するときは、次のような指標を確認する。

| 指標 | 意味 |
|---|---|
| レスポンスタイム | リクエストから応答までにかかった時間 |
| スループット | 一定時間内に処理できたリクエスト数 |
| CPU使用率 | CPUがどの程度使用されているか |
| メモリ使用率 | メモリがどの程度使用されているか |
| エラー率 | 全リクエストのうちエラーになった割合 |

例えば、レスポンスタイムが急に長くなり、CPU使用率も高くなっている場合は、サーバーの処理負荷が原因である可能性がある。

#### ④ ログを使ったパフォーマンス調査

ログには、処理にかかった時間や処理対象などを記録できる。

例えば、次のようなログがある。

```text
[INFO] UserService ユーザー情報取得開始
[INFO] UserService ユーザー情報取得完了 duration=2500ms
```

このログから、ユーザー情報の取得に2.5秒かかっていることが分かる。

通常より処理時間が長い場合は、SQLや外部API、アプリケーションの処理などを詳しく調査する。

#### ⑤ まとめ

パフォーマンス問題とは、システムの処理速度や応答性能が低下している状態。

原因はアプリケーション、DB、ネットワーク、CPU、メモリ、外部サービスなどさまざま。

ログやメトリクスを使って状況を把握し、原因を切り分けることが重要。

### 3.2 レスポンス遅延の調査

#### ① レスポンス遅延とは？

レスポンス遅延とは、リクエストを送信してから、サーバーから応答が返ってくるまでに時間がかかる状態のこと。

例えば、通常は0.2秒で完了するAPIが、突然5秒かかるようになった場合、レスポンス遅延が発生していると考えられる。

レスポンスが遅くなると、ユーザーの操作性が悪くなり、タイムアウトやエラーにつながる可能性もある。

#### ② レスポンス遅延が発生する主な原因

| 原因 | 具体例 |
|---|---|
| DB処理 | SQLの実行に時間がかかる |
| アプリケーション | 複雑な計算や非効率な処理 |
| ネットワーク | 通信に時間がかかる |
| 外部API | 外部サービスからの応答が遅い |
| サーバー負荷 | CPUやメモリが不足している |

最初から原因を決めつけず、処理のどの部分で時間がかかっているかを調査することが重要。

#### ③ ログでレスポンス時間を確認する

ログに処理時間を記録しておくと、どの処理に時間がかかっているか確認しやすくなる。

例えば、次のようなログがあるとする。

```text
[INFO] API /users 開始
[INFO] UserRepository DB検索完了 duration=3000ms
[INFO] API /users 完了 duration=3200ms
```

このログから、次のことが分かる。

- API全体の処理時間は3,200ms
- DB検索に3,000msかかっている
- API全体の処理時間の大部分をDB検索が占めている

この場合、DB検索の処理を詳しく調査する必要がある。

#### ④ 処理時間を分解して調査する

API全体の処理時間だけでは、原因を特定できないことがある。

そのため、処理を細かく分けて時間を計測する。

例えば、次のような流れでAPIが動作しているとする。

1. リクエスト受信
2. DB検索
3. 外部API通信
4. レスポンス生成
5. レスポンス返却

それぞれの処理時間を記録すれば、どこに時間がかかっているか判断しやすくなる。

#### ⑤ レスポンス遅延の調査手順

1. 遅延が発生しているAPIや機能を特定する
2. 通常時と現在のレスポンスタイムを比較する
3. ログから処理時間を確認する
4. 処理を分解して遅い箇所を特定する
5. DB・ネットワーク・外部APIなどを調査する
6. 原因に対する改善を行い、処理時間が改善したか確認する

#### ⑥ まとめ

レスポンス遅延を調査するときは、API全体の処理時間だけでなく、内部の処理ごとの時間も確認する。

ログに処理時間を記録しておくことで、時間がかかっている箇所を特定しやすくなる。

### 3.3 スロークエリの調査

#### ① スロークエリとは？

スロークエリとは、実行に時間がかかっているSQLのこと。

データベースへの検索や更新に時間がかかると、API全体のレスポンスも遅くなる可能性がある。

例えば、ユーザー情報を取得するSQLに3秒かかっている場合、そのSQLがパフォーマンス問題の原因になっている可能性がある。

#### ② スロークエリが発生する主な原因

| 原因 | 具体例 |
|---|---|
| インデックス不足 | 検索対象のデータを効率よく探せない |
| データ量の増加 | 大量のデータを検索・処理している |
| 非効率なSQL | 不要なデータまで取得している |
| JOINの負荷 | 大量のテーブルを結合している |
| 条件の問題 | 検索条件によって効率が悪くなっている |

#### ③ スロークエリログとは？

スロークエリログとは、実行に時間がかかったSQLを記録するログのこと。

例えば、次のような情報を確認できる。

- 実行されたSQL
- SQLの実行時間
- 実行日時
- 対象のデータベースやテーブル

これらを確認することで、時間がかかっているSQLを特定しやすくなる。

#### ④ スロークエリの調査例

例えば、次のSQLがあるとする。

```sql
SELECT *
FROM users
WHERE email = 'sample@example.com';
```

このSQLの実行に時間がかかっている場合、次のような点を調査する。

- email列にインデックスが設定されているか
- usersテーブルのデータ量が多すぎないか
- SQLの実行計画に問題がないか
- 不要な列まで取得していないか

特に、SQLの実行計画を確認すると、データベースがどのように検索や結合を行っているか把握できる。

#### ⑤ スロークエリを改善する方法

主な改善方法は次のとおり。

- **インデックスの追加**：検索対象のデータを効率よく探せるようにする
- **SQLの見直し**：不要な検索や結合を減らす
- **取得データの削減**：必要な列や行だけ取得する
- **実行計画の確認**：非効率な検索方法になっていないか確認する

ただし、インデックスを増やしすぎると、INSERTやUPDATEなどの更新処理に負荷がかかる場合があるため注意する。

#### ⑥ まとめ

スロークエリとは、実行に時間がかかっているSQLのこと。

スロークエリログやSQLの実行計画を確認し、インデックスやSQLの内容を見直すことで、データベースの処理性能を改善できる。

### 3.4 CPU・メモリ使用率の調査

#### ① CPU使用率とは？

CPU使用率とは、CPUがどの程度処理に使われているかを表す指標。

CPU使用率が高い状態が続くと、処理が追いつかず、レスポンスが遅くなる可能性がある。

例えば、CPU使用率が常に95%程度になっている場合、サーバーに大きな負荷がかかっている可能性がある。

#### ② CPU使用率が高くなる主な原因

- 大量のリクエストが集中している
- 非効率なプログラムが実行されている
- 重い計算処理が繰り返されている
- 無限ループなどの不具合が発生している
- バックグラウンド処理がCPUを大量に使用している

ログやメトリクスを確認し、どの処理がCPUを多く使用しているか調査する。

#### ③ メモリ使用率とは？

メモリ使用率とは、サーバーのメモリがどの程度使用されているかを表す指標。

メモリが不足すると、処理が遅くなったり、アプリケーションが異常終了したりする可能性がある。

#### ④ メモリ不足が発生する主な原因

- 一度に大量のデータを読み込んでいる
- 不要なデータをメモリに保持し続けている
- メモリリークが発生している
- 同時に大量の処理が実行されている

#### ⑤ メモリリークとは？

メモリリークとは、プログラムが不要になったメモリを適切に解放できず、使用メモリが増え続ける現象のこと。

例えば、処理が終了しているのに不要なデータを保持し続けていると、メモリの空き容量が少なくなっていく。

その結果、処理速度の低下やアプリケーションの異常終了につながることがある。

#### ⑥ ログを使った調査方法

CPUやメモリの使用率は、主にメトリクスで確認する。

一方、ログでは、その時間帯にどのような処理やエラーが発生していたかを確認する。

例えば、次のような情報を組み合わせて調査する。

| 確認対象 | 調査する内容 |
|---|---|
| CPU使用率 | 急激に上昇していないか |
| メモリ使用率 | 徐々に増加し続けていないか |
| アプリケーションログ | 特定の処理が繰り返されていないか |
| エラーログ | メモリ不足などのエラーが発生していないか |

#### ⑦ まとめ

CPUやメモリの使用率が高くなると、レスポンス遅延やアプリケーションの異常終了につながる可能性がある。

メトリクスで使用状況を確認し、ログから原因となる処理を調査することが重要。

### 3.5 ボトルネック分析

#### ① ボトルネックとは？

ボトルネックとは、システム全体の処理速度を低下させている原因となる箇所のこと。

例えば、複数の処理が順番に実行される場合、そのうち1つの処理だけが極端に遅いと、全体の処理時間も長くなる。

このように、全体の性能を制限している箇所をボトルネックという。

#### ② ボトルネックの具体例

例えば、注文APIが次のような処理を行っているとする。

| 処理 | 実行時間 |
|---|---:|
| 注文情報の受信 | 50ms |
| DB検索 | 100ms |
| 外部決済API通信 | 3,000ms |
| レスポンス生成 | 50ms |
| 合計 | 3,200ms |

この場合、外部決済APIとの通信に3,000msかかっている。

そのため、外部決済APIとの通信がボトルネックになっている可能性が高い。

#### ③ ボトルネックを特定する方法

ボトルネックを特定するには、処理全体を細かく分解して調査する。

主に次の情報を確認する。

- APIごとのレスポンスタイム
- DBのSQL実行時間
- 外部APIとの通信時間
- CPU使用率
- メモリ使用率
- 分散トレーシングの処理時間

特に、分散トレーシングを利用すると、複数サービスのどこで時間がかかっているか把握しやすい。

#### ④ ボトルネックを改善する方法

原因となる箇所によって改善方法は異なる。

| ボトルネック | 改善方法 |
|---|---|
| SQLの実行が遅い | SQLやインデックスを見直す |
| 外部API通信が遅い | タイムアウトや通信方法を見直す |
| CPU使用率が高い | 処理の効率化や負荷分散を行う |
| メモリ不足 | メモリ使用量やデータ保持方法を見直す |
| サーバーへのアクセス集中 | サーバーの増強や負荷分散を検討する |

ただし、やみくもにサーバーを増やすのではなく、まず原因を特定してから適切な改善を行うことが重要。

#### ⑤ 改善後の確認

ボトルネックを改善したら、必ず改善前後の状態を比較する。

例えば、外部API通信を改善した結果、次のようになったとする。

| 項目 | 改善前 | 改善後 |
|---|---:|---:|
| 外部API通信 | 3,000ms | 500ms |
| API全体 | 3,200ms | 700ms |

このように、処理時間が短くなったことを確認する。

また、改善によって別の箇所が新たなボトルネックになっていないかも確認する。

#### ⑥ まとめ

ボトルネック分析とは、システム全体の処理速度を低下させている箇所を特定すること。

処理時間やCPU・メモリ使用率、分散トレーシングなどを利用して原因を調査し、適切な改善を行う。

改善後は、必ず数値を比較して効果を確認する。

### 3.6 第3章まとめ

#### ① パフォーマンス問題とは？

パフォーマンス問題とは、システムの処理速度や応答性能が低下すること。

主な原因には次のようなものがある。

- アプリケーションの処理負荷
- データベースの処理遅延
- ネットワークの通信遅延
- CPUやメモリのリソース不足
- 外部サービスとの通信遅延

調査では、ログだけでなくメトリクスも活用する。

#### ② レスポンス遅延の調査

レスポンス遅延とは、リクエストを受け取ってからレスポンスを返すまでに時間がかかる状態。

処理を細かく分けて、どこで時間がかかっているか確認する。

- API全体の処理時間
- DB検索の時間
- 外部APIとの通信時間
- アプリケーション内部の処理時間

#### ③ スロークエリの調査

スロークエリとは、実行に時間がかかっているSQLのこと。

主な原因は次のとおり。

- インデックスが適切に設定されていない
- データ量が多い
- SQLの書き方が非効率
- JOINなどの処理に時間がかかっている

SQLの実行時間や実行計画を確認し、必要に応じてSQLやインデックスを改善する。

#### ④ CPU・メモリ使用率の調査

CPU使用率が高い場合、処理負荷が大きくなっている可能性がある。

メモリ使用率が高い場合、メモリ不足やメモリリークなどが考えられる。

- CPU使用率：CPUがどの程度処理に使われているか
- メモリ使用率：メモリがどの程度使用されているか
- メモリリーク：不要になったメモリが解放されず、使用量が増え続ける現象

メトリクスで状況を把握し、ログから原因を調査する。

#### ⑤ ボトルネック分析

ボトルネックとは、システム全体の処理速度を低下させている箇所のこと。

処理を細かく分解し、時間がかかっている箇所を特定する。

改善後は、改善前後の数値を比較して効果を確認する。

#### ⑥ 第3章の重要ポイント

パフォーマンス問題を調査するときは、次の流れを意識する。

1. どの機能・APIで遅延が発生しているか確認する。
2. ログやメトリクスから状況を把握する。
3. 処理を分解して原因となる箇所を特定する。
4. SQLやプログラム、サーバー構成などを改善する。
5. 改善後の数値を確認し、効果を検証する。

パフォーマンス問題は、単に「処理が遅い」と判断するだけでは不十分。

ログ・メトリクス・分散トレーシングなどを組み合わせ、原因を数値で把握することが重要。
