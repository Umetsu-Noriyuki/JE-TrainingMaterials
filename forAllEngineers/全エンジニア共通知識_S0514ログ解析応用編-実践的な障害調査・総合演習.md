### 5.1 実践演習の進め方

#### ① 実践的な障害調査とは？

実践的な障害調査とは、実際のシステムで発生した問題を想定し、ログやメトリクスなどを使って原因を特定すること。

これまで学んできた知識を組み合わせて、障害の発生状況から根本原因まで調査する。

#### ② 障害調査の基本的な流れ

実際の障害調査では、次の流れを意識する。

1. 障害の発生状況を確認する。
2. エラーが発生した時刻を確認する。
3. 関連するログを収集する。
4. エラー発生前後の処理を追跡する。
5. メトリクスやDBの状態を確認する。
6. 根本原因を特定する。
7. 改善策を検討する。

#### ③ 調査に使用する情報

障害調査では、複数の情報を組み合わせることが重要。

| 情報 | 確認する内容 |
|---|---|
| アプリケーションログ | エラーや処理の流れ |
| DBログ | SQLエラーや接続状況 |
| アクセスログ | リクエスト数やHTTPステータス |
| メトリクス | CPU・メモリ・レスポンス時間 |
| 分散トレーシング | サービス間の処理時間や通信状況 |

1つの情報だけでは原因を特定できない場合もあるため、複数の情報を組み合わせて判断する。

#### ④ 原因と推測を区別する

障害調査では、確認できた事実と、まだ確定していない推測を区別する。

例えば、

- 事実：DB接続エラーが10時頃から発生している
- 推測：DB接続数の上限に達した可能性がある
- 確認事項：実際のDB接続数や接続上限を確認する

このように、推測だけで原因を決めつけず、ログや数値などの根拠を確認することが重要。

#### ⑤ まとめ

実践的な障害調査では、ログ・メトリクス・分散トレーシングなどを組み合わせて調査する。

また、確認できた事実と推測を区別し、根拠をもとに原因を特定することが重要。

### 5.2 APIエラーとDB障害の調査

#### ① APIエラーとDB障害の関係

APIでHTTP 500などのエラーが発生した場合、必ずしもAPIそのものに原因があるとは限らない。

APIの裏側で処理しているDBとの接続や、SQLの実行に問題が発生している可能性もある。

例えば、注文APIでエラーが発生した場合、次のような処理の流れが考えられる。

1. ユーザーが注文APIを呼び出す
2. APIが注文登録処理を開始する
3. DBに接続しようとする
4. DBへの接続に失敗する
5. 注文登録処理が失敗する
6. APIがHTTP 500を返す

この場合、表面上はAPIエラーに見えるが、根本原因はDB接続の問題である可能性がある。

#### ② ログから原因を特定する

実際のログを確認してみる。

```text
14:00:01 INFO  API /orders requestId=req-789 userId=42
14:00:01 INFO  OrderService 注文登録開始
14:00:02 ERROR DB connection timeout
14:00:02 ERROR OrderService 注文登録失敗
14:00:02 ERROR API /orders HTTP 500
```

このログから、次のことが分かる。

| 時刻 | ログ | 分かること |
|---|---|---|
| 14:00:01 | API /orders | 注文APIが呼び出された |
| 14:00:01 | 注文登録開始 | 注文処理が開始された |
| 14:00:02 | DB connection timeout | DB接続がタイムアウトした |
| 14:00:02 | 注文登録失敗 | DB接続に失敗し、処理が失敗した |
| 14:00:02 | HTTP 500 | APIがエラーを返した |

このように、ログを時系列で確認することで、エラーが発生するまでの流れを把握できる。

#### ③ DB障害の主な原因

DBに関連する障害には、いくつかの種類がある。

| 原因 | 内容 | 確認すること |
|---|---|---|
| DB接続エラー | DBに接続できない | DBの稼働状態、接続設定 |
| 接続数の上限 | DBへの接続数が上限に達している | 現在の接続数、最大接続数 |
| 接続プール枯渇 | アプリ側で利用できるDB接続が不足している | 接続プールの使用数、解放状況 |
| SQLエラー | SQLの実行に失敗している | SQL文、テーブル、制約 |
| スロークエリ | SQLの実行に時間がかかっている | 実行時間、実行計画、インデックス |
| DB負荷の増大 | DBの処理能力が不足している | CPU、メモリ、同時実行数 |

特に、接続プールの枯渇には注意が必要。

接続プールとは、アプリケーションがDBに接続するための接続をあらかじめ確保し、再利用する仕組みである。

接続が適切に解放されなかったり、同時アクセスが増えたりすると、利用できる接続が不足することがある。

#### ④ APIログ・アプリログ・DBログを組み合わせる

障害調査では、1種類のログだけで判断しないことが重要。

| 調査対象 | 確認する内容 |
|---|---|
| APIログ | どのAPIでエラーが発生したか |
| アプリケーションログ | どの処理で失敗したか |
| DBログ | DB側でエラーや負荷が発生していないか |
| メトリクス | CPU、メモリ、接続数などに異常がないか |

また、Request IDやTrace IDが記録されている場合は、それを使って関連するログをまとめて検索する。

これにより、APIの呼び出しからDB処理まで、一連の流れを追跡できる。

#### ⑤ 障害調査から復旧・確認まで

原因を特定したら、復旧対応と正常性の確認を行う。

基本的な流れは次のとおり。

1. エラーが発生したAPIと時間帯を特定する
2. APIログ・アプリログ・DBログを確認する
3. DB接続数や接続プールの状態を確認する
4. 原因に応じて設定変更や負荷軽減などの対応を行う
5. APIが正常に応答するか確認する
6. DBへの接続数やエラー率が正常に戻ったか確認する
7. 必要に応じてデータの整合性も確認する

なお、注文登録などの更新処理では、エラーが返ったからといってすぐに再実行してはいけない場合がある。

API側ではエラーになっていても、DBへの登録自体は完了している可能性があるためだ。

再実行する前に、注文データが登録済みかどうかを確認することも重要である。

#### ⑥ 5.2 まとめ

- APIのHTTP 500は、DB障害が原因で発生することもある。
- ログを時系列で確認し、エラー発生までの流れを把握する。
- DB接続エラー、接続数の上限、SQLエラー、スロークエリなどを切り分ける。
- APIログ・アプリログ・DBログ・メトリクスを組み合わせて調査する。
- 更新処理の再実行前には、データがすでに登録されていないか確認する。

### 5.3 分散システムの障害調査

#### ① 分散システムで障害調査が難しい理由

分散システムでは、1つの処理を複数のサービスが連携して実行する。

例えば、ネットショップの注文処理では、次のようなサービスが関係する。

1. API Gateway：リクエストを受け付ける
2. Order Service：注文情報を処理する
3. Payment Service：決済を処理する
4. Notification Service：注文完了通知を送信する

このとき、注文処理が失敗しても、どのサービスで問題が発生したのかすぐには分からない。

また、あるサービスの障害が、別のサービスのエラーとして表面化することもある。

そのため、サービスをまたいでログを追跡する必要がある。

#### ② Trace IDを使って処理を追跡する

分散システムの調査では、Trace IDが重要になる。

Trace IDとは、複数のサービスにまたがる1つの処理を識別するためのIDである。

例えば、注文処理に次のTrace IDが付与されたとする。

`traceId=abc-123`

各サービスのログに同じTrace IDが記録されていれば、関連するログをまとめて検索できる。

```text
15:00:01 INFO  ApiGateway      traceId=abc-123 注文リクエスト受信
15:00:02 INFO  OrderService    traceId=abc-123 注文処理開始
15:00:03 INFO  PaymentService  traceId=abc-123 決済処理開始
15:00:05 ERROR PaymentService  traceId=abc-123 決済APIタイムアウト
15:00:05 ERROR OrderService    traceId=abc-123 注文処理失敗
15:00:05 ERROR ApiGateway      traceId=abc-123 HTTP 500
```

このログから、次の流れが分かる。

- API Gatewayでリクエストを受信
- Order Serviceで注文処理を開始
- Payment Serviceで決済処理を開始
- 決済APIがタイムアウト
- 注文処理が失敗し、HTTP 500が返された

この場合、最初にエラーが発生しているPayment Serviceを重点的に調査する。

#### ③ 分散トレーシングで処理の流れを確認する

分散トレーシングとは、複数のサービスをまたぐ処理の流れや所要時間を可視化する仕組みである。

Trace IDで処理全体を識別し、Spanという単位で各処理の開始・終了時刻や結果を記録する。

例えば、次のような情報を確認できる。

| サービス | 処理 | 所要時間 | 結果 |
|---|---|---:|---|
| API Gateway | リクエスト受付 | 100ms | 成功 |
| Order Service | 注文処理 | 200ms | 失敗 |
| Payment Service | 決済処理 | 3000ms | タイムアウト |

この例では、Payment Serviceの処理に時間がかかっていることが分かる。

ログだけでなく、各処理にかかった時間も確認することで、原因を特定しやすくなる。

#### ④ 複数サービスのログを調査する手順

分散システムで障害が発生した場合、次の順番で調査する。

1. 障害が発生した時間帯を確認する
2. Trace IDやRequest IDを取得する
3. Trace IDを使って各サービスのログを検索する
4. ログを時系列に並べて処理の流れを確認する
5. 最初に異常が発生したサービスを特定する
6. 該当サービスのログやメトリクスを詳しく調査する
7. 原因に応じて修正・復旧する

ただし、最初にエラーが記録されたサービスが、必ずしも根本原因とは限らない。

例えば、別のサービスから応答が返ってこないためにタイムアウトが発生している可能性もある。

エラーが発生したサービスだけでなく、その前後のサービスも確認することが重要。

#### ⑤ 調査時に注意すること

分散システムでは、次の点にも注意する必要がある。

| 注意点 | 内容 |
|---|---|
| ログの時刻 | サーバー間で時刻にずれがある可能性がある |
| リトライ | 同じ処理が複数回実行されている可能性がある |
| タイムアウト | 呼び出し元と呼び出し先の両方でエラーが記録されることがある |
| Trace ID | サービス間で正しく引き継がれているか確認する |

特にリトライには注意が必要。

例えば、決済サービスから応答が返ってこなくても、実際には決済が完了している場合がある。

その状態で再実行すると、二重決済につながる可能性がある。

そのため、エラーが発生した場合は処理の実行状況も確認する必要がある。

#### ⑥ 5.3 まとめ

- 分散システムでは、複数のサービスをまたいで障害が発生する。
- Trace IDを使うことで、関連するログをまとめて追跡できる。
- 分散トレーシングでは、サービスごとの処理内容や所要時間を確認できる。
- ログを時系列で並べ、最初に異常が発生した箇所を調査する。
- タイムアウトやリトライによる二次的なエラーにも注意する。

### 5.4 パフォーマンス低下の調査

#### ① パフォーマンス低下とは？

パフォーマンス低下とは、システムの処理速度や応答性能が悪くなること。

例えば、次のような現象が発生する。

- APIのレスポンスが遅くなる
- 画面の読み込みに時間がかかる
- DBの検索に時間がかかる
- 同時アクセスが増えると処理が失敗する

パフォーマンス低下の原因は1つとは限らない。

そのため、アプリケーション・DB・外部API・サーバーなど、複数の観点から調査する必要がある。

#### ② まずは異常が発生している範囲を確認する

最初に、どの機能やAPIで遅延が発生しているのかを確認する。

例えば、次のような情報を確認する。

| 確認項目 | 内容 |
|---|---|
| 発生時刻 | いつから遅くなったか |
| 対象API | どのAPIで遅延しているか |
| 発生範囲 | 特定の機能か、システム全体か |
| 発生頻度 | 常に遅いのか、一時的なのか |
| 影響範囲 | どのユーザーや処理に影響しているか |

また、障害発生前の正常な状態と比較することも重要。

普段は200msで完了するAPIが、突然3000msになった場合、通常時との差から異常を判断できる。

#### ③ ログから処理時間を確認する

アプリケーションログに処理時間が記録されていれば、どの処理に時間がかかっているのかを確認できる。

例えば、次のログを見てみる。

```text
16:00:01 INFO  API /orders 開始
16:00:01 INFO  OrderService 開始
16:00:01 INFO  DB検索開始
16:00:04 INFO  DB検索完了 duration=2800ms
16:00:04 INFO  OrderService 完了 duration=2900ms
16:00:04 INFO  API /orders 完了 duration=3000ms
```

このログから、API全体の処理時間は3000msで、そのうちDB検索に2800msかかっていることが分かる。

つまり、今回の遅延はDB検索が主な原因である可能性が高い。

#### ④ メトリクスから原因を調査する

ログだけでなく、メトリクスも確認する。

メトリクスとは、システムの状態を数値で表した情報のこと。

代表的な確認項目は次のとおり。

| メトリクス | 確認する内容 |
|---|---|
| CPU使用率 | CPUに処理負荷が集中していないか |
| メモリ使用率 | メモリ不足やメモリリークが発生していないか |
| DB接続数 | DB接続が上限に達していないか |
| レスポンスタイム | APIの応答時間が長くなっていないか |
| エラー率 | エラーが増加していないか |
| リクエスト数 | アクセスが急増していないか |

例えば、アクセス数が急増したタイミングでCPU使用率も上昇している場合、アクセス増加によるサーバー負荷が原因の可能性がある。

#### ⑤ パフォーマンス低下の主な原因

パフォーマンス低下には、さまざまな原因がある。

| 原因 | 内容 | 調査すること |
|---|---|---|
| スロークエリ | DB検索に時間がかかる | SQL、実行計画、インデックス |
| CPU負荷 | CPUの処理能力が不足する | CPU使用率、処理量 |
| メモリ不足 | メモリが不足して処理が遅くなる | メモリ使用率、メモリリーク |
| 外部API遅延 | 外部サービスからの応答が遅い | 通信時間、タイムアウト |
| アクセス集中 | 同時リクエストが増加する | リクエスト数、同時接続数 |
| DB接続不足 | DB接続を確保できない | 接続数、接続プール |

原因によって確認するログやメトリクスが異なるため、状況に応じて調査対象を切り替える必要がある。

#### ⑥ ボトルネックを特定する

ボトルネックとは、システム全体の処理速度を低下させている原因となる部分のこと。

例えば、次のような処理があるとする。

| 処理 | 所要時間 |
|---|---:|
| API受付 | 100ms |
| アプリケーション処理 | 200ms |
| DB検索 | 300ms |
| 外部決済API | 3000ms |
| 合計 | 3600ms |

この場合、外部決済APIの処理に最も時間がかかっている。

そのため、外部決済APIとの通信状況や、相手側の応答時間を重点的に調査する。

ただし、処理時間だけで判断せず、リトライや並列処理などの影響も確認することが重要。

#### ⑦ 調査から改善・確認まで

パフォーマンス低下を調査するときは、次の流れで進める。

1. 遅延が発生している機能やAPIを特定する
2. 正常時と異常時のレスポンスタイムを比較する
3. ログから処理ごとの所要時間を確認する
4. CPU・メモリ・DB接続数などのメトリクスを確認する
5. ボトルネックとなっている処理を特定する
6. 原因に応じてSQLや設定、処理方法などを改善する
7. 改善後のレスポンスタイムやエラー率を確認する

改善前後の数値を比較することで、実際に効果があったかを判断できる。

#### ⑧ 5.4 まとめ

- パフォーマンス低下は、API・DB・外部サービスなど複数の原因で発生する。
- まずは遅延が発生している機能や時間帯を特定する。
- ログから処理ごとの所要時間を確認する。
- CPU・メモリ・DB接続数などのメトリクスも組み合わせる。
- 処理時間を比較してボトルネックを特定する。
- 改善後は数値を比較し、効果を確認する。

### 5.5 複合障害の調査

#### ① 複合障害とは？

複合障害とは、複数の問題が同時に発生したり、1つの障害が別の問題を引き起こしたりする状態のこと。

例えば、DBへの接続が遅くなったことでAPIの処理が遅延し、タイムアウトやエラーが増加するケースがある。

このような場合、1つのログだけを見ても根本原因を特定できないことがある。

そのため、複数のログやメトリクスを組み合わせて調査する必要がある。

#### ② 複合障害の調査：注文APIで障害が発生

あるネットショップで、注文APIのレスポンスが遅くなり、HTTP 500エラーも増加した。

障害発生時の情報は次のとおり。

**発生状況**

- 10:00頃から注文APIの遅延が発生
- 注文APIのレスポンスタイムが急増
- 一部の注文でHTTP 500が発生
- ユーザーから注文できないという問い合わせが増加

**APIログ**

```text
10:00:01 INFO  API /orders requestId=req-001 注文リクエスト受信
10:00:04 ERROR API /orders requestId=req-001 HTTP 500
10:00:05 INFO  API /orders requestId=req-002 注文リクエスト受信
10:00:09 ERROR API /orders requestId=req-002 HTTP 500
```

**アプリケーションログ**

```text
10:00:01 INFO  OrderService 注文処理開始
10:00:02 INFO  DB接続取得開始
10:00:04 ERROR DB connection timeout
10:00:04 ERROR OrderService 注文登録失敗
```

**DBメトリクス**

| 項目 | 通常時 | 障害発生時 |
|---|---:|---:|
| CPU使用率 | 30% | 85% |
| メモリ使用率 | 50% | 75% |
| DB接続数 | 20 | 100 |
| 最大接続数 | 100 | 100 |

**分散トレーシング**

| サービス | 処理時間 | 結果 |
|---|---:|---|
| API Gateway | 4000ms | HTTP 500 |
| Order Service | 3900ms | 失敗 |
| DB接続処理 | 3000ms | タイムアウト |

#### ③ 情報を整理する

各情報から分かることを整理する。

| 調査対象 | 分かったこと |
|---|---|
| APIログ | 注文APIでHTTP 500が発生 |
| アプリログ | DB接続時にタイムアウト |
| DBメトリクス | DB接続数が最大接続数に達している |
| 分散トレーシング | DB接続処理に時間がかかっている |

これらを組み合わせると、DB接続数が上限に達したことで、新しい接続を確保できなくなり、注文APIの遅延やエラーにつながった可能性が考えられる。

ただし、ここで分かったのは有力な原因候補である。

なぜDB接続数が増加したのかについては、さらに調査する必要がある。

例えば、次のような原因が考えられる。

- アクセス数が急増した
- DB接続が適切に解放されていない
- アプリケーションの接続プール設定に問題がある
- DB側の処理が遅くなり、接続が長時間使用されている

#### ④ 根本原因を特定する

根本原因を特定するために、追加で確認する情報を考える。

| 調査項目 | 確認する内容 |
|---|---|
| アクセスログ | リクエスト数が急増していないか |
| 接続プール | 接続が適切に解放されているか |
| DBログ | SQLの実行時間やロックが増えていないか |
| アプリログ | 接続取得・解放の処理に問題がないか |
| メトリクス | 接続数やCPU使用率がいつから増加したか |

例えば、アクセス数に大きな変化がないのにDB接続数だけが増加し続けている場合、接続が適切に解放されていない可能性がある。

このように、事実を集めながら仮説を検証することが重要。

#### ⑤ 障害対応と復旧確認

原因が特定できたら、サービスの復旧と再発防止を進める。

**初動対応**

- 障害の発生時刻と影響範囲を確認する
- 注文APIのエラー率やレスポンスタイムを確認する
- 必要に応じてアクセスを制限するなど、負荷を軽減する

**原因への対応**

- DB接続の解放漏れを修正する
- 接続プールの設定を見直す
- DBの負荷やSQLの実行状況を改善する

**復旧確認**

- DB接続数が正常な範囲に戻っているか
- 注文APIのレスポンスタイムが改善したか
- HTTP 500エラーが減少したか
- 注文データが正しく登録されているか

復旧したように見えても、データの整合性まで確認することが大切。

#### ⑥ 再発防止を考える

障害が復旧した後は、同じ問題が再発しないように改善する。

例えば、次のような対策が考えられる。

| 対策 | 目的 |
|---|---|
| DB接続数の監視 | 接続数の異常な増加を早期発見する |
| 接続プールの見直し | 接続不足や過剰な接続を防ぐ |
| ログの改善 | 接続取得・解放の状況を追跡しやすくする |
| アラート設定 | 接続数やエラー率の異常を通知する |
| 負荷テスト | 大量アクセス時の問題を事前に発見する |

障害対応は、サービスを復旧させて終わりではない。

原因を分析し、監視や設計を改善することで、次の障害を防ぐことが重要。

#### ⑦ 5.5 まとめ

- 複合障害では、複数のログやメトリクスを組み合わせて調査する。
- APIログ・アプリログ・DBログ・分散トレーシングを活用する。
- 事実と仮説を分け、追加調査によって根本原因を特定する。
- 復旧時にはAPIの応答だけでなく、DBやデータの整合性も確認する。
- 障害後は監視・ログ・設定・テストなどを改善し、再発防止につなげる。

### 5.6 ログ調査 応用編まとめ

#### ① 第1章：大規模システムのログ設計

大規模システムでは、多くのサービスから大量のログが出力される。

そのため、ログを効率よく検索・分析できるように設計することが重要。

**学習した内容**

- ログの出力形式やルールを統一する
- INFO・WARN・ERRORなどのログレベルを適切に使う
- 構造化ログによって検索や集計をしやすくする
- ログの保存期間やローテーションを管理する
- ログを継続的に監視し、改善する

**重要ポイント：**
ログは出力するだけでなく、後から調査・分析しやすい状態で管理することが重要。

#### ② 第2章：分散システム・マイクロサービスのログ調査

分散システムでは、1つの処理が複数のサービスをまたいで実行される。

そのため、サービスごとのログを関連付けて調査する必要がある。

**学習した内容**

- 分散システムとマイクロサービスの仕組み
- Trace IDによるログの追跡
- 分散トレーシングによる処理の可視化
- 複数サービスのログを時系列で確認する方法
- タイムアウトやリトライによる影響

**重要ポイント：**
Trace IDを使って、複数サービスにまたがる一連の処理を追跡することが重要。

#### ③ 第3章：パフォーマンス問題の調査

システムの処理速度が低下した場合、ログやメトリクスを組み合わせて原因を調査する。

**学習した内容**

- レスポンス遅延の調査
- スロークエリの確認
- CPU・メモリ使用率の確認
- DB接続数や外部APIの応答時間の確認
- ボトルネックの特定と改善

**重要ポイント：**
処理全体のどこに時間がかかっているのかを特定し、ボトルネックを改善することが重要。

#### ④ 第4章：本番障害対応とインシデント分析

本番環境で障害が発生した場合、原因調査だけでなく、ユーザーへの影響を抑えてサービスを復旧させることが重要。

**学習した内容**

- インシデントの考え方
- 障害発生時の初動対応
- 影響範囲の特定
- ログを使った原因分析
- 再発防止と事後分析

**重要ポイント：**
障害対応は、サービスの復旧だけで終わらず、原因分析と再発防止まで行うことが重要。

#### ⑤ 第5章：実践的な障害調査

これまで学んだ知識を組み合わせ、実際の障害を想定した調査を行った。

**学習した内容**

- APIエラーとDB障害の切り分け
- Trace IDを使った分散システムの調査
- パフォーマンス低下の原因分析
- 複数のログやメトリクスを使った総合調査
- 原因の特定から復旧・再発防止までの流れ

**重要ポイント：**
1つのログだけで判断せず、複数の情報を組み合わせて事実と仮説を整理し、根本原因を特定することが重要。

#### ⑥ ログ調査 応用編で身につけた考え方

応用編では、単にログを読むだけでなく、複雑なシステムで発生した問題を分析する方法を学んだ。

特に重要なのは、次の5つ。

| 項目 | 身につけた考え方 |
|---|---|
| ログ設計 | 調査しやすいログを設計・管理する |
| 分散システム | Trace IDで複数サービスを追跡する |
| 性能調査 | ログやメトリクスからボトルネックを特定する |
| 障害対応 | 影響を抑えながら復旧と原因分析を進める |
| 再発防止 | 原因を分析し、監視や設計を改善する |

#### ⑦ 障害調査の基本的な流れ

応用編で学んだ内容をまとめると、障害調査は次の流れで進められる。

1. **状況確認**
   - いつ、どこで、どのような問題が発生したか確認する

2. **情報収集**
   - アプリケーションログ、DBログ、アクセスログ、メトリクスを集める

3. **関連付け**
   - Request IDやTrace IDを使って処理の流れを追跡する

4. **原因分析**
   - ログを時系列で確認し、事実と仮説を整理する

5. **原因特定**
   - DB、API、外部サービス、サーバーなどから根本原因を特定する

6. **復旧対応**
   - 影響を抑えながら、システムを正常な状態に戻す

7. **再発防止**
   - ログ設計、監視、設定、処理方法などを改善する

#### ⑧ 基礎編と応用編の違い

| 比較項目 | 基礎編 | 応用編 |
|---|---|---|
| 主な目的 | ログの読み方を理解する | 複雑な障害の原因を分析する |
| 調査対象 | 個別のログやエラー | 複数サービス・DB・メトリクス |
| 調査方法 | ログから原因を探す | 情報を組み合わせて根本原因を特定する |
| 対応 | エラーの原因を確認する | 復旧・改善・再発防止まで考える |

#### ⑨ 応用編の最終まとめ

ログ調査では、ログを読む技術だけでなく、システム全体の動きを理解することが重要。

大規模システムや分散システムでは、複数のサービスが連携しているため、1つのログだけでは原因を特定できないことも多い。

そのため、ログ・メトリクス・分散トレーシングなどを組み合わせ、事実に基づいて調査する必要がある。

また、障害を復旧させるだけでなく、原因を分析して再発防止につなげることも重要。

**ログ調査の最終的な目的は、障害の原因を特定し、システムの安定稼働につなげることである。**
