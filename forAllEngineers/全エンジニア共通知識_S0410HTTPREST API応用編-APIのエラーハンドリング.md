### 5.1 APIでエラーが発生する原因

#### ① APIのエラーハンドリングとは？

エラーハンドリングとは、プログラムでエラーが発生したときに、適切に処理する仕組みのこと。

API通信では、リクエストが失敗したり、サーバーが正常に処理できなかったりすることがある。

そのような場合に、エラーの原因を把握し、適切に対応することが重要。

#### ② APIでエラーが発生する主な原因

APIでエラーが発生する原因は、大きく分けて4つある。

**1. クライアント側の問題**

クライアント（アプリやブラウザ）から送信したリクエストに問題がある場合。

例：
- 必須項目が入力されていない
- パラメータの形式が間違っている
- 存在しないURLにアクセスしている

**2. 認証・認可の問題**

APIを利用するための認証情報や、アクセス権限に問題がある場合。

例：
- ログインしていない
- トークンの有効期限が切れている
- 操作する権限がない

**3. サーバー側の問題**

サーバー内部でエラーが発生し、正常に処理できない場合。

例：
- プログラムの不具合
- データベースへの接続失敗
- サーバーへのアクセス集中

**4. ネットワーク・通信の問題**

クライアントとサーバーの間で、正常に通信できない場合。

例：
- インターネットに接続されていない
- 通信が途中で切断された
- サーバーからの応答が遅い

#### ③ エラーの原因を切り分ける

APIでエラーが発生した場合は、まず原因がどこにあるのかを確認することが大切。

原因によって、必要な対処方法が異なる。

例えば、リクエストの内容に問題がある場合は送信内容を修正し、通信環境に問題がある場合はネットワークの状態を確認する。

また、通信エラーの場合はHTTPステータスコードが返ってこないこともある。

そのため、ステータスコードだけでなく、通信自体が成功したかどうかも確認する必要がある。


### 5.2 エラーレスポンスの構造

#### ① エラーレスポンスとは？

エラーレスポンスとは、APIの処理に失敗したときに、サーバーから返されるレスポンスのこと。

APIでエラーが発生した場合、HTTPステータスコードだけでなく、エラーの内容を示す情報も返すことが多い。

エラーレスポンスを確認することで、何が原因で処理に失敗したのかを把握しやすくなる。

#### ② エラーレスポンスの主な構造

エラーレスポンスには、主に次のような情報が含まれる。

- status：HTTPステータスコード
- message：エラーの概要や説明
- code：エラーの種類を識別するコード
- details：具体的なエラーの詳細

例えば、次のようなJSON形式で返されることがある。

```json
{
  "status": 400,
  "code": "INVALID_PARAMETER",
  "message": "入力された値が正しくありません。",
  "details": {
    "field": "age",
    "reason": "年齢は数値で入力してください。"
  }
}
```

それぞれの意味：

- status：400 Bad Requestを表す
- code：エラーの種類を識別する
- message：エラーの概要を伝える
- details：どの項目に、どのような問題があるかを伝える

※ エラーレスポンスの項目名や構造は、APIの設計によって異なる。必ずしもすべての項目が含まれるわけではない。

#### ③ HTTPステータスコードとエラー情報の違い

HTTPステータスコードとエラー情報は、それぞれ役割が異なる。

**HTTPステータスコード**

リクエストが成功したのか、失敗したのかなど、大まかな結果を表す。

例：
- 400：リクエストの内容に問題がある
- 401：認証が必要、または認証情報が無効
- 404：指定されたリソースが見つからない
- 500：サーバー内部でエラーが発生した

**エラー情報**

エラーが発生した具体的な理由を伝える。

例えば、同じ400 Bad Requestでも、入力値が間違っているのか、必須項目が不足しているのかは、エラー情報を確認することで判断しやすくなる。

つまり、HTTPステータスコードでエラーの大まかな種類を把握し、エラー情報で具体的な原因を確認する。

#### ④ エラーレスポンスを設計するメリット

エラーレスポンスの形式を統一すると、次のようなメリットがある。

- エラーの原因を特定しやすくなる
- アプリ側でエラーごとの処理を分けやすくなる
- 開発者が問題を調査しやすくなる
- ユーザーに適切なエラーメッセージを表示できる

APIを設計するときは、正常時のレスポンスだけでなく、エラー時にどのような情報を返すかも考えることが大切。


### 5.3 バリデーションエラー

#### ① バリデーションとは？

バリデーションとは、入力されたデータが正しい形式や条件を満たしているかを確認すること。

APIでは、クライアントから送られてきたデータをサーバー側で検証する。

例えば、ユーザー登録APIの場合、次のような項目を確認する。

- 名前が入力されているか
- メールアドレスの形式が正しいか
- 年齢が数値になっているか
- パスワードが必要な文字数を満たしているか

入力内容に問題がある場合、バリデーションエラーが発生する。

#### ② バリデーションエラーが発生する例

例えば、ユーザー登録APIに次のようなデータを送信したとする。

```json
{
  "name": "",
  "email": "example",
  "age": "abc"
}
```

この場合、次のような問題がある。

- name：名前が入力されていない
- email：メールアドレスの形式が正しくない
- age：年齢に数値以外が入力されている

このように、入力データがAPIの求める条件を満たしていない場合、サーバーはエラーを返す。

#### ③ バリデーションエラーで使われるステータスコード

バリデーションエラーでは、主に次のステータスコードが使われる。

**400 Bad Request**

リクエストの内容に問題がある場合に使われる。

例えば、必須項目が不足していたり、パラメータの形式が正しくなかったりする場合。

**422 Unprocessable Content**

リクエストの形式自体は正しいものの、入力された内容が処理できない場合に使われる。

例えば、メールアドレスの形式が正しくない場合など。

※ どちらを使用するかはAPIの設計によって異なる。

#### ④ バリデーションエラーへの対応

バリデーションエラーが発生した場合は、エラーの内容を確認し、問題のある入力データを修正する。

例えば、次のような対応を行う。

- 必須項目が空の場合は入力を促す
- メールアドレスの形式が間違っている場合は修正を促す
- 数値が必要な項目に文字列が入力されている場合は、正しい形式で入力してもらう

また、アプリ側でも入力チェックを行うことで、送信前に入力ミスを防ぎやすくなる。

ただし、クライアント側のチェックだけでは不十分なため、サーバー側でも必ずバリデーションを行うことが重要。


### 5.4 認証・認可エラー

#### ① 認証・認可エラーとは？

認証・認可エラーとは、APIを利用するときに、本人確認やアクセス権限に問題がある場合に発生するエラーのこと。

認証と認可には、それぞれ異なる役割がある。

- 認証：利用者が誰なのかを確認すること
- 認可：利用者が特定の操作を行う権限を持っているか確認すること

例えば、ログインしていない場合は認証に問題があり、ログインしていても管理者専用の機能を利用する権限がなければ認可に問題がある。

#### ② 401 Unauthorized

401 Unauthorizedは、認証が必要なAPIに対して、適切な認証情報が提供されていない場合などに返されるステータスコード。

主な原因：

- ログインしていない
- アクセストークンが送信されていない
- アクセストークンの有効期限が切れている
- アクセストークンが無効になっている

例えば、ログインが必要なAPIに対して、トークンを付けずにリクエストを送信すると、401が返されることがある。

この場合は、再ログインして新しいトークンを取得するなどの対応を行う。

#### ③ 403 Forbidden

403 Forbiddenは、リクエストの内容を理解したものの、その操作を行う権限がない場合に返されるステータスコード。

主な原因：

- 管理者専用の機能を一般ユーザーが利用しようとした
- 特定のデータを閲覧する権限がない
- 操作を許可されていないユーザーが更新や削除を行おうとした

例えば、一般ユーザーが管理者専用のAPIにアクセスしようとすると、403が返されることがある。

この場合は、利用者に必要な権限が付与されていないため、基本的には権限がない操作を行うことはできない。

#### ④ 401と403の違い

401と403は、どちらもアクセスできない場合に使われるが、意味が異なる。

**401 Unauthorized**
- 認証に問題がある
- 誰がアクセスしているのか確認できない、または認証情報が無効

**403 Forbidden**
- 認証はできているが、操作する権限がない
- 利用者に許可されていない操作である

つまり、401は「認証の問題」、403は「権限の問題」と覚えると分かりやすい。

#### ⑤ 認証・認可エラーへの対応

認証・認可エラーが発生した場合は、原因に応じて対応する。

**401の場合**
- ログイン状態を確認する
- アクセストークンが正しく送信されているか確認する
- トークンの有効期限を確認する
- 必要に応じて再ログインする

**403の場合**
- 利用者に必要な権限があるか確認する
- 権限がない場合は、許可された操作を行う
- 必要に応じて管理者に権限の付与を依頼する

APIを利用するアプリでは、401と403を区別して処理することで、利用者に適切な案内を表示できる。


### 5.5 タイムアウトと通信エラー

#### ① タイムアウトとは？

タイムアウトとは、一定時間待っても処理や通信が完了しなかった場合に、処理を終了する仕組みのこと。

API通信では、サーバーからのレスポンスが一定時間以内に返ってこない場合に、タイムアウトが発生する。

主な原因：

- サーバーの処理に時間がかかっている
- サーバーにアクセスが集中している
- ネットワークの通信速度が遅い
- データベースの処理に時間がかかっている

例えば、アプリからAPIにリクエストを送信したものの、長時間レスポンスが返ってこない場合、タイムアウトとして処理されることがある。

#### ② 通信エラーとは？

通信エラーとは、クライアントとサーバーの間で正常に通信できなかった場合に発生するエラーのこと。

主な原因：

- インターネットに接続されていない
- Wi-Fiやモバイル通信が不安定
- DNSの名前解決に失敗している
- 通信途中で接続が切断された

通信エラーの場合、サーバーからHTTPレスポンスが返ってこないこともある。

そのため、HTTPステータスコードだけでは原因を判断できない場合がある。

#### ③ タイムアウトと通信エラーの違い

タイムアウトと通信エラーは、どちらもAPI通信に失敗する原因だが、意味が異なる。

**タイムアウト**
- 一定時間待っても処理が完了しない
- 待ち時間の上限を超えたことで発生する

**通信エラー**
- クライアントとサーバーの間で正常に通信できない
- ネットワークや接続そのものに問題がある

どちらも、必ずしもサーバー側の不具合とは限らない。

#### ④ タイムアウト・通信エラーへの対応

タイムアウトや通信エラーが発生した場合は、状況に応じて対応する。

主な対応方法：

- インターネット接続を確認する
- Wi-Fiやモバイル通信を切り替えてみる
- 一定時間待ってから再度リクエストを送信する
- タイムアウト時間を適切に設定する
- 必要に応じてリトライ処理を実装する

ただし、何度もリクエストを再送信すると、サーバーに負荷をかける可能性がある。

また、POSTなどのリクエストでは、サーバー側で処理が完了しているにもかかわらず、レスポンスだけが届かなかった可能性もある。

そのため、再送信する場合は、同じ処理が重複して実行されないように注意する必要がある。

#### ⑤ リトライ処理とは？

リトライ処理とは、通信に失敗した場合などに、一定の条件でリクエストを再送信する仕組みのこと。

例えば、通信が一時的に不安定になった場合、少し時間を置いてから再度リクエストを送信する。

リトライ処理では、次のような工夫が使われる。

- 再試行する回数に上限を設ける
- 再試行までの待ち時間を設ける
- 失敗するたびに待ち時間を長くする（指数バックオフ）
- 重複処理が起きないようにする

リトライ処理を適切に実装することで、一時的な通信障害から復旧しやすくなる。


### 5.6 エラーへの対処方法

#### ① エラーへの対処が必要な理由

API通信では、どれだけ正しく実装していても、通信環境やサーバーの状態などによってエラーが発生することがある。

そのため、エラーが発生することを前提に、適切な処理を実装しておく必要がある。

エラーへの対処を適切に行うことで、次のようなメリットがある。

- アプリが突然終了することを防げる
- ユーザーに分かりやすい案内を表示できる
- エラーの原因を調査しやすくなる
- 通信に失敗しても復旧しやすくなる

#### ② エラーの種類に応じた対処方法

APIで発生するエラーは、原因によって対処方法が異なる。

**1. 400 Bad Request**

リクエストの内容に問題がある場合。

対処方法：
- 入力内容を確認する
- パラメータやデータの形式を修正する
- 必須項目が入力されているか確認する

**2. 401 Unauthorized**

認証情報に問題がある場合。

対処方法：
- ログイン状態を確認する
- アクセストークンの有効期限を確認する
- 必要に応じて再ログインする

**3. 403 Forbidden**

操作する権限がない場合。

対処方法：
- 利用者の権限を確認する
- 許可されている操作を行う
- 必要に応じて管理者に権限の付与を依頼する

**4. 404 Not Found**

指定したリソースが見つからない場合。

対処方法：
- URLが正しいか確認する
- 指定したIDが存在するか確認する
- 対象のデータが削除されていないか確認する

**5. 500 Internal Server Error**

サーバー内部でエラーが発生した場合。

対処方法：
- 少し時間を置いてから再試行する
- サーバー側のログを確認する
- サーバーのプログラムや処理を調査する

**6. タイムアウト・通信エラー**

通信が正常に完了しなかった場合。

対処方法：
- インターネット接続を確認する
- 少し時間を置いてから再試行する
- 必要に応じてリトライ処理を行う

#### ③ try-catchによるエラー処理

プログラムでは、エラーが発生する可能性がある処理をtry-catchで囲むことで、エラーを捕捉して適切に処理できる。

例えば、Flutter（Dart）では次のように記述する。

```dart
try {
  final response = await api.getUsers();

  // API通信が成功した場合の処理
  print(response);
} catch (e) {
  // エラーが発生した場合の処理
  print('通信に失敗しました：$e');
}
```

それぞれの役割：

- try：エラーが発生する可能性がある処理を記述する
- catch：エラーが発生した場合の処理を記述する

try-catchを使うことで、エラーが発生してもアプリ全体が予期せず終了することを防ぎやすくなる。

#### ④ ユーザーに分かりやすいエラーメッセージを表示する

エラーが発生した場合、開発者向けの情報をそのまま表示するのではなく、ユーザーが理解しやすいメッセージを表示することが大切。

例えば、次のようなメッセージが考えられる。

- 通信エラー：「インターネット接続を確認してください。」
- 認証エラー：「ログインの有効期限が切れました。再度ログインしてください。」
- 入力エラー：「メールアドレスの形式を確認してください。」
- サーバーエラー：「現在サービスを利用できません。しばらくしてから再度お試しください。」

また、開発者向けには、エラーの詳細をログに記録しておくと、原因の調査に役立つ。

#### ⑤ エラーハンドリングで意識するポイント

APIのエラー処理を実装するときは、次のポイントを意識する。

- エラーの種類に応じて処理を分ける
- ユーザーに分かりやすいメッセージを表示する
- 必要に応じてリトライ処理を行う
- エラーの詳細をログに記録する
- 認証情報や個人情報などをログに不用意に出力しない
- 同じリクエストが重複して実行されないように注意する

エラーを適切に処理することで、予期しない状況でも安定して利用できるアプリを作ることができる。

### 5.7 第5章のまとめ

#### ① APIのエラーハンドリングとは？

エラーハンドリングとは、プログラムでエラーが発生したときに、適切に処理する仕組みのこと。

API通信では、リクエストの内容や認証情報、サーバーの状態、通信環境などによってエラーが発生する。

主なエラーの原因：

- クライアント側の問題：リクエストの内容やパラメータに問題がある
- 認証・認可の問題：認証情報やアクセス権限に問題がある
- サーバー側の問題：サーバー内部で処理に失敗する
- ネットワーク・通信の問題：クライアントとサーバー間で正常に通信できない

エラーが発生した場合は、原因を切り分けて適切に対応することが重要。

#### ② エラーレスポンスの構造

エラーレスポンスとは、APIの処理に失敗したときにサーバーから返されるレスポンスのこと。

主に次のような情報が含まれる。

- status：HTTPステータスコード
- code：エラーの種類を識別するコード
- message：エラーの概要や説明
- details：具体的なエラーの詳細

例：

```json
{
  "status": 400,
  "code": "INVALID_PARAMETER",
  "message": "入力された値が正しくありません。",
  "details": {
    "field": "age",
    "reason": "年齢は数値で入力してください。"
  }
}
```

HTTPステータスコードでエラーの大まかな種類を把握し、エラー情報で具体的な原因を確認する。

※ エラーレスポンスの項目名や構造はAPIの設計によって異なる。

#### ③ バリデーションエラー

バリデーションとは、入力されたデータが正しい形式や条件を満たしているか確認すること。

例えば、次のような項目を検証する。

- 必須項目が入力されているか
- メールアドレスの形式が正しいか
- 数値が必要な項目に文字列が入力されていないか
- パスワードが必要な文字数を満たしているか

バリデーションエラーで使われる主なステータスコード：

- 400 Bad Request：リクエストの内容に問題がある
- 422 Unprocessable Content：リクエストの形式は正しいが、内容を処理できない

※ どちらを使用するかはAPIの設計によって異なる。

クライアント側だけでなく、サーバー側でも必ずバリデーションを行うことが重要。

#### ④ 認証・認可エラー

認証・認可エラーとは、本人確認やアクセス権限に問題がある場合に発生するエラーのこと。

主なステータスコード：

**401 Unauthorized**

認証に問題がある場合に使われる。

例：
- ログインしていない
- アクセストークンが送信されていない
- アクセストークンの有効期限が切れている

**403 Forbidden**

認証はできているが、操作する権限がない場合に使われる。

例：
- 管理者専用のAPIに一般ユーザーがアクセスした
- 特定のデータを閲覧する権限がない

401は「認証の問題」、403は「権限の問題」と覚える。

#### ⑤ タイムアウトと通信エラー

**タイムアウト**

一定時間待っても処理や通信が完了しなかった場合に発生する。

主な原因：
- サーバーの処理に時間がかかっている
- サーバーにアクセスが集中している
- ネットワークの通信速度が遅い

**通信エラー**

クライアントとサーバーの間で正常に通信できなかった場合に発生する。

主な原因：
- インターネットに接続されていない
- Wi-Fiやモバイル通信が不安定
- 通信途中で接続が切断された

どちらもHTTPステータスコードが返ってこない場合がある。

また、リトライ処理とは、通信に失敗した場合などにリクエストを再送信する仕組みのこと。

リトライ処理では、再試行回数に上限を設けたり、待ち時間を長くしたりする工夫が重要。

#### ⑥ エラーへの対処方法

APIでエラーが発生した場合は、原因に応じて適切に対応する。

主な対処方法：

- 入力内容やリクエストの形式を確認する
- 認証情報やアクセス権限を確認する
- インターネット接続を確認する
- 必要に応じてリトライ処理を行う
- エラーの詳細をログに記録する
- ユーザーに分かりやすいメッセージを表示する

Flutter（Dart）では、try-catchを使ってエラーを捕捉できる。

```dart
try {
  final response = await api.getUsers();

  // API通信が成功した場合の処理
  print(response);
} catch (e) {
  // エラーが発生した場合の処理
  print('通信に失敗しました：$e');
}
```

- try：エラーが発生する可能性がある処理を記述する
- catch：エラーが発生した場合の処理を記述する

エラーの詳細をログに記録するときは、アクセストークンやパスワードなどの機密情報を不用意に出力しないように注意する。

---

#### 第5章の重要ポイント

APIのエラーハンドリングでは、次のポイントを意識する。

1. エラーの原因を切り分ける
2. HTTPステータスコードでエラーの大まかな種類を把握する
3. エラーレスポンスから具体的な原因を確認する
4. バリデーションはクライアント側とサーバー側の両方で行う
5. 401と403の違いを理解する
6. タイムアウトや通信エラーに備える
7. try-catchなどを使って適切にエラーを処理する
8. ユーザーに分かりやすいエラーメッセージを表示する

APIでは、正常に通信できる場合だけでなく、エラーが発生した場合の動作も考えて設計することが大切。
