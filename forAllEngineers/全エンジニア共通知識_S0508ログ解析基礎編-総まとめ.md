### 8.1 ログ調査の全体像

#### ① ログ調査とは？

ログ調査とは、アプリケーションやシステムに記録されたログを確認し、処理の状況やエラーの原因を特定すること。

システムで問題が発生した場合、ログを確認することで次のような情報を把握できる。

- いつ問題が発生したのか
- どの機能で問題が発生したのか
- どのような処理が行われていたのか
- どの段階でエラーが発生したのか
- エラーの原因は何か

ログ調査では、記録された情報をもとに事実を確認し、原因を一つずつ切り分けていくことが重要。

#### ② ログ調査の基本的な流れ

実務でログ調査を行う場合、次のような流れで進める。

1. **状況を確認する**
   - 発生した日時
   - 操作内容
   - 対象の機能
   - エラーメッセージ
   - 発生頻度や発生環境

2. **該当するログを探す**
   - 発生日時付近のログを確認する
   - ERRORやWARNなどのログを探す
   - 関連するサービスのログを確認する

3. **処理の流れを確認する**
   - エラーの直前に何が行われたか
   - エラー発生後にどのような処理が行われたか
   - ログを時系列で並べて確認する

4. **原因を切り分ける**
   - アプリケーションの問題か
   - APIの問題か
   - DBの問題か
   - ネットワークや外部サービスの問題か
   - データや設定の問題か

5. **根本原因を特定する**
   - 最初に発生したエラーを探す
   - 関連するログを組み合わせる
   - エラーの原因と影響を区別する

6. **修正して動作を確認する**
   - 原因に対する修正を行う
   - 正常系・異常系の動作を確認する
   - 関連する機能への影響も確認する

#### ③ システム全体の処理とログの関係

バックエンドでは、一つの操作でも複数の処理が連携していることがある。

例えば、ユーザー情報を取得する場合は次のような流れになる。

```text
ユーザーが画面を操作
        ↓
Flutterアプリ
        ↓
APIリクエスト
        ↓
バックエンド
        ↓
データベース
        ↓
バックエンド
        ↓
APIレスポンス
        ↓
Flutterアプリに表示
```

この処理の途中で問題が発生すると、複数の場所にログが出力される可能性がある。

例えば、DBへの接続に失敗した場合は、DB側のエラーログだけでなく、バックエンドやAPI側にもエラーが記録されることがある。

そのため、一つのログだけで判断せず、処理全体の流れを確認することが重要。

#### ④ ログ調査で使用する主な情報

ログ調査では、次の情報を組み合わせて原因を特定する。

| 情報 | 役割 |
|---|---|
| Timestamp | エラーが発生した日時を確認する |
| Log Level | ログの重要度を確認する |
| Logger / Source | どの機能やクラスで発生したか確認する |
| Message | 発生した処理やエラーの内容を確認する |
| Stack Trace | エラーが発生した処理の呼び出し経路を確認する |
| Request ID | 個々のリクエストに関連するログを探す |
| Trace ID | 複数のサービスにまたがる処理を追跡する |

特に、Request IDやTrace IDを利用すると、複数のサービスに分散したログを関連付けやすくなる。

#### ⑤ ログ調査で大切な考え方

ログ調査では、次のことを意識する。

- エラーメッセージだけで原因を決めつけない
- エラーの前後にあるログも確認する
- 時系列で処理の流れを追う
- 複数のログを組み合わせて確認する
- 根本原因と二次的なエラーを区別する
- 推測ではなく、ログなどの証拠をもとに判断する
- 調査結果や修正内容を記録する

ログは、システム内部で何が起きたのかを知るための重要な情報源。

ログを正しく読み取り、処理全体を把握することで、問題の早期発見や原因の特定につなげることができる。

### 8.2 実務で使うログ調査のチェックポイント

#### ① 調査を始める前に確認すること

ログ調査を始める前に、まずは問題が発生した状況を整理する。

確認する内容は次のとおり。

| 確認項目 | 確認する内容 |
|---|---|
| 発生日時 | いつ問題が発生したか |
| 操作内容 | どのような操作を行ったか |
| 対象機能 | どの画面や機能で発生したか |
| 発生頻度 | 毎回発生するか、特定の条件で発生するか |
| 発生環境 | 開発環境・テスト環境・本番環境のどこで発生したか |
| エラー内容 | どのようなエラーメッセージが表示されたか |

最初に状況を整理しておくことで、調査するログの範囲を絞り込みやすくなる。

#### ② ログを確認するときのチェックポイント

ログを確認するときは、次の項目を意識する。

- [ ] 発生日時付近のログを確認したか
- [ ] ERRORやWARNなどのログを確認したか
- [ ] エラーの直前・直後のログを確認したか
- [ ] ログの出力元（Logger / Source）を確認したか
- [ ] Stack Traceがある場合は確認したか
- [ ] Request IDやTrace IDで関連ログを検索したか
- [ ] ログを時系列で並べて確認したか

エラーログだけでなく、その前後の正常な処理ログも確認することが重要。

#### ③ API・DB・外部サービスの確認ポイント

バックエンドの処理では、API・DB・外部サービスなど、複数の要素が連携している。

それぞれの確認ポイントを整理する。

**APIの確認**

- [ ] HTTPメソッドやURLは正しいか
- [ ] リクエストの内容は正しいか
- [ ] HTTPステータスコードは何か
- [ ] レスポンスの内容は正しいか
- [ ] 処理時間が長くなっていないか

**DBの確認**

- [ ] DBに正常に接続できているか
- [ ] SQLの内容に問題はないか
- [ ] テーブル名やカラム名は正しいか
- [ ] 必要なデータが存在しているか
- [ ] SQLの実行時間が長くなっていないか
- [ ] トランザクションが正常に完了しているか

**外部サービスの確認**

- [ ] 接続先URLは正しいか
- [ ] リクエスト内容は正しいか
- [ ] 認証情報に問題はないか
- [ ] 外部サービスが正常に稼働しているか
- [ ] タイムアウトが発生していないか
- [ ] リトライ処理は正常に動作しているか

#### ④ 原因を切り分けるときのチェックポイント

ログを確認したら、次は原因を切り分ける。

例えば、APIで500エラーが発生した場合でも、原因はAPI以外にある可能性がある。

| 調査対象 | 主な確認内容 |
|---|---|
| アプリケーション | 入力値や画面側の処理に問題がないか |
| API | リクエストやバックエンドの処理に問題がないか |
| DB | 接続やSQLの実行に問題がないか |
| ネットワーク | 通信が正常に行われているか |
| 外部サービス | 連携先で障害が発生していないか |
| 設定・環境 | 環境変数や接続先などに問題がないか |

最初から原因を決めつけず、一つずつ確認していくことが重要。

#### ⑤ 修正後に確認すること

原因を特定して修正したら、正常に動作するか確認する。

- [ ] 発生していたエラーが解消されているか
- [ ] 正常な操作が問題なく実行できるか
- [ ] 異常な入力や通信失敗にも適切に対応できるか
- [ ] 関連する機能に影響が出ていないか
- [ ] 新しいエラーが発生していないか
- [ ] 必要なログが正しく出力されているか

修正した箇所だけでなく、関連する機能も確認することが重要。

#### ⑥ 実務で使うログ調査チェックリスト

実際の調査では、次のような流れで確認するとよい。

**調査開始**

- [ ] 発生日時・操作内容・対象機能を整理する
- [ ] 発生環境と発生頻度を確認する

**ログ確認**

- [ ] 該当するエラーログを探す
- [ ] エラーの前後のログを確認する
- [ ] Request IDやTrace IDで関連ログを集める
- [ ] 時系列で処理の流れを確認する

**原因特定**

- [ ] API・DB・外部サービスなどを切り分ける
- [ ] 最初に発生したエラーを確認する
- [ ] 根本原因を特定する

**修正・確認**

- [ ] 原因に対する修正を行う
- [ ] 正常系・異常系の動作を確認する
- [ ] 関連機能への影響を確認する
- [ ] 調査結果や修正内容を記録する

ログ調査では、決まった手順に沿って確認することで、調査漏れを防ぎやすくなる。

また、調査結果を記録しておくと、同じような障害が発生したときにも役立つ。

### 8.3 第8章まとめ

#### ① ログ調査の目的

ログ調査とは、アプリケーションやシステムに記録されたログを確認し、処理の状況やエラーの原因を特定すること。

ログ調査を行う主な目的は次のとおり。

- エラーが発生した原因を特定する
- システムが正常に動作しているか確認する
- 障害の発生状況や影響範囲を把握する
- 処理時間やパフォーマンスの問題を調査する
- セキュリティ上の問題を確認する

#### ② ログ調査で確認する情報

ログには、調査に必要なさまざまな情報が記録されている。

| 情報 | 確認する内容 |
|---|---|
| Timestamp | ログが出力された日時 |
| Log Level | ログの重要度 |
| Logger / Source | ログの出力元 |
| Message | 処理内容やエラーの内容 |
| Stack Trace | エラー発生までの呼び出し経路 |
| Request ID | 個々のリクエストを識別する情報 |
| Trace ID | 複数のサービスにまたがる処理を識別する情報 |

これらの情報を組み合わせることで、エラーが発生した場所や処理の流れを把握できる。

#### ③ ログ調査の基本的な手順

実務でログ調査を行う場合は、次の手順を意識する。

1. **状況を整理する**
   - 発生日時・操作内容・対象機能・発生環境などを確認する

2. **ログを検索する**
   - 発生日時付近のログやERRORログを確認する

3. **処理の流れを追う**
   - エラーの前後のログを時系列で確認する

4. **原因を切り分ける**
   - アプリケーション・API・DB・ネットワーク・外部サービスなどを確認する

5. **根本原因を特定する**
   - 複数のログを関連付け、最初に発生した問題を探す

6. **修正・動作確認を行う**
   - 修正後に正常系・異常系や関連機能への影響を確認する

#### ④ ログ調査で重要な考え方

ログ調査では、次のポイントが重要になる。

- エラーメッセージだけで原因を判断しない
- エラーの前後にあるログを確認する
- ログを時系列で並べて処理の流れを把握する
- Request IDやTrace IDを使って関連ログを集める
- 根本原因と二次的なエラーを区別する
- 推測ではなく、ログなどの証拠をもとに判断する
- 調査結果や修正内容を記録する

また、ログにはパスワードやアクセストークンなどの機密情報を出力しないように注意する。

#### ⑤ ログ調査で身につけた知識

| ログレベル | TRACE・DEBUG・INFO・WARN・ERROR・FATAL |
| ログ出力 | print()・developer.log()・出力タイミング |

| 実践的な調査 | 複数ログの関連付け・時系列での調査 |

#### ⑥ ログ調査のまとめ

ログ調査は、システムで発生した問題の原因を特定し、正常な状態に戻すために重要な作業。

実際の開発現場では、エラーの内容だけでなく、処理全体の流れを把握する必要がある。

そのためには、ログを正しく読み取り、複数の情報を組み合わせながら、原因を一つずつ切り分けることが大切。

ログ調査の知識は、障害対応だけでなく、システムの品質向上やパフォーマンス改善にも役立つ。
