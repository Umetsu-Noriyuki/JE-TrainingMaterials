### 4.1 REST APIの設計原則

#### ① REST APIとは？

REST（Representational State Transfer）とは、Web APIを設計するときに使われる設計思想のこと。

RESTの考え方に沿って設計されたAPIをREST APIと呼ぶ。

REST APIでは、データを「リソース」として扱い、HTTPメソッドを使って操作する。

例えば、ユーザー情報を扱うAPIなら、

- ユーザー一覧を取得する
- 特定のユーザー情報を取得する
- ユーザーを新しく登録する
- ユーザー情報を更新する
- ユーザーを削除する

といった操作を行う。

#### ② REST APIの主な設計原則

RESTには、いくつかの設計原則がある。

**1. クライアント・サーバー**

クライアントとサーバーの役割を分ける考え方。

- クライアント：画面表示やユーザー操作を担当する
- サーバー：データの管理や処理を担当する

例えば、Flutterアプリがクライアントで、APIサーバーがサーバーになる。

**2. ステートレス**

サーバーが、クライアントの過去のリクエスト状態を保持しない考え方。

各リクエストには、処理に必要な情報を含める必要がある。

例えば、認証が必要なAPIでは、リクエストごとに認証トークンを送信する。

**3. キャッシュ可能**

取得したデータを一時的に保存して、再利用できるようにする考え方。

キャッシュを利用することで、通信量やサーバーの負担を減らせる。

**4. 統一インターフェース**

APIの操作方法やデータの扱い方に、一貫したルールを設ける考え方。

例えば、リソースの取得にはGET、登録にはPOSTを使うなど、共通のルールで設計する。

**5. 階層化システム**

クライアントとサーバーの間に、複数のサーバーや中継システムを配置できる考え方。

クライアントは、通信先の内部構造を意識せずにAPIを利用できる。

#### ③ REST APIを設計するメリット

- APIの使い方が分かりやすくなる
- クライアントとサーバーを分けて開発しやすくなる
- 複数のアプリから同じAPIを利用しやすくなる
- 一貫したルールでAPIを管理できる


### 4.2 リソースとエンドポイント

#### ① リソースとは？

リソースとは、APIで操作する対象となるデータや情報のこと。

例えば、ユーザー管理のAPIなら、

- ユーザー
- 商品
- 注文
- 試合記録

などがリソースになる。

REST APIでは、これらのリソースをURLで表す。

#### ② エンドポイントとは？

エンドポイントとは、APIにアクセスするためのURL（またはURLの特定のパス）のこと。

例えば、ユーザー一覧を取得するAPIなら、

```http
GET /users
```

この場合、

- /users：ユーザーというリソースを表すエンドポイント
- GET：ユーザー一覧を取得する操作

という意味になる。

#### ③ リソースとHTTPメソッドの関係

REST APIでは、同じエンドポイントでもHTTPメソッドを変えることで、異なる操作ができる。

例えば、/usersというエンドポイントの場合、

| HTTPメソッド | 操作 |
|---|---|
| GET | ユーザー一覧を取得する |
| POST | 新しいユーザーを登録する |

特定のユーザーを操作する場合は、ユーザーIDを指定する。

| HTTPメソッド | エンドポイント | 操作 |
|---|---|---|
| GET | /users/1 | IDが1のユーザーを取得する |
| PUT | /users/1 | IDが1のユーザー情報を置き換える |
| PATCH | /users/1 | IDが1のユーザー情報を一部更新する |
| DELETE | /users/1 | IDが1のユーザーを削除する |

#### ④ リソースを意識したURL設計

REST APIでは、URLに操作内容を表す動詞を入れるのではなく、操作対象となるリソースを名詞で表すのが基本。

例えば、

- /getUsers より /users
- /createUser より /users
- /deleteUser/1 より /users/1

のように設計する。

操作内容はHTTPメソッドで表す。


### 4.3 URL設計のルール

#### ① リソースは名詞で表す

REST APIでは、URLに操作内容を表す動詞ではなく、操作対象となるリソースを名詞で表すのが基本。

例えば、

| 避けたいURL | 推奨されるURL |
|---|---|
| /getUsers | /users |
| /createUser | /users |
| /deleteUser/1 | /users/1 |

データの取得・登録・削除などの操作は、HTTPメソッドで表す。

#### ② リソース名は複数形にする

リソース名は、基本的に複数形で統一することが多い。

例えば、

- /user → /users
- /product → /products
- /match → /matches

複数形にすることで、そのリソースの集合を表現しやすくなる。

特定のデータを指定するときは、IDを続ける。

```http
GET /users
GET /users/5
```

- /users：ユーザー一覧
- /users/5：IDが5のユーザー

#### ③ URLは小文字で統一する

URLのパスは、小文字で統一するのがおすすめ。

例えば、

```http
/users
/userProfiles
/UserProfiles
```

このような表記が混在すると、URLのルールが分かりにくくなる。

そのため、次のように統一する。

```http
/users
/user-profiles
```

#### ④ 単語の区切りにはハイフンを使う

URL内で複数の単語を使う場合は、ハイフン（-）で区切る方法がよく使われる。

例えば、

```http
/user-profiles
/match-records
/training-menus
```

アンダースコア（_）や大文字・小文字を混在させず、ハイフンで統一すると読みやすくなる。

#### ⑤ 階層構造を意識する

関連するリソースは、URLの階層構造で表現できる。

例えば、ユーザーが登録した試合記録を取得する場合、

```http
GET /users/5/matches
```

これは、IDが5のユーザーに紐づく試合記録を取得するという意味。

さらに、特定の試合記録を取得する場合は、

```http
GET /users/5/matches/10
```

のように表せる。

ただし、階層を深くしすぎるとURLが複雑になるため、必要な範囲にとどめることが大切。

#### ⑥ URLに不要な情報を含めない

URLには、リソースを特定するために必要な情報を含める。

例えば、次のようなURLは避けたい。

```http
/getUserDataByUserId/5
```

代わりに、

```http
/users/5
```

とすれば、シンプルで分かりやすい。


### 4.4 クエリパラメータの活用

#### ① クエリパラメータとは？

クエリパラメータとは、URLに追加情報を付けて、取得するデータの条件などを指定する仕組みのこと。

URLの ? 以降に指定する。

例えば、ユーザー一覧を取得するときに、年齢を条件にしたい場合は、

```http
GET /users?age=20
```

この場合、

- /users：ユーザー一覧のリソース
- ?：ここからクエリパラメータが始まる
- age=20：年齢が20のユーザーを指定する条件

という意味になる。

#### ② 複数の条件を指定する

クエリパラメータは、& でつなげることで複数指定できる。

例えば、

```http
GET /users?age=20&gender=female
```

これは、

- age=20：年齢が20
- gender=female：性別がfemale

という2つの条件を指定している。

? は最初のパラメータの前に1回だけ付けて、2つ目以降は & でつなげる。

#### ③ よく使われるクエリパラメータ

APIでは、次のような用途でクエリパラメータがよく使われる。

| パラメータ | 用途 | 例 |
|---|---|---|
| page | ページ番号 | ?page=2 |
| limit | 取得件数 | ?limit=10 |
| sort | 並び替え | ?sort=name |
| keyword | キーワード検索 | ?keyword=taro |
| status | 状態による絞り込み | ?status=active |

例えば、

```http
GET /users?page=2&limit=10
```

この場合は、2ページ目のデータを10件取得するという意味になる。

#### ④ パスパラメータとの違い

URLで使うパラメータには、クエリパラメータのほかに、パスパラメータもある。

| 種類 | 役割 | 例 |
|---|---|---|
| パスパラメータ | 特定のリソースを指定する | /users/5 |
| クエリパラメータ | 検索・絞り込みなどの条件を指定する | /users?age=20 |

例えば、

```http
GET /users/5
```

これはIDが5のユーザーを取得する。

一方、

```http
GET /users?age=20
```

これは年齢が20のユーザーを検索する。

つまり、

- パスパラメータ：どのデータを対象にするか
- クエリパラメータ：どんな条件でデータを取得するか

という違い。


### 4.5 ページネーション

#### ① ページネーションとは？

ページネーションとは、大量のデータを複数のページに分割して取得する仕組みのこと。

例えば、ユーザーが1,000人登録されている場合、一度に1,000人分のデータを取得すると、通信量やサーバーへの負荷が大きくなる可能性がある。

そこで、データを分割して取得する。

例えば、

- 1ページ目：1〜10件目
- 2ページ目：11〜20件目
- 3ページ目：21〜30件目

というように分ける。

#### ② ページネーションの指定方法

ページネーションでは、クエリパラメータを使って取得するページや件数を指定することが多い。

代表的なパラメータは次の2つ。

| パラメータ | 意味 |
|---|---|
| page | 取得するページ番号 |
| limit | 1ページあたりの取得件数 |

例えば、

```http
GET /users?page=2&limit=10
```

この場合、

- page=2：2ページ目を取得する
- limit=10：1ページあたり10件取得する

という意味になる。

#### ③ ページネーションを使うメリット

ページネーションには、主に次のようなメリットがある。

**1. 通信量を減らせる**

一度に大量のデータを取得しないため、通信量を抑えられる。

**2. サーバーへの負荷を軽減できる**

一度に処理するデータ量が少なくなるため、サーバーの負荷を抑えられる。

**3. 画面の表示が速くなる**

最初に必要なデータだけ取得できるため、一覧画面を早く表示しやすくなる。

#### ④ ページネーションの種類

ページネーションには、代表的に2つの方式がある。

**① オフセット方式**

取得開始位置と件数を指定する方式。

例えば、

```http
GET /users?offset=10&limit=10
```

- offset=10：先頭から10件分を飛ばす
- limit=10：そこから10件取得する

つまり、11件目から20件目までを取得するイメージ。

**② カーソル方式**

直前に取得したデータの最後の位置を基準に、次のデータを取得する方式。

例えば、

```http
GET /users?cursor=abc123&limit=10
```

- cursor=abc123：次のデータを取得するための基準位置
- limit=10：10件取得する

カーソルの値はAPI側が発行することが多く、次のページを取得するときに利用する。

| 方式 | 特徴 |
|---|---|
| オフセット方式 | 件数や開始位置を指定する。仕組みが分かりやすい |
| カーソル方式 | 前回の取得位置を基準にする。大量データや更新が多いデータに向いている |

※カーソル方式は、データの追加・削除によるページずれを抑えやすいが、カーソルの設計によって動作は異なる。


### 4.6 フィルタリングとソート

#### ① フィルタリングとは？

フィルタリングとは、指定した条件に合うデータだけを取得すること。

例えば、ユーザー一覧の中から、年齢が20歳のユーザーだけを取得したい場合、

```http
GET /users?age=20
```

このように指定する。

ほかにも、次のような条件を指定できる。

| 条件 | URLの例 |
|---|---|
| 年齢が20歳 | /users?age=20 |
| 有効なユーザーのみ | /users?status=active |
| 名前がtaroのユーザー | /users?name=taro |

複数の条件を指定することもできる。

```http
GET /users?age=20&status=active
```

この場合は、年齢が20歳で、かつ有効なユーザーだけを取得するという意味になる。

#### ② ソートとは？

ソートとは、取得したデータを特定の順番に並び替えること。

例えば、ユーザー一覧を名前順に並び替えたい場合、

```http
GET /users?sort=name
```

このように指定する。

一般的には、次のような指定方法がある。

| パラメータ | 意味 |
|---|---|
| sort=name | 名前順 |
| sort=created_at | 登録日時順 |
| sort=age | 年齢順 |

ただし、昇順・降順の指定方法はAPIによって異なる。

#### ③ 昇順と降順

ソートには、主に2つの並び順がある。

**昇順（ASC）**

小さい値から大きい値へ並べる方法。

例えば、数字なら、

1 → 2 → 3 → 4 → 5

日付なら、古いものから新しいものへ並べる。

**降順（DESC）**

大きい値から小さい値へ並べる方法。

例えば、数字なら、

5 → 4 → 3 → 2 → 1

日付なら、新しいものから古いものへ並べる。

APIでは、例えば次のように指定することがある。

```http
GET /users?sort=age&order=asc
```

- sort=age：年齢を基準に並び替える
- order=asc：昇順にする

降順にしたい場合は、

```http
GET /users?sort=age&order=desc
```

と指定する。

※ sortやorderというパラメータ名・指定値はAPIの設計によって異なる。

#### ④ フィルタリングとソートを組み合わせる

フィルタリングとソートは、同時に利用することもできる。

例えば、

```http
GET /users?status=active&sort=created_at&order=desc
```

この場合、

1. status=active：有効なユーザーだけに絞り込む
2. sort=created_at：登録日時を基準にする
3. order=desc：新しい順に並び替える

という処理になる。

このように、クエリパラメータを組み合わせることで、必要なデータを効率よく取得できる。


### 4.7 APIバージョニング

#### ① APIバージョニングとは？

APIバージョニングとは、APIの仕様を変更するときに、バージョンを付けて管理する仕組みのこと。

APIは、一度公開したあとも機能追加や仕様変更が発生する。

例えば、最初はユーザーの名前だけを返していたAPIに、年齢やメールアドレスも追加したい場合がある。

変更前：

```json
{
  "id": 1,
  "name": "Taro"
}
```

変更後：

```json
{
  "id": 1,
  "name": "Taro",
  "age": 20,
  "email": "taro@example.com"
}
```

このような変更をするとき、既存のアプリが正常に動かなくなる可能性がある。

そこで、APIのバージョンを分けて管理する。

#### ② URLでバージョンを指定する方法

APIバージョニングの代表的な方法の1つが、URLにバージョンを含める方法。

例えば、

```http
GET /v1/users
GET /v2/users
```

- /v1/users：バージョン1のAPI
- /v2/users：バージョン2のAPI

このように分けることで、古い仕様を使っているアプリと、新しい仕様を使っているアプリを共存させられる。

#### ③ バージョニングが必要な理由

APIのバージョンを管理する主な理由は、次の3つ。

**1. 既存アプリへの影響を抑える**

APIの仕様を変更しても、古いバージョンを利用しているアプリは従来どおり動作できるようにする。

**2. 新しい機能を追加しやすくする**

新しいバージョンを用意することで、既存の仕様に影響を与えずに機能を追加できる。

**3. 段階的に移行できる**

利用者がすぐに新しいバージョンへ切り替えられなくても、一定期間は古いバージョンを提供できる。

#### ④ APIバージョニングの方法

URLにバージョンを含める方法以外にも、いくつかの方法がある。

| 方法 | 例 | 特徴 |
|---|---|---|
| URL方式 | /v1/users | URLでバージョンを確認できる |
| クエリパラメータ方式 | /users?version=1 | URLのクエリで指定する |
| ヘッダー方式 | API-Version: 1 | HTTPヘッダーで指定する |

一般的には、URLにバージョンを含める方式が分かりやすく、よく使われている。

#### ⑤ 後方互換性とは？

APIバージョニングと一緒に覚えておきたい言葉が、後方互換性（Backward Compatibility）。

後方互換性とは、新しい仕様に変更しても、古い仕様を利用しているアプリが引き続き動作できること。

例えば、APIのレスポンスに新しい項目を追加するだけなら、古いアプリへの影響は少ない場合がある。

一方で、既存の項目を削除したり、データ形式を変更したりすると、古いアプリが動かなくなる可能性がある。

そのため、APIを変更するときは、既存の利用者への影響を考えることが大切。


### 4.8 第4章のまとめ

#### ① REST APIの設計原則

RESTとは、Representational State Transferの略で、Web APIを設計するための考え方・制約のこと。

主な設計原則：

- クライアント・サーバー：役割を分離する
- ステートレス：リクエストごとに必要な情報を含める
- キャッシュ可能：レスポンスを再利用できるようにする
- 統一インターフェース：一貫したルールで操作する
- 階層化システム：中間サーバーなどを配置できる

REST APIでは、リソースをHTTPメソッドで操作する。

#### ② リソースとエンドポイント

**リソース**とは、APIで操作する対象となるデータや情報のこと。

**エンドポイント**とは、APIにアクセスするためのURL（またはURLの特定のパス）のこと。

例：

```http
GET /users
GET /users/1
POST /users
```

同じエンドポイントでも、HTTPメソッドを変えることで操作内容を変えられる。

#### ③ URL設計のルール

REST APIのURLを設計するときの基本ルール：

- リソースは名詞で表す
- リソース名は複数形にすることが多い
- URLは小文字で統一する
- 単語の区切りにはハイフンを使う
- 関連するリソースは階層構造で表す
- URLに不要な情報を含めない

例：

```http
GET /users/5/matches
```

#### ④ クエリパラメータの活用

クエリパラメータとは、URLに追加情報を付けて、取得するデータの条件などを指定する仕組み。

URLの ? 以降に指定する。

例：

```http
GET /users?age=20
GET /users?age=20&status=active
```

複数の条件は & でつなげる。

**パスパラメータとの違い**

- パスパラメータ：特定のリソースを指定する
- クエリパラメータ：検索・絞り込みなどの条件を指定する

#### ⑤ ページネーション

ページネーションとは、大量のデータを複数のページに分割して取得する仕組み。

主なパラメータ：

- page：取得するページ番号
- limit：1ページあたりの取得件数
- offset：取得開始位置
- cursor：次のデータを取得するための基準位置

代表的な方式：

- オフセット方式：取得開始位置と件数を指定する
- カーソル方式：前回の取得位置を基準に次のデータを取得する

ページネーションを使うメリット：

- 通信量を減らせる
- サーバーへの負荷を軽減できる
- 画面の表示を速くしやすい

#### ⑥ フィルタリングとソート

**フィルタリング**とは、指定した条件に合うデータだけを取得すること。

例：

```http
GET /users?status=active
```

**ソート**とは、取得したデータを特定の順番に並び替えること。

- ASC：昇順（小さい値から大きい値）
- DESC：降順（大きい値から小さい値）

例：

```http
GET /users?sort=created_at&order=desc
```

フィルタリングとソートは、同時に利用することもできる。

#### ⑦ APIバージョニング

APIバージョニングとは、APIの仕様を変更するときに、バージョンを付けて管理する仕組み。

例：

```http
GET /v1/users
GET /v2/users
```

バージョンを分けるメリット：

- 既存アプリへの影響を抑えられる
- 新しい機能を追加しやすい
- 段階的に新しいバージョンへ移行できる

**後方互換性（Backward Compatibility）**

新しい仕様に変更しても、古い仕様を利用しているアプリが引き続き動作できること。

APIを変更するときは、既存の利用者への影響を考えることが大切。

---

#### 第4章の重要ポイント

REST APIを設計するときは、次のポイントを意識する。

1. リソースをURLで表し、HTTPメソッドで操作内容を指定する
2. URLは名詞を使い、分かりやすく統一する
3. クエリパラメータで検索や絞り込みの条件を指定する
4. ページネーションで大量のデータを分割して取得する
5. フィルタリングとソートで必要なデータを取得する
6. APIバージョニングで仕様変更による影響を抑える

REST APIは、利用する側にも設計する側にも分かりやすく、一貫性のあるルールで設計することが大切。
