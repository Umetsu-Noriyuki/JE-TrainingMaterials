### 2.1 ログの種類

#### ① アプリケーションログ

アプリケーションログとは、アプリケーション内部で発生した処理やイベントを記録したログのこと。

例えば、次のような情報が記録される。

- ユーザーのログイン処理
- データの登録や更新
- API通信の成功・失敗
- アプリケーション内部で発生したエラー

アプリケーションの不具合や処理の問題を調査するときに利用する。

#### ② アクセスログ

アクセスログとは、WebサーバーやAPIなどに対するアクセス情報を記録したログのこと。

例えば、次のような情報が記録される。

- アクセスした日時
- リクエストされたURL
- HTTPメソッド（GET、POSTなど）
- HTTPステータスコード
- リクエスト元のIPアドレス

アクセスログを確認することで、どのようなリクエストが送信されたのか、APIがどのようなレスポンスを返したのかを調査できる。

#### ③ システムログ

システムログとは、OSやサーバーなどのシステム自体の動作状況を記録したログのこと。

例えば、次のような情報が記録される。

- サーバーの起動・停止
- メモリやCPUの異常
- ディスク容量の不足
- システムサービスのエラー

アプリケーションではなく、OSやサーバー側に問題が発生していないかを調査するときに利用する。

#### ④ データベースログ

データベースログとは、データベースで実行された処理や動作状況を記録したログのこと。

例えば、次のような情報が記録される。

- SQLの実行内容
- データベースへの接続・切断
- クエリの実行時間
- データベース接続エラー
- トランザクションの失敗

データベースへの接続失敗やSQLの実行エラー、処理速度の低下などを調査するときに利用する。

#### ⑤ セキュリティログ・監査ログ

セキュリティログや監査ログとは、認証や権限に関する操作、重要なデータへのアクセスや変更履歴などを記録したログのこと。

例えば、次のような情報が記録される。

- ログインの成功・失敗
- アカウント情報の変更
- 権限の変更
- 重要なデータへのアクセス
- 不正アクセスの試行

不審な操作や不正アクセスの調査、システムの安全性を確認するときに利用する。

#### ⑥ 主なログの種類の比較

| ログの種類 | 主な記録内容 | 主な利用目的 |
|---|---|---|
| アプリケーションログ | アプリ内部の処理やエラー | アプリの不具合調査 |
| アクセスログ | リクエストやアクセス情報 | 通信状況の確認 |
| システムログ | OSやサーバーの動作 | サーバー障害の調査 |
| データベースログ | SQLやDBの処理 | DB関連の問題調査 |
| セキュリティ・監査ログ | 認証や重要操作の履歴 | 不正アクセスや操作履歴の調査 |

#### ⑦ この節のポイント

ログは、記録する対象によって種類が異なる。

問題が発生したときは、調査したい内容に応じて適切なログを確認することが重要。

例えば、APIの通信状況を調べたい場合はアクセスログ、SQLの実行エラーを調べたい場合はデータベースログを確認するとよい。


### 2.2 ログレベルとは？

#### ① ログレベルの基本

ログレベルとは、ログに記録する情報の重要度や深刻度を分類するための仕組みのこと。

ログレベルを設定することで、大量のログの中から重要な情報やエラーを見つけやすくなる。

例えば、正常な処理の記録とシステム障害の記録を区別できる。

#### ② 主なログレベル

代表的なログレベルには、次のようなものがある。

| ログレベル | 意味 | 利用例 |
|---|---|---|
| TRACE | 非常に詳細な処理情報 | 関数内部の細かな処理 |
| DEBUG | デバッグ用の情報 | 変数の値や処理の途中経過 |
| INFO | 正常な処理やイベントの情報 | ログイン成功、データ取得成功 |
| WARN | 警告・注意が必要な状態 | リトライ発生、設定値の不足 |
| ERROR | エラーが発生した状態 | API通信失敗、DB接続失敗 |
| FATAL | システムの継続が困難な重大なエラー | サーバー起動失敗など |

※ ログレベルの種類や名称、重要度の扱いは、使用する言語やログ出力ライブラリによって異なる場合がある。

#### ③ ログレベルの重要度

一般的には、次の順番で重要度が高くなる。

TRACE → DEBUG → INFO → WARN → ERROR → FATAL

例えば、本番環境でログを確認する場合、DEBUGやTRACEのような詳細な情報よりも、WARNやERRORなどの問題につながる情報を優先して確認することが多い。

ただし、DEBUGログが本番環境で出力されることもあり、実際の設定によって異なる。

#### ④ ログレベルの出力例

例えば、次のようなログが出力されていたとする。

```text
2026-11-05 09:00:00 INFO  ユーザーのログインに成功しました
2026-11-05 09:00:01 DEBUG 取得したユーザーID: 123
2026-11-05 09:00:02 WARN  APIの応答が遅くなっています
2026-11-05 09:00:03 ERROR データベースへの接続に失敗しました
```

このログから、次のように判断できる。

- INFO：正常にログインできている
- DEBUG：処理中の詳細情報が記録されている
- WARN：APIの応答速度に注意が必要
- ERROR：データベースへの接続に失敗している

このように、ログレベルを見るだけでも、どのログを優先して調査すべきか判断しやすくなる。

#### ⑤ ログレベルを適切に使う理由

ログレベルを適切に設定することで、次のようなメリットがある。

- 重要なエラーを見つけやすくなる
- 大量のログから必要な情報を絞り込める
- 問題の深刻度を判断しやすくなる
- 開発時と本番環境で必要なログを使い分けられる

反対に、すべてのログをERRORとして出力すると、正常な処理と本当のエラーを区別できなくなる。

そのため、ログの内容に応じて適切なレベルを設定することが重要。

#### ⑥ この節のポイント

- ログレベルは、ログの重要度や深刻度を分類する仕組み
- INFOは正常な処理、WARNは警告、ERRORはエラーを表す
- ログレベルを適切に設定することで、重要な情報を見つけやすくなる
- ログレベルの種類や扱いは、使用する環境によって異なる場合がある


### 2.3 ログの構成要素

#### ① ログの基本的な構成

ログには、一般的に次のような情報が含まれている。

| 構成要素 | 内容 |
|---|---|
| 日時（Timestamp） | ログが出力された日時 |
| ログレベル | INFO、WARN、ERRORなどの重要度 |
| 発生元（Logger） | ログを出力したクラスや処理 |
| メッセージ | 発生したイベントや処理内容 |
| 詳細情報 | エラー内容や対象データなどの補足情報 |

これらを組み合わせることで、**いつ・どこで・何が起きたのか** を把握しやすくなる。

#### ② ログの具体例

例えば、次のようなログが出力されたとする。

```text
2026-11-05 13:30:15 ERROR BackupService
バックアップデータの取得に失敗しました。
原因: Connection timeout
```

このログを分解すると、次のようになる。

| 構成要素 | 値 |
|---|---|
| 日時 | 2026-11-05 13:30:15 |
| ログレベル | ERROR |
| 発生元 | BackupService |
| メッセージ | バックアップデータの取得に失敗しました |
| 詳細情報 | Connection timeout |

この場合、次のことが読み取れる。

- 13時30分15秒に発生した
- ERRORレベルの問題である
- BackupServiceという処理で発生した
- バックアップデータの取得に失敗した
- 接続タイムアウトが原因として記録されている

#### ③ 日時（Timestamp）が重要な理由

ログ調査では、発生日時がとても重要になる。

例えば、ユーザーから「13時30分ごろにデータを保存できなかった」と報告された場合、その時間帯のログを確認することで原因を絞り込める。

また、複数のログを日時順に並べることで、エラーが発生するまでの処理の流れも確認できる。

ただし、次のような点には注意が必要。

- サーバーとDBなどで時刻がずれている場合がある
- タイムゾーン（UTC・JSTなど）が異なる場合がある
- 秒単位やミリ秒単位で記録されることもある

複数のシステムを調査するときは、時刻の基準が統一されているか確認する。

#### ④ 発生元（Logger）を確認する

発生元は、どのクラスや処理がログを出力したのかを示す情報。

例えば、次のようなログがあったとする。

```text
ERROR BackupService バックアップデータの取得に失敗しました
ERROR PlayerService プレーヤー情報の取得に失敗しました
ERROR MatchService 試合情報の保存に失敗しました
```

発生元を見ることで、どの機能に問題があるのかを把握しやすくなる。

特に大きなシステムでは、ログの発生元を確認することで調査対象を絞り込める。

#### ⑤ ログの構成要素を組み合わせて調査する

ログ調査では、1つの情報だけで判断するのではなく、複数の情報を組み合わせて考えることが大切。

例えば、次のような流れで調査を進める。

1. 日時からエラーが発生したタイミングを確認する
2. ログレベルから重要度を確認する
3. 発生元から問題が起きた機能を確認する
4. メッセージから何が起きたのかを確認する
5. 詳細情報から原因を絞り込む

このような流れで調査すると、原因を見つけやすくなる。

#### ⑥ 2.3のポイントまとめ

- ログには日時・ログレベル・発生元・メッセージなどが含まれる
- 日時はエラー発生のタイミングや処理順序を確認するために重要
- 発生元を見ることで問題が起きた機能を絞り込める
- 詳細情報は原因を特定するための手がかりになる
- 複数の構成要素を組み合わせて調査することが大切


### 2.4 第2章まとめ

#### ① ログの種類

ログには、調査する対象によっていくつかの種類がある。

| ログの種類 | 主な内容 |
|---|---|
| アプリケーションログ | アプリ内部の処理やエラー |
| アクセスログ | URL、HTTPメソッド、ステータスコードなど |
| システムログ | OSやサーバーの起動・停止、リソース状況 |
| データベースログ | SQL、DB接続、クエリの実行状況 |
| セキュリティログ・監査ログ | ログイン、権限変更、不正アクセスなど |

**調査したい問題に応じて、確認するログの種類を選ぶことが重要。**

例えば、

- APIのアクセス状況を確認したい → アクセスログ
- アプリ内の処理でエラーが発生した → アプリケーションログ
- DB接続に失敗している → データベースログ
- 不正なログインがないか確認したい → セキュリティログ

#### ② ログレベル

ログレベルは、ログの重要度や深刻度を分類するためのもの。

| ログレベル | 意味 |
|---|---|
| TRACE | 非常に細かい処理情報 |
| DEBUG | デバッグ用の詳細情報 |
| INFO | 正常な処理やイベント |
| WARN | 警告・注意が必要な状態 |
| ERROR | エラーが発生した状態 |
| FATAL | システムの継続が困難な重大なエラー |

特に覚えておきたいのは次の3つ。

- INFO：正常に処理された
- WARN：注意が必要な状態
- ERROR：処理に失敗した

ログレベルを適切に設定することで、重要なログを見つけやすくなる。

#### ③ ログの構成要素

ログには、調査に役立つ複数の情報が含まれている。

| 構成要素 | 確認できること |
|---|---|
| 日時（Timestamp） | いつ発生したか |
| ログレベル | どの程度重要か |
| 発生元（Logger） | どこで発生したか |
| メッセージ | 何が起きたか |
| 詳細情報 | 原因を特定するための補足情報 |

これらを組み合わせることで、エラーの発生状況や原因を絞り込める。

#### ④ 第2章の重要ポイント

第2章で学んだ内容を整理すると、次のようになる。

1. ログには複数の種類があり、調査対象に応じて使い分ける
2. ログレベルによって、ログの重要度を判断できる
3. ログには日時・発生元・メッセージなどの情報が含まれる
4. 複数の情報を組み合わせることで、原因を特定しやすくなる

ログ調査では、ただエラーのメッセージを読むだけではなく、**どのログを確認するか、どの情報に注目するか** が重要になる。
