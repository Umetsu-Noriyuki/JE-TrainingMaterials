### 4.1 ログを読むときの基本

#### ① ログを読む目的

ログを読む目的は、システムで何が起きたのかを把握し、問題が発生した原因を特定すること。

ログには、処理の開始・終了、エラー、外部サービスとの通信など、さまざまな情報が記録されている。

ログを読むときは、単にエラーメッセージだけを見るのではなく、前後の処理や発生した状況も確認することが重要。

#### ② 最初に確認する項目

ログを確認するときは、次の項目に注目する。

| 項目 | 確認する内容 |
|---|---|
| 日時 | いつ発生したのか |
| ログレベル | INFO、WARN、ERRORなど、重要度はどの程度か |
| 出力元 | どのクラスやサービスで発生したのか |
| メッセージ | 何が起きたのか |
| 詳細情報 | エラー内容やスタックトレースなど |

これらを確認することで、問題が発生した場所や状況を把握しやすくなる。

#### ③ エラーメッセージだけで判断しない

エラーメッセージには、問題の直接的な内容が記録されている。

しかし、エラーが発生した原因は、その直前の処理にある場合も多い。

例えば、次のようなログがあったとする。

```text
10:00:00 INFO  UserService - ユーザー情報の取得を開始
10:00:01 INFO  ApiClient - APIリクエストを送信
10:00:05 ERROR ApiClient - API通信がタイムアウトしました
10:00:05 ERROR UserService - ユーザー情報の取得に失敗しました
```

この場合、UserServiceでエラーが発生したように見えるが、最初の問題はApiClientのAPI通信で発生している。

そのため、エラーの前後に出力されたログも確認する必要がある。

#### ④ ログを読むときの基本的な流れ

1. エラーが発生した日時を確認する
2. ログレベルを確認する
3. 出力元やメッセージを確認する
4. エラーの前後にあるログを確認する
5. 何が起きたのかを整理する

**ログ調査では、エラーの内容だけでなく、発生した状況や前後の処理を含めて確認することが重要。**


### 4.2 ログの時系列を確認する

#### ① 時系列でログを確認するとは？

時系列でログを確認するとは、ログに記録された日時をもとに、処理が発生した順番を追いかけること。

システムでは、複数の処理が連続して実行されるため、ログを時間順に並べることで、問題が発生するまでの流れを把握できる。

特に、エラーが発生した直前に何が行われていたのかを確認することが重要。

#### ② エラー発生前後のログを確認する

例えば、次のようなログが出力されていたとする。

```text
10:00:00 INFO  UserService - ユーザー情報の取得を開始
10:00:01 INFO  ApiClient - APIリクエストを送信
10:00:03 INFO  ApiClient - APIレスポンスを受信
10:00:04 INFO  UserService - ユーザー情報を取得
10:00:05 ERROR UserService - データの変換に失敗
```

この場合、API通信自体は成功している。

その後のデータ変換処理でエラーが発生していることが分かる。

このように、エラーの直前にあるログを確認することで、問題が発生した処理を絞り込める。

#### ③ エラー発生後のログも確認する

エラーが発生した後のログにも、重要な情報が残っている場合がある。

例えば、次のようなケース。

```text
10:00:00 INFO  BackupService - バックアップ開始
10:00:01 ERROR BackupService - データ取得に失敗
10:00:02 WARN  BackupService - 再試行を開始
10:00:04 INFO  BackupService - 再試行に成功
10:00:05 INFO  BackupService - バックアップ完了
```

最初のエラーだけを見ると、バックアップに失敗したように見える。

しかし、その後に再試行が成功し、最終的にはバックアップが完了している。

このように、エラー発生後のログを確認することで、問題が解消されたかどうかも判断できる。

#### ④ 時刻のズレに注意する

複数のサーバーやサービスのログを確認するときは、時刻のズレに注意する必要がある。

例えば、次のようなケース。

- サーバーA：10:00:05 にAPIリクエストを送信
- サーバーB：09:59:58 にAPIリクエストを受信

一見すると、受信時刻の方が送信時刻よりも早く見える。

これは、サーバー間で時刻の設定が異なっている可能性があるため。

ログ調査では、次の点を確認する。

- サーバー間で時刻が同期されているか
- タイムゾーンが統一されているか
- UTCとJST（日本標準時）が混在していないか

#### ⑤ 時系列で調査するときの基本的な流れ

1. エラーが発生した日時を特定する
2. エラー発生前のログを確認する
3. エラー発生時のログを確認する
4. エラー発生後のログを確認する
5. 処理の流れを整理し、原因を絞り込む

**時系列でログを確認することで、エラーが発生するまでの流れや、その後の処理状況を把握できる。**


### 4.3 エラーログの読み方

#### ① エラーログとは？

エラーログとは、アプリケーションやシステムでエラーが発生したときに、その内容や状況を記録したログのこと。

エラーログには、次のような情報が含まれる。

- エラーが発生した日時
- ログレベル
- エラーが発生したクラスや処理
- エラーメッセージ
- 例外の種類
- スタックトレース

これらの情報を確認することで、問題が発生した場所や原因を調査できる。

#### ② エラーメッセージを確認する

エラーメッセージには、発生した問題の概要が記録されている。

例えば、次のようなメッセージがある。

| エラーメッセージ | 考えられる問題 |
|---|---|
| Connection timeout | 通信が制限時間内に完了しなかった |
| Connection refused | 接続先のサーバーが接続を受け付けなかった |
| Null check operator used on a null value | nullの値を不適切に扱った |
| File not found | 指定したファイルが見つからなかった |
| Permission denied | 操作に必要な権限がない |

エラーメッセージから問題の種類を把握し、原因の候補を絞り込む。

ただし、メッセージだけで原因を断定せず、前後のログやコードも確認することが重要。

#### ③ 例外の種類を確認する

例外（Exception）とは、プログラムの実行中に発生する予期しない問題を表すもの。

例えば、Dartでは次のような例外がある。

| 例外 | 内容 |
|---|---|
| FormatException | データの形式が正しくない |
| TypeError | 型が一致しないなど、型に関する問題 |
| RangeError | 配列やリストなどの範囲外にアクセスした |
| SocketException | ネットワーク通信に関する問題 |

例外の種類を確認することで、どのような問題が発生したのかを把握しやすくなる。

#### ④ スタックトレースを確認する

スタックトレース（Stack Trace）とは、エラーが発生するまでの関数やメソッドの呼び出し経路を示す情報。

例えば、次のようなログがあったとする。

```text
FormatException: Invalid JSON
#0  UserService.parseUser (user_service.dart:25)
#1  UserService.fetchUser (user_service.dart:12)
#2  UserController.loadUser (user_controller.dart:40)
```

この場合、次のように読み取れる。

- `FormatException`：JSONの解析時に形式の問題が発生
- `user_service.dart:25`：エラーが発生した箇所
- `user_service.dart:12`：parseUserを呼び出した箇所
- `user_controller.dart:40`：fetchUserを呼び出した箇所

スタックトレースを確認すると、エラーが発生した場所だけでなく、そこに至るまでの処理も追跡できる。

#### ⑤ エラーログを調査するときの流れ

1. エラーメッセージを確認する
2. 例外の種類を確認する
3. スタックトレースから発生箇所を特定する
4. 前後のログを確認する
5. 関連するソースコードを確認する
6. 原因を整理する

**エラーログは、メッセージ・例外の種類・スタックトレースを組み合わせて確認することで、原因を特定しやすくなる。**


### 4.4 複数のログを関連付けて調査する

#### ① 複数のログを関連付けるとは？

バックエンドシステムでは、1つの処理が複数のサービスやシステムを経由して実行されることがある。

例えば、ユーザーが商品を注文する場合、次のような処理が行われる。

1. 注文サービスが注文を受け付ける
2. 在庫サービスに在庫を確認する
3. 決済サービスに支払いを依頼する
4. 注文サービスが注文を完了する

このような場合、各サービスがそれぞれログを出力するため、1つのログだけでは全体の処理状況を把握できないことがある。

そこで、複数のログを関連付けて確認することで、処理全体の流れや問題が発生した場所を調査する。

#### ② リクエストIDとは？

複数のログを関連付けるために利用される情報の1つが、リクエストID（Request ID）。

リクエストIDとは、1つのリクエストを識別するために付与される一意の識別子。

例えば、次のようなログがあるとする。

```text
10:00:00 INFO OrderService
requestId=abc123 注文を受け付けました

10:00:01 INFO InventoryService
requestId=abc123 在庫を確認しました

10:00:02 ERROR PaymentService
requestId=abc123 決済に失敗しました
```

すべてのログに `requestId=abc123` が記録されている。

このIDを使って検索すれば、同じリクエストに関係するログをまとめて確認できる。

#### ③ トレースIDとは？

トレースID（Trace ID）とは、1つの処理全体を追跡するために使用される識別子。

特に、複数のサービスを経由するようなシステムで利用される。

リクエストIDと似ているが、一般的には次のような使い分けがある。

| 項目 | 役割 |
|---|---|
| リクエストID | 個々のリクエストを識別する |
| トレースID | 複数のサービスをまたぐ処理全体を追跡する |
| スパンID | トレース内の個々の処理を識別する |

※ 実際のシステムでは、リクエストIDとトレースIDを同じような目的で使う場合もある。

#### ④ 複数のログを関連付ける例

例えば、注文処理で決済エラーが発生したとする。

```text
10:00:00 INFO OrderService
traceId=xyz789 注文を受け付けました

10:00:01 INFO InventoryService
traceId=xyz789 在庫確認に成功しました

10:00:02 INFO PaymentService
traceId=xyz789 決済処理を開始しました

10:00:05 ERROR PaymentService
traceId=xyz789 決済APIがタイムアウトしました

10:00:05 ERROR OrderService
traceId=xyz789 注文処理に失敗しました
```

この場合、トレースID `xyz789` でログを検索すると、同じ注文処理に関係するログを確認できる。

その結果、次のことが分かる。

- 注文の受付は成功している
- 在庫確認も成功している
- 決済処理でタイムアウトが発生している
- 決済エラーによって注文処理も失敗している

このように、複数のログを関連付けることで、問題が発生したサービスを特定しやすくなる。

#### ⑤ 複数のログを調査するときの流れ

1. エラーが発生したログを確認する
2. リクエストIDやトレースIDを確認する
3. 同じIDを持つログを検索する
4. 複数のサービスの処理順序を確認する
5. 最初に問題が発生した箇所を特定する

**複数のログを関連付けることで、1つのサービスだけでは分からない処理全体の流れや、問題の発生箇所を把握できる。**


### 4.5 ログ検索・絞り込みの方法

#### ① ログ検索・絞り込みとは？

ログ検索・絞り込みとは、大量のログの中から、調査に必要な情報だけを探し出すこと。

システムでは、日々大量のログが出力されるため、すべてのログを確認するのは効率が悪い。

そのため、日時・ログレベル・キーワード・リクエストIDなどを使って、必要なログを絞り込む。

#### ② キーワードで検索する

ログに含まれる特定の文字列を使って検索する方法。

例えば、次のようなキーワードで検索できる。

| キーワード | 調査できる内容 |
|---|---|
| ERROR | エラーが発生したログ |
| timeout | タイムアウトに関するログ |
| failed | 失敗した処理に関するログ |
| PaymentService | 決済サービスに関するログ |
| abc123 | 特定のリクエストに関するログ |

Linuxなどの環境では、`grep` コマンドを使ってログを検索できる。

```bash
grep "ERROR" app.log
```

このコマンドでは、`app.log` の中から `ERROR` を含む行だけを表示する。

#### ③ 日時で絞り込む

問題が発生した日時が分かっている場合は、その時間帯のログに絞り込むと調査しやすい。

例えば、10:00〜10:05のログを確認したい場合、日時を条件に検索する。

日時で絞り込むことで、関係のないログを減らし、問題が発生した前後の状況を確認できる。

#### ④ ログレベルで絞り込む

ログレベルを条件にして、必要なログだけを確認する方法。

| ログレベル | 調査の目的 |
|---|---|
| INFO | 通常の処理の流れを確認する |
| WARN | 警告や注意が必要な状況を確認する |
| ERROR | エラーや処理の失敗を確認する |
| DEBUG | 詳細な処理内容を確認する |

例えば、障害が発生した場合は、まずERRORのログを検索し、その前後のINFOやWARNも確認するとよい。

#### ⑤ 条件を組み合わせて検索する

複数の条件を組み合わせることで、さらに効率よくログを絞り込める。

例えば、次のような条件が考えられる。

- 特定の日時
- ERRORレベル
- PaymentService
- 特定のtraceId

Linuxの`grep`では、パイプ（`|`）を使って検索結果をさらに絞り込める。

```bash
grep "ERROR" app.log | grep "PaymentService"
```

この例では、まずERRORを含む行を抽出し、その結果からPaymentServiceを含む行だけを表示する。

#### ⑥ ログ検索を行うときの基本的な流れ

1. 調査したい問題を整理する
2. 発生日時や対象サービスを確認する
3. キーワードやログレベルで検索する
4. 必要に応じて条件を組み合わせる
5. 抽出したログの前後関係を確認する

**ログ検索では、調査対象に合わせて条件を設定し、必要なログだけを効率よく抽出することが重要。**


### 4.6 第4章まとめ

#### ① ログを読むときの基本

ログを読む目的は、システムで何が起きたのかを把握し、問題の原因を特定すること。

ログを確認するときは、次の項目に注目する。

| 項目 | 確認する内容 |
|---|---|
| 日時 | いつ発生したのか |
| ログレベル | 重要度はどの程度か |
| 出力元 | どのクラスやサービスで発生したのか |
| メッセージ | 何が起きたのか |
| 詳細情報 | エラー内容やスタックトレースなど |

エラーメッセージだけで判断せず、前後のログも確認することが重要。

#### ② ログの時系列を確認する

時系列でログを確認することで、処理が実行された順番や、問題が発生するまでの流れを把握できる。

調査するときは、次の順番で確認する。

1. エラー発生前のログ
2. エラー発生時のログ
3. エラー発生後のログ

エラー発生後に再試行が成功している場合などもあるため、最後まで確認する必要がある。

また、複数のサーバーのログを比較するときは、時刻やタイムゾーンのズレにも注意する。

#### ③ エラーログの読み方

エラーログを読むときは、次の情報を確認する。

| 項目 | 役割 |
|---|---|
| エラーメッセージ | 発生した問題の概要を把握する |
| 例外の種類 | どのような種類の問題かを把握する |
| スタックトレース | エラーが発生した場所や呼び出し経路を追跡する |

スタックトレースを確認すると、エラーが発生したソースコードのファイル名や行番号を特定できる場合がある。

#### ④ 複数のログを関連付けて調査する

複数のサービスが連携するシステムでは、1つの処理に関係するログをまとめて確認する必要がある。

そのために利用される識別子には、次のようなものがある。

| 識別子 | 役割 |
|---|---|
| リクエストID | 個々のリクエストを識別する |
| トレースID | 複数のサービスをまたぐ処理全体を追跡する |
| スパンID | トレース内の個々の処理を識別する |

同じIDを持つログを検索することで、処理全体の流れや問題が発生したサービスを特定しやすくなる。

#### ⑤ ログ検索・絞り込みの方法

大量のログから必要な情報を探すには、検索条件を設定して絞り込む。

主な検索条件は次のとおり。

- キーワード
- 日時
- ログレベル
- サービス名
- リクエストIDやトレースID

Linuxでは、`grep` コマンドを使ってログを検索できる。

```bash
# ERRORを含むログを検索
grep "ERROR" app.log

# PaymentServiceに関するログを検索
grep "PaymentService" app.log

# ERRORかつPaymentServiceのログを検索
grep "ERROR" app.log | grep "PaymentService"
```

パイプ（`|`）を使うと、前のコマンドの検索結果を次のコマンドに渡し、さらに条件を絞り込める。

#### ⑥ 第4章の重要ポイント

第4章で学んだ内容を整理すると、次のようになる。

1. ログを読むときは、日時・ログレベル・出力元・メッセージを確認する
2. 時系列で前後のログを確認し、処理の流れを把握する
3. エラーメッセージ・例外の種類・スタックトレースから原因を調査する
4. リクエストIDやトレースIDを使い、複数のログを関連付ける
5. grepなどのコマンドを使い、必要なログを効率よく検索する

**ログ調査では、1つのログだけで判断せず、複数の情報を組み合わせて処理全体の流れを追うことが重要。**
