### 5.1 エラーの原因を特定する流れ

#### ① エラーの原因特定とは？

エラーの原因特定とは、システムで発生した問題について、何が原因で発生したのかを調査すること。

エラーが発生した場合、単にエラーメッセージを確認するだけではなく、発生した状況や関連する処理を調べる必要がある。

例えば、ユーザー情報を取得できない場合、次のような原因が考えられる。

- APIサーバーとの通信に失敗している
- データベースへの接続に失敗している
- APIから返されたデータの形式が正しくない
- プログラムの処理に問題がある

#### ② 原因特定の基本的な流れ

エラーの原因を特定するときは、次のような順番で調査する。

1. **エラーの内容を確認する**
   - エラーメッセージや例外の種類を確認する
2. **発生した状況を確認する**
   - いつ、どの操作で発生したのかを確認する
3. **関連するログを確認する**
   - エラーの前後や関連サービスのログを調べる
4. **原因を切り分ける**
   - 通信・データ・プログラムなど、問題の範囲を絞る
5. **原因を特定する**
   - ログやソースコードなどから根本的な原因を判断する
6. **修正・確認する**
   - 原因を修正し、正常に動作するか確認する

#### ③ エラーの症状と根本原因の違い

エラーが発生したときに見えている現象と、本当の原因は異なる場合がある。

例えば、画面に「ユーザー情報を取得できませんでした」と表示されたとする。

| 項目 | 内容 |
|---|---|
| 症状 | ユーザー情報を取得できない |
| 直接的な原因 | API通信がタイムアウトした |
| 根本原因の候補 | APIサーバーの負荷増加やネットワーク障害など |

症状だけを修正しても、根本原因が解決していなければ、同じ問題が再発する可能性がある。

そのため、エラーが発生した理由を深掘りすることが重要。

#### ④ 原因を特定するときの注意点

- エラーメッセージだけで原因を決めつけない
- エラー発生前後のログを確認する
- 複数の原因を考慮する
- 推測だけで修正せず、ログやコードなどの根拠を確認する
- 修正後に同じ条件で動作確認する

**エラーの原因特定では、目に見える症状だけでなく、その問題を引き起こした根本原因を調査することが重要。**

### 5.2 エラーの再現方法

#### ① エラーの再現とは？

エラーの再現とは、実際に発生したエラーと同じ状況を作り、同じ問題が発生するか確認すること。

エラーを再現できると、問題が発生する条件や原因を調査しやすくなる。

例えば、アプリで特定の操作をしたときだけエラーが発生する場合、その操作をもう一度実行して同じエラーが発生するか確認する。

#### ② エラーが発生した状況を整理する

エラーを再現するためには、まず発生したときの状況を整理する必要がある。

確認する主な項目は次のとおり。

| 項目 | 確認する内容 |
|---|---|
| 操作内容 | どのような操作をしたか |
| 発生日時 | いつエラーが発生したか |
| 入力データ | どのような値を入力したか |
| 実行環境 | OSやアプリのバージョンなど |
| 発生頻度 | 毎回発生するのか、特定の条件だけか |

これらの情報を整理することで、エラーが発生する条件を絞り込める。

#### ③ 同じ条件でエラーを再現する

エラーが発生したときの条件をできるだけ同じにして、操作を再実行する。

例えば、ユーザー登録時にエラーが発生した場合、次のような条件を確認する。

- 同じ入力値を使用する
- 同じ操作手順を実行する
- 同じアプリのバージョンを使用する
- 同じ実行環境で確認する

同じ条件でエラーが再現すれば、原因を調査しやすくなる。

#### ④ エラーが再現しない場合

エラーは必ずしも毎回発生するとは限らない。

例えば、ネットワークの一時的な不具合や、サーバーの負荷状況によって発生する場合がある。

このような場合は、次の情報を確認する。

- エラーが発生した日時
- そのときのログ
- ネットワークの状態
- サーバーの負荷状況
- 同じ問題が発生した他のユーザーや環境

再現しない場合でも、ログや実行環境の情報から原因を調査できる。

#### ⑤ エラーを再現するときの注意点

- 本番環境で不用意に操作しない
- 必要に応じて開発環境やテスト環境を利用する
- 個人情報や本番データを適切に扱う
- 発生した操作や条件を記録する
- 再現できなかった場合も、その結果を記録する

**エラーを再現することで、問題が発生する条件を把握し、原因を特定しやすくなる。**


### 5.3 原因の切り分け

#### ① 原因の切り分けとは？

原因の切り分けとは、発生したエラーについて、考えられる原因を分類し、一つずつ確認して原因を絞り込んでいくこと。

エラーが発生したとき、最初から原因を一つに決めつけるのではなく、複数の可能性を考えて調査することが重要。

例えば、ユーザー情報を取得できない場合、次のような原因が考えられる。

- アプリ側の処理に問題がある
- APIとの通信に問題がある
- バックエンドの処理に問題がある
- データベースに問題がある
- 取得したデータの形式に問題がある

これらを一つずつ確認することで、問題が発生している場所を特定しやすくなる。

#### ② 原因を分類して確認する

エラーの原因は、主に次のような観点で切り分ける。

| 分類 | 確認する内容 |
|---|---|
| アプリ・画面 | 入力値や画面側の処理に問題がないか |
| API・バックエンド | APIの処理やサーバー側のロジックに問題がないか |
| データベース | DB接続やSQL、保存データに問題がないか |
| ネットワーク | 通信エラーやタイムアウトが発生していないか |
| 外部サービス | 外部APIや連携サービスに問題がないか |
| 環境・設定 | 環境変数や接続先などの設定に問題がないか |

例えば、APIからユーザー情報を取得できない場合は、次のような順番で確認できる。

1. アプリから正しいリクエストが送信されているか
2. APIから正常なレスポンスが返っているか
3. バックエンド側でエラーが発生していないか
4. データベースから正しくデータを取得できているか

このように、処理の流れに沿って確認すると原因を絞り込みやすい。

#### ③ 一度に複数の条件を変更しない

原因を調査するときは、一度に複数の設定や処理を変更しないことも重要。

例えば、APIのURLとリクエストデータを同時に変更してエラーが解消した場合、どちらが原因だったのか判断できなくなる。

そのため、次のように一つずつ確認する。

1. APIのURLが正しいか確認する
2. リクエストデータが正しいか確認する
3. 認証情報に問題がないか確認する

一つずつ確認することで、どの条件がエラーに影響しているのか判断しやすくなる。

#### ④ 推測ではなく証拠をもとに判断する

原因を切り分けるときは、思い込みや推測だけで判断せず、ログや実際のデータを確認する。

調査に利用できる情報には、次のようなものがある。

- エラーログ
- APIのレスポンスやHTTPステータスコード
- データベースの登録内容
- 通信時間や処理時間
- リクエストIDやトレースID

例えば、APIのレスポンスが500だった場合でも、それだけでAPIの実装が原因とは限らない。

バックエンドのログやDBの状態も確認し、どの処理で問題が発生したのかを調べる必要がある。

原因を特定するときは、確認できた事実を積み重ねて判断することが大切。

#### ⑤ 症状と根本原因を区別する

エラー調査では、表面に現れている症状と、実際の根本原因を区別する必要がある。

例えば、画面に「ユーザー情報を取得できませんでした」と表示された場合、これは症状であり、根本原因とは限らない。

実際には次のような原因が考えられる。

- DBへの接続に失敗していた
- SQLの条件が間違っていた
- APIのレスポンス形式が想定と異なっていた

画面に表示されたエラーメッセージだけを修正しても、根本原因が解決していなければ、同じ問題が再発する可能性がある。

そのため、エラーが発生した直接の原因だけでなく、なぜその問題が発生したのかまで調査することが重要。


### 5.4 データ・通信・処理の確認

#### ① データの確認

エラーが発生したときは、処理に使用しているデータが正しいか確認する。

データに問題があると、正常な処理ができずエラーにつながることがある。

確認するポイントは次のとおり。

- 必須項目に値が入っているか
- データ型が正しいか（文字列・数値・日付など）
- 値の形式が想定どおりか
- データが存在しているか
- DBに正しい値が保存されているか

例えば、ユーザーIDとして数値を想定しているのに、文字列が渡されている場合、型の不一致によってエラーが発生する可能性がある。

また、APIから取得したJSONの項目名や構造が、アプリ側の想定と異なる場合も注意が必要。

#### ② 通信の確認

APIなどの外部サービスと通信する処理では、通信そのものに問題がないか確認する。

主な確認ポイントは次のとおり。

- リクエスト先のURLが正しいか
- HTTPメソッドが正しいか（GET・POSTなど）
- リクエストヘッダーや送信データが正しいか
- レスポンスのHTTPステータスコードは何か
- タイムアウトや接続エラーが発生していないか

例えば、API通信で次のようなステータスコードが返ってきた場合、それぞれ確認すべき内容が異なる。

| ステータスコード | 確認する内容 |
|---|---|
| 400 Bad Request | リクエストの内容に問題がないか |
| 401 Unauthorized | 認証情報に問題がないか |
| 403 Forbidden | 操作する権限があるか |
| 404 Not Found | URLや対象データが存在するか |
| 500 Internal Server Error | サーバー側の処理でエラーが発生していないか |
| 503 Service Unavailable | サーバーが一時的に利用できない状態ではないか |

ステータスコードだけで原因を決めつけず、レスポンスの内容やサーバー側のログも確認することが重要。

#### ③ 処理の確認

データや通信に問題がない場合は、アプリやバックエンド内部の処理を確認する。

主な確認ポイントは次のとおり。

- 処理が想定した順番で実行されているか
- 条件分岐（if文など）が正しく動作しているか
- 変数に想定した値が入っているか
- DBへの登録・更新・削除が正しく行われているか
- 例外処理によってエラーが適切に処理されているか

例えば、ユーザー情報を取得する処理で、APIからデータを取得できているのに画面に表示されない場合、データ取得後の変換処理や画面への反映処理に問題がある可能性がある。

このように、通信が成功しているかだけでなく、その後の処理も確認する必要がある。

#### ④ データ・通信・処理を組み合わせて調査する

実際のエラー調査では、データ・通信・処理をそれぞれ独立して確認するだけでなく、処理全体の流れを意識することが重要。

例えば、ユーザー情報を画面に表示する場合、次のような流れになる。

1. アプリからAPIにリクエストを送信する
2. バックエンドがリクエストを受け取る
3. バックエンドがDBからユーザー情報を取得する
4. APIがレスポンスを返す
5. アプリがレスポンスを解析する
6. 取得した情報を画面に表示する

この流れのどこで問題が発生しているのかを確認する。

| 確認対象 | 調査例 |
|---|---|
| データ | リクエストやDBの値が正しいか |
| 通信 | APIとの送受信が成功しているか |
| 処理 | データ取得後の変換や画面表示が正しいか |

問題が発生した箇所を特定できれば、修正すべき範囲も絞り込める。

#### ⑤ 調査結果を記録する

原因調査を行ったら、確認した内容と結果を記録しておく。

例えば、次のように整理する。

| 調査項目 | 確認結果 |
|---|---|
| APIリクエスト | 正常に送信されている |
| APIレスポンス | HTTP 500が返っている |
| DB接続 | 正常 |
| バックエンド処理 | DB取得後のデータ変換で例外が発生 |

このように記録しておくと、原因を説明しやすくなり、修正後の確認や同じ問題が発生したときの調査にも役立つ。


### 5.5 修正後の動作確認

#### ① 修正後の動作確認とは？

修正後の動作確認とは、エラーの原因を修正した後に、問題が解消されているかを確認すること。

エラーが発生していた処理だけでなく、関連する機能にも問題が発生していないか確認することが重要。

例えば、ユーザー情報を取得できない問題を修正した場合、次の内容を確認する。

- ユーザー情報を正常に取得できるか
- 取得した情報が正しく画面に表示されるか
- データが正しく保存・更新されているか
- エラーが再発しないか

修正したコードが正常に動くことだけでなく、アプリ全体として期待どおりに動作することを確認する。

#### ② 修正した箇所を確認する

まずは、修正した箇所が正しく動作するか確認する。

例えば、APIのレスポンスを解析する処理を修正した場合は、次のような確認を行う。

- 正常なレスポンスを正しく解析できるか
- 必要なデータを取得できるか
- 想定した形式でデータを扱えるか
- 不正なデータを受け取った場合に適切に処理できるか

修正した箇所に対して、単に一度成功しただけで判断せず、複数の条件で確認することが大切。

#### ③ 正常系と異常系の両方を確認する

動作確認では、正常系と異常系の両方を確認する。

**正常系テスト**

正常な入力や条件で、期待どおりの処理が行われるか確認する。

例：
- 正しいユーザーIDを指定して情報を取得できる
- 正しいデータを登録できる
- APIから正常なレスポンスを受け取れる

**異常系テスト**

不正な入力や予期しない状況でも、適切にエラー処理できるか確認する。

例：
- 存在しないユーザーIDを指定する
- 必須項目が未入力の状態で送信する
- API通信がタイムアウトする
- 不正な形式のデータを受け取る

正常系だけでなく異常系も確認することで、修正によって別の問題が発生していないか確認できる。

#### ④ 回帰テストを行う

回帰テストとは、ある不具合を修正したことで、以前は正常に動作していた別の機能に問題が発生していないか確認するテストのこと。

例えば、ユーザー情報の取得処理を修正した場合、次のような関連機能も確認する。

- ユーザー情報の表示
- ユーザー情報の編集
- ユーザー情報の保存
- 他の画面からのユーザー情報の参照

一つの修正が、別の機能に影響する可能性があるため、関連する範囲を確認することが重要。

また、自動テストが用意されている場合は、修正後にテストを実行して既存機能への影響を確認する。

#### ⑤ 修正内容と確認結果を記録する

修正が完了したら、何を修正し、どのような確認を行ったのか記録しておく。

例えば、次のように整理する。

| 項目 | 内容 |
|---|---|
| 発生した問題 | ユーザー情報を取得できない |
| 原因 | APIレスポンスの解析処理に問題があった |
| 修正内容 | レスポンスのデータ変換処理を修正 |
| 確認内容 | 正常系・異常系のテストを実施 |
| 確認結果 | 正常に取得・表示できることを確認 |

調査結果や修正内容を記録しておくことで、後から同じ問題が発生した場合にも役立つ。


### 5.6 第5章まとめ

#### ① エラーの原因を特定する流れ

エラーが発生した場合は、表面上の症状だけで判断せず、原因を調査することが重要。

基本的な調査の流れは次のとおり。

1. エラーメッセージやログを確認する
2. エラーが発生した状況を確認する
3. 関連するログや処理を調査する
4. 考えられる原因を切り分ける
5. 根本原因を特定する
6. 修正して動作確認を行う

症状と根本原因は異なる場合があるため、なぜエラーが発生したのかまで調査する。

#### ② エラーの再現方法

エラーの再現とは、発生したときと同じ条件を用意して、同じ問題が発生するか確認すること。

再現に必要な情報には、次のようなものがある。

- 操作手順
- 入力データ
- 発生日時
- アプリやサーバーのバージョン
- 発生した環境
- 発生頻度

同じ条件で再現できれば、原因を特定しやすくなる。

再現できない場合も、ログや通信状況などを確認して調査を進める。

#### ③ 原因の切り分け

原因の切り分けとは、考えられる原因を分類し、一つずつ確認して問題の発生箇所を絞り込むこと。

主な確認対象は次のとおり。

- アプリ・画面
- API・バックエンド
- データベース
- ネットワーク
- 外部サービス
- 環境・設定

一度に複数の条件を変更せず、ログや実際のデータなどの証拠をもとに判断することが重要。

#### ④ データ・通信・処理の確認

エラーの原因を調査するときは、次の3つの観点から確認する。

| 確認対象 | 主な確認内容 |
|---|---|
| データ | 入力値、データ型、DBの保存内容 |
| 通信 | APIのURL、HTTPメソッド、レスポンス、タイムアウト |
| 処理 | 条件分岐、データ変換、例外処理、画面への反映 |

例えば、APIからデータを取得できていても、その後のデータ変換や画面表示の処理に問題がある可能性がある。

処理全体の流れを意識し、どこで問題が発生しているのか確認する。

#### ⑤ 修正後の動作確認

エラーを修正した後は、問題が解消されたことだけでなく、関連機能に影響がないことも確認する。

確認する内容は次のとおり。

- 修正箇所が正常に動作するか
- 正常系のテストが通るか
- 異常系でも適切にエラー処理できるか
- 関連機能に影響がないか
- 既存の自動テストが通るか

特に、修正によって別の機能に不具合が発生していないか確認するテストを **回帰テスト（Regression Test）** という。

#### ⑥ 第5章で覚えておきたいこと

エラー調査では、次の流れを意識する。

**再現 → 調査 → 切り分け → 原因特定 → 修正 → 動作確認**

重要なのは、エラーの症状だけを直すのではなく、根本原因を特定して解決すること。

また、修正後は正常系・異常系・関連機能への影響まで確認することで、同じ問題の再発や新たな不具合を防ぎやすくなる。
