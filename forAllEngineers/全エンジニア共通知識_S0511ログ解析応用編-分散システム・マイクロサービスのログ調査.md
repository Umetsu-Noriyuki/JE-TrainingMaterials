### 2.1 分散システムとは？

#### ① 分散システムとは？

分散システムとは、複数のコンピューターやサーバーがネットワークを通じて連携し、1つのシステムとして動作する仕組みのこと。

1台のサーバーだけですべての処理を行うのではなく、複数のサーバーに処理を分担させる。

#### ② 分散システムの具体例

例えば、ネットショッピングのシステムを考える。

- Webサーバー：ユーザーからのリクエストを受け付ける
- 注文サーバー：注文情報を処理する
- 決済サーバー：支払いを処理する
- 在庫サーバー：商品の在庫を管理する

これらのサーバーが連携することで、注文から決済、在庫更新までの処理を実現する。

#### ③ 分散システムのメリット

- **負荷分散**：処理を複数のサーバーに分散できる
- **拡張性**：必要な部分だけサーバーを増やせる
- **障害への対応**：構成によっては、一部のサーバーに障害が発生しても他の機能を動かし続けられる
- **保守性**：機能ごとに管理しやすくなる

#### ④ 分散システムのログ調査で難しいこと

分散システムでは、1つの処理が複数のサーバーを通過する。

そのため、障害が発生した場合、どのサーバーで問題が発生したのか判断しにくい。

例えば、注文処理が失敗した場合でも、原因は注文サーバーではなく、決済サーバーや在庫サーバーにある可能性がある。

また、各サーバーが別々にログを出力するため、ログを横断して確認する必要がある。

#### ⑤ まとめ

分散システムでは、複数のサーバーが連携して1つの処理を実現する。

そのため、障害調査では個々のサーバーだけでなく、システム全体の処理の流れを把握することが重要。

### 2.2 マイクロサービスとは？

#### ① マイクロサービスとは？

マイクロサービスとは、システムを小さな独立したサービスに分割し、それぞれが特定の役割を担当する設計方式のこと。

各サービスは独立して開発・デプロイ・運用でき、APIなどを通じて連携する。

#### ② マイクロサービスの具体例

例えば、ネットショッピングのシステムを考える。

| サービス | 主な役割 |
|---|---|
| ユーザーサービス | ユーザー情報の管理 |
| 商品サービス | 商品情報の管理 |
| 注文サービス | 注文処理 |
| 決済サービス | 支払い処理 |
| 在庫サービス | 在庫数の管理 |

それぞれのサービスが役割を分担し、連携することで1つのシステムを実現する。

#### ③ マイクロサービスのメリット

- **独立性**：サービスごとに開発や修正ができる
- **拡張性**：負荷が高いサービスだけを増やせる
- **保守性**：機能ごとに管理しやすい
- **技術選択の自由度**：サービスごとに異なる技術を採用できる場合がある

#### ④ マイクロサービスのログ調査で注意すること

マイクロサービスでは、サービスごとにログが出力される。

そのため、1つの処理を調査するときは、複数のサービスのログを確認する必要がある。

例えば、注文処理が失敗した場合は次のような流れを確認する。

1. 注文サービスで注文を受け付けたか
2. 在庫サービスで在庫を確認できたか
3. 決済サービスで支払いが成功したか
4. 注文サービスに結果が正しく返ってきたか

サービスごとのログを時系列で確認することで、どこで問題が発生したのかを特定しやすくなる。

#### ⑤ 分散システムとの関係

分散システムは、複数のコンピューターやサーバーが連携して動く仕組みのこと。

マイクロサービスは、システムを小さな独立したサービスに分割する設計方式のこと。

マイクロサービスは、分散システムを実現する代表的なアーキテクチャの1つ。

#### ⑥ まとめ

マイクロサービスでは、機能ごとに独立したサービスが連携して処理を行う。

ログ調査では、個々のサービスだけでなく、サービス間の連携や処理の流れを追跡することが重要。

### 2.3 分散トレーシングとは？

#### ① 分散トレーシングとは？

分散トレーシングとは、複数のサービスにまたがる1つの処理について、どのサービスを通過し、どのように処理されたのかを追跡する仕組みのこと。

分散システムでは、1つのリクエストが複数のサービスを経由する。

そのため、各サービスのログを個別に確認するだけでは、処理全体の流れを把握しにくい。

分散トレーシングを利用すると、リクエスト単位で処理の流れを追跡できる。

#### ② 分散トレーシングの具体例

例えば、ネットショッピングで注文を行った場合、次のような処理が発生するとする。

1. Webサービスが注文リクエストを受け取る
2. 注文サービスが注文情報を登録する
3. 在庫サービスが在庫を確認する
4. 決済サービスが支払いを処理する
5. 注文サービスに結果を返す

分散トレーシングでは、これらの処理を一連の流れとして追跡できる。

#### ③ Trace IDとSpan ID

分散トレーシングでは、処理を追跡するためにIDを使用する。

| ID | 意味 |
|---|---|
| Trace ID | 一連の処理全体を識別するID |
| Span ID | 一連の処理を構成する個々の処理を識別するID |

例えば、注文処理全体に同じTrace IDを付与する。

その中で、注文サービスや決済サービスなどの個々の処理には、それぞれ異なるSpan IDを付与する。

これにより、処理全体と個々の処理を区別して追跡できる。

#### ④ 分散トレーシングのメリット

- 複数サービスにまたがる処理を追跡できる
- どのサービスでエラーが発生したか確認しやすい
- サービス間の処理時間を比較できる
- レスポンスが遅くなっている箇所を特定しやすい

#### ⑤ ログ調査との関係

分散トレーシングは、ログ調査と組み合わせることで効果を発揮する。

例えば、Trace IDを使って関連するログを検索すれば、複数のサービスに分散したログをまとめて確認できる。

また、トレース情報から遅い処理を見つけ、その処理に対応するログを確認することで、原因を詳しく調査できる。

#### ⑥ まとめ

分散トレーシングは、複数のサービスにまたがる処理の流れを追跡する仕組み。

Trace IDで処理全体を識別し、Span IDで個々の処理を識別する。

これらを利用することで、分散システムの障害調査やパフォーマンス分析がしやすくなる。

### 2.4 Trace IDによるログの追跡

#### ① Trace IDとは？

Trace IDとは、複数のサービスにまたがる一連の処理を識別するためのID。

例えば、ユーザーが注文を行ったとき、注文サービス・在庫サービス・決済サービスが連携して処理を行う。

この一連の処理に同じTrace IDを付与することで、各サービスのログを関連付けられる。

#### ② Trace IDを使ったログの例

例えば、次のようなログが出力されたとする。

```text
[OrderService] TraceID=abc123 注文を受け付けました
[InventoryService] TraceID=abc123 在庫を確認しました
[PaymentService] TraceID=abc123 決済処理を開始しました
[PaymentService] TraceID=abc123 決済に失敗しました
```

すべてのログに同じTrace IDが含まれている。

そのため、Trace IDが `abc123` のログを検索すれば、注文から決済失敗までの処理を追跡できる。

#### ③ Trace IDを使った調査手順

障害が発生した場合、次のような手順で調査する。

1. エラーが発生したログを確認する
2. エラーログに含まれるTrace IDを取得する
3. Trace IDを使って関連するログを検索する
4. 各サービスの処理を時系列で確認する
5. どのサービスで問題が発生したか特定する

このように、Trace IDを利用すると、複数サービスのログを横断して調査できる。

#### ④ Trace IDを使うときの注意点

Trace IDを使って正確に追跡するには、各サービスで適切に引き継ぐ必要がある。

例えば、注文サービスから決済サービスへリクエストを送るとき、Trace IDも一緒に引き継ぐ。

もし途中でTrace IDが引き継がれなければ、関連するログを検索できなくなる可能性がある。

また、Trace IDだけでは原因の詳細までは分からない。

エラー内容や処理時間などのログも合わせて確認することが重要。

#### ⑤ まとめ

Trace IDを利用すると、複数サービスに分散したログを関連付けて検索できる。

障害発生時には、Trace IDを手掛かりに処理全体の流れを追跡し、問題が発生した箇所を特定する。

### 2.5 複数サービスにまたがる障害調査

#### ① 複数サービスのログを調査する理由

マイクロサービスでは、1つの処理が複数のサービスを経由する。

そのため、あるサービスでエラーが発生していても、原因が別のサービスにある可能性がある。

例えば、注文処理が失敗した場合、次のような原因が考えられる。

- 注文サービスで注文登録に失敗した
- 在庫サービスとの通信に失敗した
- 決済サービスで決済処理に失敗した
- サービス間の通信がタイムアウトした

障害の原因を特定するには、関連するサービスのログを横断して確認する必要がある。

#### ② 障害調査の具体例

ネットショッピングで注文処理が失敗したケースを考える。

次のログが出力されていたとする。

```text
[OrderService] TraceID=abc123 注文を受け付けました
[InventoryService] TraceID=abc123 在庫確認に成功しました
[PaymentService] TraceID=abc123 決済処理を開始しました
[PaymentService] TraceID=abc123 ERROR 決済APIがタイムアウトしました
[OrderService] TraceID=abc123 注文処理に失敗しました
```

このログから、次のことが分かる。

1. 注文サービスで注文を受け付けている
2. 在庫サービスで在庫確認に成功している
3. 決済サービスで決済処理を開始している
4. 決済APIのタイムアウトが発生している
5. 注文サービスに失敗結果が返されている

この場合、決済サービスや決済APIとの通信に問題がある可能性が高い。

#### ③ 障害調査の基本的な手順

複数サービスにまたがる障害では、次の手順で調査する。

1. **障害の発生状況を確認する**
   - いつ発生したのか
   - どの機能で発生したのか
   - どのユーザーやリクエストに影響したのか

2. **Trace IDを取得する**
   - エラーログからTrace IDを確認する

3. **関連ログを検索する**
   - Trace IDを使って複数サービスのログを検索する

4. **処理の流れを時系列で確認する**
   - どのサービスまで正常に処理されたか
   - 最初に異常が発生した箇所はどこか

5. **原因を特定する**
   - アプリケーションのエラーか
   - DBのエラーか
   - 外部APIとの通信エラーか
   - サービス間のタイムアウトか

6. **影響範囲と復旧状況を確認する**
   - 影響を受けた処理やユーザー
   - エラーが継続しているか
   - 必要な復旧対応が完了したか

#### ④ ログ調査で注意すること

複数サービスのログを調査するときは、次の点に注意する。

- Trace IDが正しく引き継がれているか
- 各サービスのログの時刻を確認する
- 最初に異常が発生した箇所を探す
- エラーが発生したサービスだけで原因を決めつけない
- タイムアウトなど、サービス間の通信状況も確認する

なお、複数サーバーの時刻がずれていると、ログの順番を正しく判断できないことがある。

そのため、サーバー間の時刻を同期することも重要。

#### ⑤ まとめ

複数サービスにまたがる障害では、Trace IDを使って関連ログを集め、処理の流れを時系列で確認する。

エラーが発生したサービスだけでなく、その前後のサービスの動きも確認することで、根本原因を特定しやすくなる。

### 2.6 第2章まとめ

#### ① 分散システムとは？

複数のコンピューターやサーバーが連携し、1つのシステムとして動作する仕組み。

複数のサーバーに処理を分散できる一方、障害調査ではシステム全体の処理の流れを把握する必要がある。

#### ② マイクロサービスとは？

システムを小さな独立したサービスに分割し、それぞれが特定の役割を担当する設計方式。

各サービスはAPIなどを通じて連携するため、障害調査では複数サービスのログを確認する必要がある。

#### ③ 分散トレーシングとは？

複数サービスにまたがる一連の処理を追跡する仕組み。

Trace IDやSpan IDを利用することで、処理全体や個々の処理を把握できる。

#### ④ Trace IDによるログの追跡

Trace IDは、一連の処理全体を識別するためのID。

各サービスで同じTrace IDを引き継ぐことで、複数サービスのログを関連付けて検索できる。

#### ⑤ 複数サービスにまたがる障害調査

障害調査では、次の手順が重要。

1. 障害の発生状況を確認する
2. エラーログからTrace IDを取得する
3. Trace IDを使って関連ログを検索する
4. 処理の流れを時系列で確認する
5. 最初に異常が発生した箇所を特定する
6. 影響範囲や復旧状況を確認する

#### ⑥ 第2章の重要ポイント

分散システムやマイクロサービスでは、1つの処理が複数のサービスにまたがる。

そのため、障害が発生した場合は、Trace IDを利用して関連ログを集め、処理全体の流れを追跡することが重要。

エラーが発生したサービスだけでなく、その前後のサービスや通信状況も確認することで、根本原因を特定しやすくなる。
