### 6.1 HTTPSとは

#### ① HTTPSとは？

HTTPSとは、HTTPによる通信をTLSという仕組みで暗号化して、安全に通信できるようにしたもの。

HTTPでは、通信内容が暗号化されていないため、通信経路上で第三者に内容を盗み見られる可能性がある。

HTTPSを利用すると、クライアントとサーバーの間の通信を暗号化できる。

WebサイトやAPIで、パスワードや個人情報などを安全に送受信するために利用される。

#### ② HTTPSの仕組み

HTTPSでは、TLSという仕組みを使って通信を保護する。

TLSには、主に次のような役割がある。

- 暗号化：通信内容を第三者に読み取られにくくする
- 改ざん検知：通信内容が途中で変更されていないか確認する
- 認証：接続先のサーバーが正しい相手か確認する

これらの仕組みによって、安全性の高い通信を実現している。

#### ③ HTTPとHTTPSの違い

**HTTP**
- 通信内容が暗号化されていない
- 第三者に通信内容を盗み見られる可能性がある

**HTTPS**
- TLSによって通信内容が暗号化される
- 通信内容の改ざんを検知できる
- サーバーの正当性を確認できる

HTTPSは、HTTPよりも安全に通信できる仕組みになっている。

#### ④ APIでHTTPSを利用する理由

APIでは、次のような重要な情報を送受信することがある。

- ログインIDやパスワード
- アクセストークン
- 個人情報
- ユーザーの登録情報

これらの情報が第三者に盗み見られたり、改ざんされたりすると、情報漏えいや不正アクセスにつながる可能性がある。

そのため、API通信ではHTTPSを利用することが重要。

また、HTTPSを利用していても、アプリ側での認証・認可や入力チェックなど、ほかのセキュリティ対策も必要になる。


### 6.2 APIキーの管理

#### ① APIキーとは？

APIキーとは、APIを利用するアプリケーションやシステムを識別するための文字列のこと。

APIを利用するときに、リクエストにAPIキーを含めることで、どのアプリケーションからのアクセスなのかを識別できる。

#### ② APIキーの役割

APIキーには、主に次のような役割がある。

- **アプリケーションの識別**：どのアプリからアクセスされたかを確認する
- **利用状況の管理**：APIの利用回数や使用量を記録する
- **アクセス制限**：利用できるAPIやアクセス元を制限する

ただし、APIキーだけでユーザー本人の認証が完了するとは限らない。

#### ③ APIキーの安全な管理

APIキーが第三者に漏れると、不正利用される可能性がある。

そのため、次のような対策が重要。

- **ソースコードに直接書かない**：GitHubなどの公開リポジトリに漏れるのを防ぐ
- **環境変数などで管理する**：秘密情報をソースコードと分けて管理する
- **不要になったキーを無効化する**：漏えいや不正利用が疑われる場合は、キーを無効化・再発行する
- **利用範囲を制限する**：必要なAPIやアクセス元だけに利用を許可する

#### ④ クライアントアプリでの注意点

WebブラウザやスマートフォンアプリにAPIキーを埋め込んでも、解析されて第三者に見られる可能性がある。

そのため、秘密にする必要があるAPIキーは、サーバー側で管理することが基本。

なお、公開されることを前提に発行されるAPIキーもあり、その場合は利用範囲やアクセス元などを制限して管理する。


### 6.3 CORSとCSRF

#### ① CORSとは？

CORS（Cross-Origin Resource Sharing）とは、異なるオリジンからのAPIアクセスを許可するための仕組み。

オリジンとは、次の3つの組み合わせのこと。

- スキーム（http / https）
- ホスト（example.com など）
- ポート番号

例えば、次の2つはオリジンが異なる。

- https://example.com
- https://api.example.com

ブラウザには、異なるオリジンへのアクセスを制限する「同一オリジンポリシー」という仕組みがある。

CORSを利用すると、APIサーバー側で許可するオリジンを指定できる。

代表的なレスポンスヘッダー：
Access-Control-Allow-Origin

なお、CORSは主にブラウザが適用する仕組みであり、APIの認証・認可そのものではない。

#### ② CSRFとは？

CSRF（Cross-Site Request Forgery）とは、ログイン中のユーザーに意図しないリクエストを送信させる攻撃のこと。

例えば、ユーザーがWebサービスにログインしている状態で、悪意のあるサイトを開くと、そのサイトからユーザーのブラウザを通じて不正なリクエストが送られる可能性がある。

特に、Cookieなどの認証情報がブラウザによって自動送信される仕組みで注意が必要。

#### ③ CSRFへの対策

CSRFを防ぐためには、次のような対策がある。

- **CSRFトークン**：正規の画面から発行されたトークンをリクエストに含める
- **SameSite Cookie**：Cookieが別サイトへのリクエストで送信されることを制限する
- **Origin / Refererの確認**：リクエスト元が正しいサイトか確認する
- **HTTPメソッドの適切な使用**：データ変更などの処理をGETで実行しない

#### ④ CORSとCSRFの違い

| 項目 | CORS | CSRF |
|---|---|---|
| 目的 | 異なるオリジンからのアクセスを制御する | 不正なリクエストを防ぐ |
| 関係するもの | ブラウザとAPIサーバー | ユーザーのブラウザとWebサービス |
| 主な対策 | 許可するオリジンの指定 | CSRFトークンなど |

CORSを設定しただけでは、CSRF対策にはならないため注意する。


### 6.4 SQLインジェクション

#### ① SQLインジェクションとは？

SQLインジェクションとは、悪意のあるSQL文を入力データに含めることで、データベースに不正な操作をさせる攻撃のこと。

例えば、ユーザーが入力した文字列をそのままSQL文に連結すると、意図しないSQLが実行される可能性がある。

#### ② SQLインジェクションの例

例えば、次のようなSQL文があるとする。

```spl
SELECT * FROM users
WHERE name = '入力された名前';
```

ユーザーの入力値をそのままSQL文に連結している場合、悪意のあるSQLを入力されると、検索条件を書き換えられる可能性がある。

その結果、次のような被害につながることがある。
- 本来見られないデータの取得
- データの不正な変更や削除
- データベース内の情報漏えい

#### ③ SQLインジェクションへの対策
主な対策は次のとおり。
- プレースホルダ（パラメータ化クエリ）を使用する：SQL文と入力値を分けて扱う
- ORMを適切に利用する：安全なパラメータバインド機能を利用する
- 入力値を検証する：想定した形式や値になっているか確認する
- データベースの権限を制限する：必要最小限の操作だけ許可する
特に、プレースホルダを利用することが重要。

#### ④ SQLインジェクション対策の注意点
入力値のチェックだけでは、SQLインジェクションを完全に防ぐことはできない。

そのため、SQL文に入力値を直接連結せず、プレースホルダなどを使って安全に処理する必要がある。

また、データベースの詳細なエラー情報をそのままユーザーに表示しないことも重要。

### 6.5 APIのセキュリティ対策

#### ① APIのセキュリティ対策とは？

APIのセキュリティ対策とは、不正アクセスや情報漏えい、データの改ざんなどを防ぐために行う対策のこと。

APIではユーザー情報やパスワードなどの重要なデータを扱うことがあるため、複数の対策を組み合わせることが重要。

#### ② 主なセキュリティ対策

APIを安全に利用するためには、次のような対策が必要。

- **HTTPSを使用する**：通信内容を暗号化し、盗聴や改ざんを防ぐ
- **APIキーを安全に管理する**：キーの漏えいや不正利用を防ぐ
- **認証・認可を適切に行う**：利用者が誰なのか、どの操作を許可するのか確認する
- **入力値を検証する**：不正なデータや想定外の値を受け付けない
- **SQLインジェクションを防ぐ**：プレースホルダなどを利用して安全にSQLを実行する
- **アクセス回数を制限する**：短時間に大量のリクエストが送られることを防ぐ（レート制限）

#### ③ 最小権限の原則

最小権限の原則とは、ユーザーやアプリケーションに必要最低限の権限だけを与える考え方のこと。

例えば、データを閲覧するだけのユーザーには、データを削除する権限を与えない。

これにより、万が一不正アクセスが発生した場合でも、被害を小さくできる可能性がある。

#### ④ エラー情報とログの管理

セキュリティ対策では、エラー情報やログの扱いにも注意が必要。

- **詳細なエラー情報を公開しない**：データベースの構造や内部情報を第三者に知られないようにする
- **ログを適切に記録する**：不正アクセスや異常な操作を調査できるようにする
- **秘密情報をログに残さない**：パスワードやアクセストークン、APIキーなどを記録しない

#### ⑤ セキュリティ対策の考え方

APIのセキュリティは、1つの対策だけで完全に守れるものではない。

HTTPS、認証・認可、入力値の検証、権限管理など、複数の対策を組み合わせて安全性を高めることが重要。

また、利用するライブラリやサーバーの脆弱性にも注意し、定期的に更新する必要がある。


### 6.6 第6章のまとめ

#### ① HTTPSとは？

HTTPSとは、TLSによってHTTP通信を暗号化し、安全性を高める仕組み。

主な役割は次の3つ。

- **暗号化**：通信内容を第三者に読み取られにくくする
- **改ざん検知**：通信内容が途中で変更されていないか確認する
- **サーバー認証**：接続先が正しいサーバーか確認する

#### ② APIキーの管理

APIキーとは、APIを利用するアプリケーションやシステムを識別するための文字列。

主な役割：
- アプリケーションの識別
- APIの利用状況の管理
- アクセス範囲の制限

安全に管理するためには、ソースコードに直接書かず、環境変数などで管理することが重要。

また、スマートフォンアプリやブラウザに埋め込んだキーは解析される可能性があるため、秘密にする必要があるキーはサーバー側で管理する。

#### ③ CORSとCSRF

**CORS（Cross-Origin Resource Sharing）**

異なるオリジンからのアクセスを、APIサーバー側で許可・制御する仕組み。

ブラウザの同一オリジンポリシーに関係する仕組みであり、APIの認証・認可とは異なる。

**CSRF（Cross-Site Request Forgery）**

ログイン中のユーザーに、意図しないリクエストを送信させる攻撃。

主な対策：
- CSRFトークン
- SameSite Cookie
- Origin / Refererの確認

CORSを設定しただけではCSRF対策にはならない。

#### ④ SQLインジェクション

SQLインジェクションとは、悪意のあるSQL文を入力データに含め、データベースに不正な操作をさせる攻撃。

主な対策：
- プレースホルダ（パラメータ化クエリ）の使用
- ORMの安全なパラメータバインド機能の利用
- 入力値の検証
- データベース権限の制限

特に、SQL文に入力値を直接連結せず、プレースホルダを使用することが重要。

#### ⑤ APIのセキュリティ対策

APIを安全に利用するためには、複数の対策を組み合わせることが重要。

主な対策：
- HTTPSによる通信の暗号化
- APIキーの適切な管理
- 認証・認可の実施
- 入力値の検証
- SQLインジェクション対策
- レート制限によるアクセス回数の制御
- 最小権限の原則
- エラー情報やログの適切な管理
- ライブラリやサーバーの定期的な更新

#### ⑥ 第6章の重要ポイント

| 用語 | 意味・役割 |
|---|---|
| HTTPS | 通信を暗号化して安全性を高める |
| APIキー | アプリケーションなどを識別する |
| CORS | 異なるオリジンからのアクセスを制御する |
| CSRF | ログイン中のユーザーに不正なリクエストを送らせる攻撃 |
| SQLインジェクション | 悪意のあるSQLによる不正操作 |
| 最小権限の原則 | 必要最低限の権限だけを与える |

APIのセキュリティでは、1つの対策だけに頼らず、通信・認証・入力値・権限・データベースなど、さまざまな観点から安全性を確保することが重要。
