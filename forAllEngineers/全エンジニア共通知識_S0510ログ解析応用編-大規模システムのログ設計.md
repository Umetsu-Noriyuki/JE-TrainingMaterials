## 1.1 大規模システムにおけるログ設計とは？

### ① ログ設計とは？

ログ設計とは、システムで発生する処理やエラーなどの情報を、どのような形式・内容・タイミングで記録するかを決めること。

基礎編では、出力されたログを読んで原因を調査する方法を学んだ。

応用編では、そもそも「調査しやすいログを出力するにはどうすればよいか」という視点で考える。

### ② なぜログ設計が重要なのか？

小規模なシステムであれば、ログの出力先や種類が少なく、比較的簡単に調査できる。

しかし、大規模システムでは次のような問題が発生する。

- 多数のユーザーが同時にシステムを利用する
- 複数のサーバーやサービスが連携している
- 大量のログが日々出力される
- 障害の発生箇所を特定しにくい
- ログの保存容量が増え続ける

そのため、あらかじめログの出力ルールを決めておく必要がある。

### ③ ログ設計で実現したいこと

ログ設計では、主に次のようなことを実現する。

| 目的 | 内容 |
|---|---|
| 調査のしやすさ | 必要な情報をすぐに検索できる |
| 原因特定 | エラーが発生した箇所や原因を追跡できる |
| 処理の可視化 | システム内部の処理状況を把握できる |
| 性能分析 | 処理時間や通信時間を確認できる |
| セキュリティ | 不正アクセスや不審な操作を確認できる |
| 運用管理 | ログの保存容量や保存期間を管理できる |

### ④ 大規模システムでのログ設計の例

例えば、ECサイトで注文処理を行う場合を考える。

```text
ユーザー
  ↓
注文API
  ↓
注文サービス
  ↓
データベース
  ↓
決済サービス
  ↓
注文完了
```

このような処理では、各サービスでログを出力する必要がある。

もし決済処理でエラーが発生した場合、注文API・注文サービス・データベース・決済サービスのログを確認することで、どこで問題が発生したのかを調査できる。

そのため、各サービスで共通したログの出力ルールを設けることが重要になる。

### ⑤ まとめ

ログ設計は、単にログを出力するための設定ではない。

障害発生時の原因特定や性能分析、セキュリティ対策などを効率的に行うための重要な仕組みである。

大規模システムでは、複数のサービスや大量のログを扱うため、最初にログの形式や出力ルールを統一しておくことが重要になる。

### 1.2 ログ設計で考えるべきこと

#### ① ログに何を記録するか決める

ログ設計では、最初に「どのような情報を記録するか」を決める必要がある。

記録する情報が不足していると、障害発生時に原因を特定できなくなる可能性がある。

代表的な記録項目は次のとおり。

| 項目 | 内容 |
|---|---|
| Timestamp | ログが出力された日時 |
| Log Level | INFO、WARN、ERRORなどの重要度 |
| Logger | ログを出力したサービスやクラス |
| Message | 処理内容やエラーの説明 |
| Request ID | 個々のリクエストを識別するID |
| Trace ID | 複数のサービスにまたがる処理を識別するID |
| Stack Trace | エラー発生時の呼び出し履歴 |

これらの情報を適切に記録することで、ログを検索・分析しやすくなる。

#### ② ログの出力レベルを統一する

複数のサービスでログレベルの使い方が異なると、ログの重要度を正しく判断できなくなる。

例えば、あるサービスでは正常処理をERRORで出力し、別のサービスではINFOで出力している場合、調査時に混乱が生じる。

そのため、次のような共通ルールを設ける。

| ログレベル | 使用する場面 |
|---|---|
| DEBUG | 開発・調査に必要な詳細情報 |
| INFO | 正常な処理や重要なイベント |
| WARN | 処理は継続できるが注意が必要な状態 |
| ERROR | 処理が失敗した状態 |

サービスごとに独自の判断をするのではなく、システム全体で共通した基準を設けることが重要。

#### ③ ログの形式を統一する

ログの形式がサービスごとに異なると、検索や集計が難しくなる。

例えば、次のようなログが混在している場合を考える。

```text
2026-11-06 10:00:00 ERROR UserService ユーザー取得失敗
```

```text
[ERROR] UserService: Failed to retrieve user
```

人間が読むことはできるが、機械的に情報を抽出したり、複数のログをまとめて検索したりする際に扱いづらくなる。

そのため、ログの出力形式を統一することが重要になる。

代表的な形式として、JSON形式を利用した構造化ログがある。

構造化ログについては、次の1.3で詳しく学習する。

#### ④ ログの出力タイミングを決める

どの処理でログを出力するかも重要な設計項目。

例えば、次のタイミングでログを出力する。

- APIリクエストを受信したとき
- 重要な処理を開始したとき
- 処理が正常に完了したとき
- データベースへの接続やSQL実行を行ったとき
- 外部サービスと通信したとき
- エラーが発生したとき

ただし、すべての処理で大量のログを出力すると、ログの保存容量や検索性能に影響する。

必要な情報を適切なタイミングで記録することが重要。

#### ⑤ セキュリティを考慮する

ログには、ユーザー情報やシステム内部の情報が含まれる可能性がある。

そのため、次のような情報は原則としてそのまま記録しない。

- パスワード
- アクセストークン
- APIキー
- クレジットカード番号
- 個人情報

必要に応じてマスキング（情報の一部を隠す処理）を行う。

例：

```text
メールアドレス: example@example.com
```

マスキング後：

```text
メールアドレス: ex*****@example.com
```

ログは障害調査に役立つ一方で、情報漏えいの原因にもなり得る。

そのため、調査に必要な情報と保護すべき情報を区別して設計する必要がある。

#### ⑥ まとめ

ログ設計では、次の5つを意識する。

1. 記録する情報を決める
2. ログレベルを統一する
3. ログの形式を統一する
4. ログの出力タイミングを決める
5. セキュリティを考慮する

これらをシステム全体で統一することで、障害調査やログ分析を効率的に行えるようになる。

### 1.3 構造化ログとは？

#### ① 構造化ログとは？

構造化ログとは、ログの情報を決められた項目や形式に沿って記録する方法。

一般的には、JSON形式で出力されることが多い。

通常のログでは、日時や重要度、メッセージなどの情報がひとつの文章として記録される。

一方、構造化ログでは、それぞれの情報をキーと値の組み合わせで記録する。

#### ② 通常のログと構造化ログの違い

**通常のログ**

```text
2026-11-06 10:00:00 ERROR UserService ユーザー情報の取得に失敗しました
```

**構造化ログ（JSON形式）**

```json
{
  "timestamp": "2026-11-06T10:00:00+09:00",
  "level": "ERROR",
  "service": "UserService",
  "message": "ユーザー情報の取得に失敗しました"
}
```

通常のログは文章として情報を記録する。

構造化ログは、情報を項目ごとに分けて記録する。

例えば、構造化ログでは次のように情報を取得できる。

- `timestamp`：ログの出力日時
- `level`：ログレベル
- `service`：ログを出力したサービス
- `message`：処理内容やエラーの説明

このように、ログの情報を機械的に扱いやすくなる。

#### ③ 構造化ログのメリット

構造化ログには、次のようなメリットがある。

| メリット | 内容 |
|---|---|
| 検索しやすい | 項目ごとに条件を指定して検索できる |
| 集計しやすい | ERRORの件数やサービスごとの発生数を集計できる |
| 分析しやすい | ログ管理ツールで情報を分析しやすい |
| 形式を統一できる | 複数のサービスで共通の形式を利用できる |
| 自動処理しやすい | プログラムでログの内容を解析しやすい |

例えば、ログ管理ツールで次のような検索ができる。

```text
level = ERROR
service = UserService
```

この条件を使うことで、UserServiceが出力したERRORログだけを抽出できる。

#### ④ 構造化ログでよく使われる項目

実際の構造化ログでは、次のような項目を記録することがある。

| 項目 | 内容 |
|---|---|
| timestamp | ログの出力日時 |
| level | ログレベル |
| service | サービス名 |
| message | ログの内容 |
| requestId | リクエストを識別するID |
| traceId | 複数サービスにまたがる処理を識別するID |
| userId | 操作したユーザーを識別するID（取り扱いには注意が必要） |
| duration | 処理にかかった時間 |
| error | エラーの種類や詳細 |

必要な項目はシステムの構成や調査目的によって異なる。

また、個人情報や認証情報などを不用意に記録しないように注意する。

#### ⑤ 構造化ログの利用例

例えば、注文APIでエラーが発生した場合、次のようなログを出力する。

```json
{
  "timestamp": "2026-11-06T10:30:00+09:00",
  "level": "ERROR",
  "service": "OrderService",
  "message": "注文処理に失敗しました",
  "requestId": "req-123",
  "traceId": "trace-456",
  "duration": 1500,
  "error": "Database connection timeout"
}
```

このログから、次の情報を確認できる。

- いつエラーが発生したか
- どのサービスで発生したか
- どのリクエストに関係するか
- どの処理の流れに関係するか
- 処理にどれくらい時間がかかったか
- どのようなエラーだったか

このように、構造化ログを利用すると、障害調査に必要な情報を整理して扱える。

#### ⑥ まとめ

構造化ログとは、ログの情報を決められた項目や形式に沿って記録する方法。

JSON形式などを利用することで、ログの検索・集計・分析・自動処理がしやすくなる。

大規模システムでは、複数のサービスのログをまとめて扱うことが多いため、構造化ログは重要な仕組みとなる。

### 1.4 ログの管理・保存方法

#### ① なぜログの管理・保存が必要なのか？

大規模システムでは、日々大量のログが出力される。

ログを適切に管理しないと、次のような問題が発生する。

- ログファイルが大きくなり、ディスク容量を圧迫する
- 必要なログを探すのに時間がかかる
- 古いログが残り続け、管理が難しくなる
- 障害発生時に必要なログがすでに削除されている
- ログへの不正アクセスや情報漏えいが発生する

そのため、ログをどこに保存するか、どのくらいの期間保存するか、どのように管理するかを決める必要がある。

#### ② ログの保存先

ログの保存先には、主に次のようなものがある。

| 保存先 | 内容 |
|---|---|
| ローカルファイル | サーバーやアプリケーション内のファイルに保存する |
| ログ管理サーバー | 複数のサーバーからログを集約して保存する |
| クラウドストレージ | クラウド上のストレージにログを保存する |
| ログ分析サービス | ログの保存だけでなく、検索・分析・可視化も行う |

大規模システムでは、複数のサーバーやサービスからログを集約できる仕組みがよく利用される。

ログを一か所に集約することで、サーバーごとにログインして確認する手間を減らせる。

#### ③ ログのローテーション

ログローテーションとは、ログファイルが大きくなりすぎないように、一定の条件でファイルを切り替える仕組み。

例えば、次のような条件でローテーションを行う。

- ファイルサイズが一定以上になったとき
- 1日経過したとき
- 1週間経過したとき

例：

```text
app.log
app.log.1
app.log.2
app.log.3
```

新しいログを `app.log` に出力し、古いログは順番に別ファイルへ移動する。

ローテーションを行うことで、ひとつのログファイルが巨大になることを防げる。

#### ④ ログの保存期間

ログは、必要以上に長期間保存し続ける必要はない。

一方で、短期間で削除してしまうと、後から障害の原因を調査できなくなる可能性がある。

そのため、ログの種類や目的に応じて保存期間を決める。

| ログの種類 | 保存期間を決める際の考え方 |
|---|---|
| アプリケーションログ | 障害調査に必要な期間を考慮する |
| アクセスログ | 利用状況やセキュリティ調査に必要な期間を考慮する |
| 監査ログ | 法令や社内規定、監査要件を考慮する |
| デバッグログ | 必要性を確認し、比較的短期間で管理する |

※実際の保存期間は、法令・業界規制・社内ルール・システム要件によって異なる。

#### ⑤ ログのアクセス制御

ログには、ユーザー情報やシステム内部の情報が含まれる場合がある。

そのため、誰でも自由にログを閲覧・変更・削除できる状態にしてはいけない。

例えば、次のような対策を行う。

- ログを閲覧できるユーザーを制限する
- ログの変更や削除ができる権限を制限する
- 通信や保存時に必要な暗号化を行う
- 重要な監査ログは改ざんされにくい場所に保存する

特に監査ログは、後から内容を確認できるように、改ざん防止を考慮することが重要。

#### ⑥ ログ管理のまとめ

ログの管理・保存では、次の5つを意識する。

1. 適切な保存先を選ぶ
2. ログを集約して管理する
3. ログローテーションを設定する
4. ログの保存期間を決める
5. アクセス制御や改ざん防止を行う

ログを出力するだけでなく、必要なときに安全に利用できる状態で管理することが重要。

### 1.5 ログの運用と改善

#### ① ログは設計して終わりではない

ログは、最初に出力ルールを決めたら終わりではない。

実際にシステムを運用する中で、ログが適切に出力されているか、調査に役立っているかを継続的に確認する必要がある。

例えば、次のような点を監視する。

- ERRORログが急増していないか
- 特定のサービスからログが出力されなくなっていないか
- ログの保存先の容量が不足していないか
- ログ管理システムへの取り込みが遅れていないか

#### ② ログ監視とアラート

重要なログや異常を検知したときに、担当者へ通知する仕組みをアラートという。

例えば、次のような条件でアラートを設定する。

| 監視対象 | アラートの条件 |
|---|---|
| ERRORログ | 一定時間内に大量発生した |
| ログ出力 | 特定サービスのログが出力されなくなった |
| ディスク容量 | ログ保存先の空き容量が少なくなった |
| ログ取り込み | ログ管理システムへの反映が遅れている |

アラートを設定することで、障害の兆候に早く気づき、対応につなげられる。

#### ③ ログの品質を定期的に見直す

ログが大量に出力されていても、必要な情報が含まれていなければ調査に役立たない。

そのため、定期的にログの内容を確認する。

- 調査に必要な情報が含まれているか
- Request IDやTrace IDが適切に出力されているか
- 不要なログや重複したログが多くないか
- ログレベルの使い分けが適切か
- パスワードやトークンなどの機密情報が出力されていないか

問題があれば、ログの出力内容やルールを改善する。

#### ④ ログの出力量を調整する

ログを増やしすぎると、保存容量や検索性能に影響することがある。

例えば、次のような改善が考えられる。

- 調査に不要なDEBUGログを減らす
- 同じ内容のログが何度も出力されないようにする
- 必要な情報が不足している場合は項目を追加する
- 大量に発生するログは、用途に応じてサンプリングを検討する

ただし、セキュリティ監査や重要な操作記録など、必ず残す必要があるログを安易に間引いてはいけない。

#### ⑤ ログとメトリクスを組み合わせる

システムの状態を把握するには、ログだけでなくメトリクスも役立つ。

| 項目 | 意味 | 具体例 |
|---|---|---|
| ログ | 発生した出来事の詳細 | DB接続に失敗した |
| メトリクス | システムの状態を数値で表したもの | CPU使用率が90% |

例えば、CPU使用率が急上昇したというメトリクスを確認し、その時間帯のログを調べることで、原因となった処理を特定しやすくなる。

このように、ログとメトリクスを組み合わせることで、より効果的な障害調査ができる。

#### ⑥ まとめ

ログは出力するだけでなく、継続的に監視・改善することが重要。

- ERRORログやログ出力状況を監視する
- 異常を検知するためにアラートを設定する
- ログの内容や品質を定期的に見直す
- 不要なログを減らし、必要な情報を追加する
- ログとメトリクスを組み合わせて調査する

### 1.6 第1章まとめ

#### ① 大規模システムにおけるログ設計

大規模システムでは、複数のサービスやサーバーから大量のログが出力される。

そのため、システム全体でログの出力ルールや形式を統一することが重要。

ログを設計するときは、次の内容を決めておく。

- 何を記録するか
- どのログレベルを使用するか
- どの形式で出力するか
- どのタイミングで出力するか
- 機密情報をどのように扱うか

大量のログを適切に管理するため、次の仕組みを利用する。

- ログの一元管理

- 保存期間の設定
- アクセス制御

#### ⑥ 第1章の重要ポイント

大規模システムでは、ログを統一されたルールで設計し、適切に保存・管理・運用することが重要。
