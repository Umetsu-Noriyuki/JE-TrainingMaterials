### 7.1 実践的なログ調査の進め方

#### ① 実践的なログ調査とは？

実践的なログ調査とは、実際に発生したエラーや不具合について、ログを確認しながら原因を特定すること。

これまで学んできたログの種類や読み方を使い、問題が発生した場所や原因を順番に調査していく。

例えば、次のような問題が発生した場合を考える。

- ユーザー情報を取得できない
- APIのレスポンスが遅い
- データの登録に失敗する
- 外部サービスとの通信が失敗する
- 特定の操作をするとアプリがエラーになる

このような問題に対して、ログから事実を確認し、原因を絞り込んでいく。

#### ② 調査を始める前に情報を整理する

ログを確認する前に、まずは問題が発生した状況を整理する。

主に確認する情報は次のとおり。

| 確認項目 | 内容 |
|---|---|
| 発生日時 | いつ問題が発生したか |
| 発生した操作 | どのような操作をしたときか |
| 発生した機能 | どの画面やAPIで発生したか |
| 発生頻度 | 毎回発生するか、特定の条件だけか |
| 対象環境 | 開発環境・テスト環境・本番環境のどれか |
| エラー内容 | どのようなエラーが表示されたか |

これらの情報があると、調査対象となるログを絞り込みやすくなる。

特に、発生日時やRequest IDなどが分かっていると、関連するログを探しやすい。

#### ③ ログ調査の基本的な流れ

実際にログを調査するときは、次のような流れで進める。

1. エラーが発生した日時や操作を確認する
2. 該当するエラーログを探す
3. エラーの前後に出力されたログを確認する
4. 関連するAPI・DB・外部サービスのログを確認する
5. 原因を切り分ける
6. 原因に対する修正や対策を行う
7. 修正後に正常に動作するか確認する

エラーログだけを確認しても、原因が分からない場合がある。

そのため、エラーの直前に何が行われていたのか、後続の処理がどうなったのかも確認することが重要。

#### ④ ログから事実を確認する

ログ調査では、推測だけで原因を決めつけないことが大切。

例えば、APIの処理が失敗した場合でも、原因はさまざま考えられる。

- リクエストの内容が間違っていた
- バックエンドの処理に問題があった
- DBへの接続に失敗した
- 外部サービスとの通信に失敗した

ログに記録されたステータスコードやエラー内容、処理時間などを確認し、事実に基づいて原因を絞り込む。

#### ⑤ 調査結果を記録する

原因を特定したら、調査した内容や結果を記録しておく。

例えば、次のような内容を残す。

- 発生した問題
- 発生日時や発生条件
- 確認したログ
- 特定した原因
- 実施した修正内容
- 修正後の確認結果

調査結果を記録しておくことで、同じ問題が発生したときに解決しやすくなる。

また、チーム内で調査内容を共有する際にも役立つ。

#### ⑥ 実践的なログ調査で意識すること

実際のログ調査では、次のポイントを意識する。

- 発生した状況を先に整理する
- エラーログだけでなく前後のログも確認する
- API・DB・外部サービスなど関連するログを確認する
- Request IDやTrace IDを活用する
- 推測ではなくログに記録された事実をもとに判断する
- 原因と修正内容を記録する

ログ調査は、単にエラーのメッセージを読むだけではない。

複数の情報を組み合わせて、問題が発生した流れを理解することが重要。

### 7.2 APIエラーの調査演習

#### ① APIエラーの調査とは？

APIエラーの調査とは、API通信で問題が発生したときに、リクエストやレスポンス、バックエンドのログなどを確認して原因を特定すること。

例えば、次のような問題がある。

- APIを呼び出してもデータが取得できない
- データの登録に失敗する
- APIのレスポンスが遅い
- 特定のユーザーだけエラーになる
- APIから500エラーが返される

APIエラーが発生した場合は、ステータスコードだけで判断せず、関連するログも確認することが重要。

#### ② APIのログを確認する

まずは、APIのリクエストとレスポンスに関するログを確認する。

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 INFO ApiServer
Request received
Method: GET
Path: /api/users/10
Request ID: req-001

2026-11-05 10:00:01 ERROR ApiServer
Request failed
Status: 500
Request ID: req-001
```

このログから、次のことが分かる。

- GETメソッドでユーザー情報を取得しようとしている
- 対象のURLは `/api/users/10`
- リクエストIDは `req-001`
- APIの処理結果は500エラー

ここで重要なのは、Request IDが同じログを検索すること。

同じRequest IDを持つログを探すことで、APIのリクエストからエラー発生までの処理を追跡できる。

#### ③ HTTPステータスコードから原因を絞り込む

APIエラーの調査では、HTTPステータスコードも重要な手掛かりになる。

| ステータスコード | 主な原因 | 確認する内容 |
|---|---|---|
| 400 Bad Request | リクエストの形式や値が不正 | パラメータや入力値 |
| 401 Unauthorized | 認証に失敗 | トークンや認証情報 |
| 403 Forbidden | アクセス権限がない | ユーザーの権限 |
| 404 Not Found | 対象が存在しない | URLや対象データ |
| 500 Internal Server Error | サーバー内部でエラー | バックエンドの処理や例外 |
| 503 Service Unavailable | サービスを利用できない | サーバーの稼働状況や負荷 |

例えば、500エラーが発生した場合は、バックエンド側のログを確認し、例外やDB処理などに問題がないか調査する。

#### ④ 実際のAPIエラーを調査する

次のログを見てみよう。

```text
2026-11-05 10:00:00 INFO ApiServer
Request received
Method: GET
Path: /api/users/10
Request ID: req-002

2026-11-05 10:00:01 INFO UserService
Fetching user data
Request ID: req-002

2026-11-05 10:00:02 ERROR UserRepository
Database connection failed
Request ID: req-002

2026-11-05 10:00:02 ERROR ApiServer
Request failed
Status: 500
Request ID: req-002
```

このログから、次の処理の流れが分かる。

1. APIリクエストを受信した
2. UserServiceでユーザー情報を取得しようとした
3. UserRepositoryでDB接続に失敗した
4. APIが500エラーを返した

この場合、APIのリクエスト自体ではなく、DB接続に問題が発生している可能性が高い。

さらにDBの接続ログを確認し、接続先や認証情報、DBサーバーの状態などを調査する。

#### ⑤ APIエラー調査で意識すること

APIエラーを調査するときは、次のポイントを意識する。

- HTTPステータスコードを確認する
- リクエストの内容やURLを確認する
- Request IDで関連するログを検索する
- エラーの前後に出力されたログを確認する
- バックエンドやDBのログも確認する
- エラーの発生箇所と根本原因を区別する

APIのエラーは、必ずしもAPIそのものが原因とは限らない。

DBや外部サービスなど、APIの内部で利用している仕組みに問題がある場合もあるため、処理全体の流れを追跡することが重要。

### 7.3 DBエラーの調査演習

#### ① DBエラーの調査とは？

DBエラーの調査とは、データベースへの接続やSQLの実行で問題が発生したときに、ログを確認して原因を特定すること。

例えば、次のような問題がある。

- DBに接続できない
- SQLの実行に失敗する
- データを登録できない
- データを取得できない
- SQLの実行に時間がかかる
- トランザクションが途中で失敗する

DBエラーが発生した場合は、エラーの内容だけでなく、実行されたSQLや処理の流れも確認することが重要。

#### ② DB接続エラーを調査する

まずは、バックエンドからDBへ正常に接続できているか確認する。

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 ERROR DatabaseConnection
Connection refused
Host: db-server
Port: 5432
```

このログから、DBサーバーへの接続が拒否されたことが分かる。

PostgreSQLでは、一般的にポート番号5432が使用される。

主な確認ポイントは次のとおり。

- DBサーバーが起動しているか
- 接続先のホスト名やポート番号が正しいか
- ネットワークに問題がないか
- DBへの接続数が上限に達していないか
- 認証情報に問題がないか

#### ③ SQLの実行エラーを調査する

DBへの接続が正常でも、SQLの実行時にエラーが発生する場合がある。

例えば、次のようなログがある。

```text
2026-11-05 10:00:01 ERROR UserRepository
SQL execution failed
Error: column "user_name" does not exist
```

この場合、SQLで指定した `user_name` というカラムが存在しない可能性がある。

主な確認ポイントは次のとおり。

- テーブル名やカラム名が正しいか
- SQLの構文に間違いがないか
- WHERE句の条件が正しいか
- 必要なデータが存在しているか
- DBのテーブル構造が想定どおりか

例えば、アプリ側では `user_name` を参照しているのに、実際のDBでは `name` というカラム名になっている場合、SQLの実行に失敗する可能性がある。

#### ④ SQLの実行時間が長い場合を調査する

SQLが正常に実行されていても、処理に時間がかかる場合がある。

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 WARN UserRepository
Slow query detected
Duration: 4500ms
```

この場合、SQLの実行に4,500ミリ秒（4.5秒）かかっている。

主な原因として、次のようなものが考えられる。

- インデックスが適切に設定されていない
- 大量のデータを取得している
- SQLの検索条件が適切でない
- DBサーバーの負荷が高い
- 他の処理によってDBがロックされている

このような場合は、SQLの内容や実行計画、DBの負荷などを確認する。

#### ⑤ トランザクションのエラーを調査する

複数のDB操作をまとめて実行するトランザクションでは、途中の処理に失敗すると、変更内容が取り消される場合がある。

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 INFO OrderRepository
Transaction BEGIN

2026-11-05 10:00:01 INFO OrderRepository
Order data inserted

2026-11-05 10:00:02 ERROR OrderRepository
Stock update failed

2026-11-05 10:00:02 WARN OrderRepository
Transaction ROLLBACK
```

このログから、次の流れが分かる。

1. トランザクションを開始した
2. 注文データの登録に成功した
3. 在庫数の更新に失敗した
4. トランザクションを取り消した

この場合、注文データの登録も含めて変更が取り消されている可能性がある。

どの処理で失敗したのか、ROLLBACKが正常に行われたのかを確認することが重要。

#### ⑥ 実際のDBエラーを調査する

次のログを見てみよう。

```text
2026-11-05 10:00:00 INFO UserService
Fetching user data

2026-11-05 10:00:01 INFO UserRepository
Executing SQL

2026-11-05 10:00:05 WARN UserRepository
Slow query detected
Duration: 4000ms

2026-11-05 10:00:05 ERROR ApiServer
Request timeout
Status: 500
```

このログから、次のことが分かる。

1. ユーザー情報の取得処理が開始された
2. SQLが実行された
3. SQLの実行に4秒かかった
4. APIの処理がタイムアウトした

この場合、SQLの実行時間が長いことが原因の一つとして考えられる。

SQLの内容や実行計画、インデックス、DBの負荷などを確認して、処理が遅くなっている原因を調査する。

#### ⑦ DBエラー調査で意識すること

DBエラーを調査するときは、次のポイントを意識する。

- DBへの接続状況を確認する
- SQLの内容や実行結果を確認する
- テーブルやカラムの構造を確認する
- SQLの実行時間を確認する
- トランザクションの開始・確定・取り消しを確認する
- バックエンドのログとDBのログを関連付ける

DBエラーは、単純な接続エラーだけでなく、SQLやデータ、処理時間など、さまざまな原因で発生する。

ログを順番に確認し、どの段階で問題が発生したのかを特定することが重要。

### 7.4 外部サービス連携エラーの調査演習

#### ① 外部サービス連携エラーとは？

外部サービス連携エラーとは、自分たちのシステムから外部のAPIやサービスを利用するときに発生するエラーのこと。

例えば、次のようなサービスとの連携がある。

- 決済サービス
- メール送信サービス
- 外部の認証サービス
- 地図情報サービス
- ファイル保存サービス

外部サービスとの通信で問題が発生すると、自分たちのシステムの処理も失敗する場合がある。

そのため、ログを確認して、どこで問題が発生したのかを特定する必要がある。

#### ② 外部サービスへのリクエストを確認する

まずは、外部サービスに対して正常にリクエストを送信できているか確認する。

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 INFO PaymentService
Sending request to payment API
Method: POST
URL: https://api.example.com/payments
Request ID: req-101
```

このログから、決済APIにPOSTリクエストを送信しようとしていることが分かる。

主な確認ポイントは次のとおり。

- 接続先のURLが正しいか
- HTTPメソッドが正しいか
- リクエストの内容が正しいか
- 必要なヘッダーが設定されているか
- 認証情報に問題がないか

#### ③ HTTPステータスコードを確認する

外部サービスからレスポンスが返ってきた場合は、HTTPステータスコードを確認する。

| ステータスコード | 主な意味 | 調査する内容 |
|---|---|---|
| 200 OK | 正常終了 | 期待したレスポンスが返っているか |
| 400 Bad Request | リクエスト不正 | 送信したデータや形式 |
| 401 Unauthorized | 認証失敗 | APIキーや認証情報 |
| 403 Forbidden | アクセス拒否 | 利用権限や契約内容 |
| 429 Too Many Requests | リクエスト過多 | APIの利用制限 |
| 500 Internal Server Error | サーバー内部エラー | 外部サービス側の処理状況 |
| 503 Service Unavailable | サービス利用不可 | 外部サービスの稼働状況 |

ただし、500や503が返ってきても、必ず外部サービス側だけに原因があるとは限らない。

自分たちのリクエスト内容や通信経路にも問題がないか確認することが重要。

#### ④ タイムアウトエラーを調査する

外部サービスから一定時間内にレスポンスが返ってこない場合、タイムアウトが発生することがある。

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 INFO PaymentService
Sending request to payment API

2026-11-05 10:00:10 ERROR PaymentService
Connection timeout
Duration: 10000ms
Request ID: req-101
```

このログから、外部サービスとの通信が10秒経過しても完了しなかったことが分かる。

主な確認ポイントは次のとおり。

- 外部サービスが正常に稼働しているか
- ネットワークに問題がないか
- 接続先URLが正しいか
- タイムアウト時間の設定が適切か
- 外部サービス側の応答が遅くなっていないか

#### ⑤ リトライ処理を確認する

外部サービスとの通信に一時的な問題が発生した場合、リトライ処理によって再度リクエストを送信することがある。

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 WARN PaymentService
Request failed

2026-11-05 10:00:01 INFO PaymentService
Retrying request
Attempt: 2

2026-11-05 10:00:02 INFO PaymentService
Request succeeded
```

このログから、最初のリクエストは失敗したものの、2回目のリクエストで成功したことが分かる。

リトライ処理を調査するときは、次の点を確認する。

- リトライが何回実行されたか
- リトライの間隔は適切か
- 最終的に成功したか失敗したか
- リトライ上限に達していないか

ただし、決済処理などでは注意が必要。

最初のリクエストが成功していたのに、レスポンスだけ受け取れなかった場合、再送信によって二重決済が発生する可能性がある。

そのため、二重実行を防ぐ仕組み（冪等性キーなど）が重要になる。

#### ⑥ エラーの発生場所を切り分ける

外部サービス連携のエラーでは、どこに原因があるのかを切り分ける必要がある。

| 調査対象 | 確認する内容 |
|---|---|
| 自分たちのシステム | リクエスト内容や送信処理に問題がないか |
| ネットワーク | 通信が正常に行われているか |
| 外部サービス | サービス側で障害が発生していないか |
| 認証情報 | APIキーやトークンなどに問題がないか |
| 設定 | 接続先URLやタイムアウト時間が正しいか |

例えば、外部サービスから401が返ってきた場合は、認証情報を確認する。

一方、Connection timeoutが発生した場合は、ネットワークや外部サービスの稼働状況などを確認する。

エラーの種類によって調査する対象を変えることが重要。

#### ⑦ 実際の外部サービス連携エラーを調査する

次のログを見てみよう。

```text
2026-11-05 10:00:00 INFO OrderService
Creating order

2026-11-05 10:00:01 INFO PaymentService
Sending request to payment API
Request ID: req-201

2026-11-05 10:00:11 ERROR PaymentService
Connection timeout
Duration: 10000ms
Request ID: req-201

2026-11-05 10:00:11 ERROR OrderService
Payment processing failed
```

このログから、次の流れが分かる。

1. 注文作成処理が開始された
2. 決済APIにリクエストを送信した
3. 10秒経過してもレスポンスが返らず、タイムアウトした
4. 決済処理が失敗した

この場合、次のような調査が必要になる。

- 外部の決済サービスが正常に稼働しているか
- ネットワークに問題がないか
- タイムアウト時間の設定は適切か
- 決済が実際には完了していないか

特に決済処理では、タイムアウトしたからといって決済が失敗したと決めつけてはいけない。

決済結果を外部サービス側で確認してから、必要に応じて再処理することが重要。

#### ⑧ 外部サービス連携エラー調査で意識すること

外部サービス連携エラーを調査するときは、次のポイントを意識する。

- リクエストの送信内容を確認する
- レスポンスのステータスコードを確認する
- 通信時間やタイムアウトを確認する
- リトライの回数と最終結果を確認する
- 自分たちのシステムと外部サービスのどちらに原因があるか切り分ける
- Request IDなどを使って関連ログを追跡する
- 決済などの二重実行に注意する

外部サービス連携では、自分たちのシステムだけでなく、通信経路や連携先の状態も調査する必要がある。

### 7.5 複数のログを使った原因特定

#### ① 複数のログを使う理由

実際のシステムでは、一つの処理が複数のサービスや機能を通って実行されることがある。

例えば、注文処理では次のような流れになる。

1. APIがリクエストを受け取る
2. バックエンドが注文内容を確認する
3. DBに注文データを登録する
4. 外部の決済サービスにリクエストを送信する
5. APIが結果を返す

このような処理では、エラーが発生した場所とは別の場所に原因がある場合もある。

そのため、API・DB・外部サービスなど、複数のログを関連付けて調査することが重要。

#### ② Request ID・Trace IDを使ってログを関連付ける

複数のログを関連付けるときは、Request IDやTrace IDを利用する。

- **Request ID**：個々のリクエストを識別するID
- **Trace ID**：複数のサービスをまたぐ一連の処理を識別するID
- **Span ID**：一連の処理の中にある個々の処理を識別するID

例えば、次のようなログがある。

```text
INFO ApiServer: Request received
Trace ID: trace-001

INFO OrderService: Creating order
Trace ID: trace-001

INFO OrderRepository: Inserting order
Trace ID: trace-001

ERROR PaymentService: Connection timeout
Trace ID: trace-001
```

すべて同じTrace IDを持っているため、一連の注文処理に関係するログだと分かる。

このように、Trace IDを使うことで複数のサービスにまたがる処理を追跡できる。

#### ③ 時系列でログを確認する

関連するログを集めたら、次は時系列で確認する。

例えば、次のログがある。

```text
10:00:00 INFO ApiServer
Request received

10:00:01 INFO OrderService
Creating order

10:00:02 INFO OrderRepository
Order data inserted

10:00:03 INFO PaymentService
Sending payment request

10:00:13 ERROR PaymentService
Connection timeout

10:00:13 ERROR OrderService
Payment processing failed

10:00:13 ERROR ApiServer
Request failed Status 500
```

このログから、次の流れが分かる。

1. APIがリクエストを受け取った
2. 注文作成処理が開始された
3. DBへの注文データ登録に成功した
4. 決済サービスへリクエストを送信した
5. 決済サービスとの通信がタイムアウトした
6. 注文処理が失敗した
7. APIが500エラーを返した

ここで重要なのは、**最初にエラーが発生した場所を確認すること**。

APIの500エラーだけを見ると、API自体に問題があるように見える。

しかし、時系列で確認すると、最初のエラーは決済サービスとの通信で発生していることが分かる。

#### ④ エラーの連鎖を確認する

一つのエラーが原因となって、別のエラーが発生することがある。

これをエラーの連鎖として捉えることができる。

例えば、次のような流れ。

```text
PaymentService:
Connection timeout

OrderService:
Payment processing failed

ApiServer:
Request failed Status 500
```

この場合、3つのエラーが出力されているが、すべてが独立した問題とは限らない。

決済サービスとの通信タイムアウトが原因となり、注文処理の失敗やAPIの500エラーにつながった可能性がある。

そのため、複数のエラーが出ている場合は、それぞれの発生時刻や処理の関係を確認することが重要。

#### ⑤ 根本原因と二次的なエラーを区別する

障害調査では、最初に発生した問題と、その影響によって発生した問題を区別する必要がある。

| 分類 | 意味 | 例 |
|---|---|---|
| 根本原因 | 障害を引き起こした元の問題 | 外部サービスとの通信タイムアウト |
| 二次的なエラー | 根本原因の影響で発生したエラー | 注文処理の失敗 |
| 表面化したエラー | 利用者やAPIに見えるエラー | HTTP 500 |

例えば、APIが500を返していても、根本原因はDB接続や外部サービスとの通信にあるかもしれない。

表面に出ているエラーだけを修正するのではなく、根本原因を特定することが重要。

#### ⑥ 実際のログから原因を特定する

次のログを確認してみよう。

```text
10:00:00 INFO ApiServer
Request received
Trace ID: trace-100

10:00:01 INFO OrderService
Creating order
Trace ID: trace-100

10:00:02 INFO OrderRepository
Order data inserted
Trace ID: trace-100

10:00:03 INFO PaymentService
Sending payment request
Trace ID: trace-100

10:00:13 ERROR PaymentService
Connection timeout
Trace ID: trace-100

10:00:13 ERROR OrderService
Payment processing failed
Trace ID: trace-100

10:00:13 ERROR ApiServer
Request failed Status 500
Trace ID: trace-100
```

このログから、次のことが分かる。

- APIのリクエスト受付は成功している
- DBへの注文データ登録は成功している
- 決済サービスへのリクエスト後にタイムアウトが発生している
- その影響で注文処理が失敗している
- 最終的にAPIが500を返している

したがって、最初に調査するべきなのは決済サービスとの通信部分である。

さらに、決済が実際に完了していないかも確認する必要がある。

#### ⑦ 複数ログを使った調査で意識すること

複数のログを使って調査するときは、次のポイントを意識する。

- Request IDやTrace IDで関連ログを集める
- ログを時系列に並べて確認する
- 最初に発生したエラーを探す
- エラー同士のつながりを確認する
- 根本原因と二次的なエラーを区別する
- 表面化したエラーだけで原因を判断しない

複数のログを組み合わせることで、一つのログだけでは分からなかった処理の流れや根本原因を特定できる。

### 7.6 第7章まとめ

#### ① 実践的なログ調査の進め方

実際にエラーが発生した場合は、状況を整理してからログを確認する。

基本的な調査の流れは次のとおり。

1. エラーが発生した状況を確認する
2. 該当するエラーログを探す
3. エラーの前後にあるログを確認する
4. 関連するAPI・DB・外部サービスのログを調べる
5. 原因を切り分ける
6. 根本原因を特定する
7. 修正後に動作を確認する

エラーメッセージだけで判断せず、ログを組み合わせて原因を調査することが重要。

#### ② APIエラーの調査

APIエラーが発生した場合は、次の内容を確認する。

- HTTPメソッドやURL
- リクエストの内容
- HTTPステータスコード
- レスポンスの内容
- Request IDやTrace ID
- バックエンドの処理ログ

例えば、APIが500を返している場合でも、原因はDBや外部サービスにある可能性がある。

APIのログだけで判断せず、関連する処理のログも確認する。

#### ③ DBエラーの調査

DBエラーが発生した場合は、次の内容を確認する。

- DBへの接続状況
- SQLの内容や実行結果
- テーブル名やカラム名
- SQLの実行時間
- インデックスや検索条件
- トランザクションの状態

DBへの接続エラーなのか、SQLの実行エラーなのか、処理時間の問題なのかを切り分けることが重要。

#### ④ 外部サービス連携エラーの調査

外部サービスとの連携でエラーが発生した場合は、次の内容を確認する。

- リクエストの送信内容
- HTTPステータスコード
- 外部サービスの稼働状況
- ネットワークの状態
- タイムアウトの設定
- リトライの回数と結果

また、決済処理などでは、タイムアウトが発生しても実際には処理が成功している可能性がある。

二重実行を防ぐためにも、外部サービス側の処理結果を確認することが重要。

#### ⑤ 複数のログを使った原因特定

複数のサービスにまたがる処理では、Request IDやTrace IDを使って関連ログを集める。

ログを時系列に並べることで、処理の流れやエラーが発生した場所を確認できる。

特に意識するポイントは次のとおり。

- 最初に発生したエラーを探す
- エラー同士のつながりを確認する
- 根本原因と二次的なエラーを区別する
- 表面化したエラーだけで原因を判断しない

#### ⑥ 第7章で学んだこと

第7章では、実際のログを使ってエラーの原因を特定する方法を学んだ。

| 調査対象 | 主な確認内容 |
|---|---|
| API | リクエスト・レスポンス・HTTPステータスコード |
| DB | 接続状況・SQL・実行時間・トランザクション |
| 外部サービス | 通信状況・タイムアウト・リトライ |
| 複数のログ | Request ID・Trace ID・時系列 |

ログ調査では、一つのエラーだけを見て判断するのではなく、複数のログを組み合わせて処理全体を把握することが重要。

原因を正しく特定するためには、ログから事実を集め、順番に切り分けていく必要がある。
