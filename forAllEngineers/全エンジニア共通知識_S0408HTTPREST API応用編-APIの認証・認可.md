### 3.1 認証と認可の違い

#### ① 認証とは？

認証とは、アクセスしてきた人が誰なのかを確認すること。

例えば、Webサービスにログインするとき、メールアドレスやパスワードを使って本人かどうかを確認する。

これが認証（Authentication）。

#### ② 認可とは？

認可とは、認証された人が何を利用・操作できるのかを判断すること。

例えば、
- 一般ユーザー：自分のプロフィールを閲覧・編集できる
- 管理者：すべてのユーザー情報を管理できる

このように、ユーザーの権限に応じて利用できる機能を制限する仕組みが認可（Authorization）。

#### ③ 認証と認可の違い

| 項目 | 認証 | 認可 |
|---|---|---|
| 英語 | Authentication | Authorization |
| 目的 | 誰なのかを確認する | 何ができるのかを判断する |
| 例 | ログインする | 管理者機能を利用できるか判断する |

覚え方：
- 認証：あなたは誰？
- 認可：あなたは何ができる？

#### ④ 認証と認可の流れ

1. ユーザーがログインする
2. サーバーがIDやパスワードを確認する（認証）
3. ログインしたユーザーの権限を確認する（認可）
4. 管理者であればアクセスを許可する
5. 一般ユーザーであればアクセスを拒否する


### 3.2 Basic認証

#### ① Basic認証とは？

Basic認証とは、ユーザー名とパスワードを使って、APIやWebページへのアクセスを認証する仕組み。

サーバーは送られてきたユーザー名とパスワードを確認し、正しければアクセスを許可する。

#### ② Basic認証の仕組み

Basic認証では、ユーザー名とパスワードを「:」でつなぎ、Base64という方式でエンコードする。

例：

```text
taro:password123
```


### 3.3 トークン認証

#### ① トークン認証とは？

トークン認証とは、ユーザーの認証後に発行されたトークンを使って、APIへのアクセスを認証する仕組み。

トークンとは、本人確認に利用するための文字列。

ユーザーがログインすると、サーバーは認証情報を確認してトークンを発行する。

その後、クライアントはAPIにアクセスするとき、そのトークンを送信する。

#### ② トークン認証の仕組み

1. ユーザーがID・パスワードを使ってログインする
2. サーバーが認証情報を確認する
3. 認証に成功すると、サーバーがトークンを発行する
4. クライアントはトークンを保存する
5. APIにアクセスするとき、トークンを送信する
6. サーバーがトークンを確認し、アクセスを許可する

#### ③ トークンを使ったAPIリクエスト

トークンは、一般的にHTTPリクエストのAuthorizationヘッダーに設定して送信する。

例：

```http
GET /users/1 HTTP/1.1
Host: example.com
Authorization: Bearer abc123xyz
```

この例では、abc123xyzがトークン。

※Bearerという指定方法については、3.4で詳しく説明する。


#### ④ トークン認証のメリット

- ログイン時以外は、毎回パスワードを送る必要がない
- トークンを使ってAPIへのアクセスを管理できる
- トークンの有効期限を設定できる
- トークンを無効化することで、アクセスを制限できる（方式によって仕組みは異なる）

#### ⑤ トークン認証の注意点

トークンは、本人確認に使われる重要な情報。

第三者に盗まれると、本人になりすましてAPIを利用される危険性がある。

安全に利用するためには、次のような対策が必要。

- HTTPSを利用する
- トークンを安全に保存する
- 有効期限を設定する
- 不要になったトークンを無効化する


### 3.4 Bearer認証

#### ① Bearer認証とは？

Bearer認証（ベアラー認証）とは、トークンを持っている人（Bearer）が、そのトークンを提示することでAPIへのアクセスを認証する方式。

Bearerは「所持者」という意味。

トークンを持っていることを証明として、APIにアクセスする仕組み。

#### ② Bearer認証の仕組み

1. ユーザーがID・パスワードでログインする
2. サーバーが認証情報を確認する
3. 認証に成功すると、サーバーがアクセストークンを発行する
4. クライアントはAPIリクエストにトークンを付けて送信する
5. サーバーがトークンを検証する
6. 問題がなければAPIへのアクセスを許可する

#### ③ Authorizationヘッダーの書き方

Bearer認証では、HTTPリクエストのAuthorizationヘッダーに、Bearerとトークンを指定する。

例：

```http
GET /users/1 HTTP/1.1
Host: example.com
Authorization: Bearer abc123xyz
```

- Authorization：認証情報を指定するHTTPヘッダー
- Bearer：トークンを使う認証方式の指定
- abc123xyz：実際に送信するトークン

#### ④ Bearer認証のメリットと注意点

メリット：

- リクエストごとにID・パスワードを送る必要がない
- HTTPヘッダーにトークンを設定するだけで利用できる
- Webアプリやスマートフォンアプリなど、さまざまなクライアントで利用できる

注意点：

Bearerトークンは、第三者に盗まれると、その人がトークンを使ってAPIにアクセスできてしまう危険性がある。

そのため、次のような対策が必要。

- HTTPSを利用する
- トークンを安全に保存する
- トークンの有効期限を設定する
- 不要になったトークンを無効化する

#### ⑤ トークン認証との関係

- トークン認証：トークンを使って認証する仕組みの総称
- Bearer認証：トークンをBearer方式で送信する方法

トークン認証で利用される代表的な方式のひとつがBearer認証。


### 3.5 JWTとは

#### ① JWTとは？

JWT（JSON Web Token）とは、JSON形式の情報を安全にやり取りするためのトークン形式。

JWTは、ユーザーの情報や権限などをトークンの中に含めることができる。

例えば、ログインしたユーザーのIDや、有効期限などを含めることができる。

#### ② JWTの構造

JWTは、次の3つの部分で構成されている。

1. Header（ヘッダー）
2. Payload（ペイロード）
3. Signature（署名）

**Header（ヘッダー）**

トークンの種類や、署名に使用するアルゴリズムなどの情報を持つ部分。

**Payload（ペイロード）**

ユーザーIDや有効期限など、実際にやり取りしたい情報を持つ部分。

**Signature（署名）**

トークンが改ざんされていないかを検証するための部分。

#### ③ JWTの形式

JWTは、3つの部分をドット（.）でつないだ形式になっている。

例：

```text
xxxxx.yyyyy.zzzzz
```

- xxxxx：Header
- yyyyy：Payload
- zzzzz：Signature

#### ④ JWTの特徴

**メリット**

- ユーザー情報などをトークンに含められる
- サーバー側でトークンの内容を検証できる
- JSON形式なので、さまざまなプログラミング言語で扱いやすい

**注意点**

JWTのPayloadは、一般的な署名付きJWT（JWS）の場合、Base64URL形式でエンコードされているだけで、暗号化されているわけではない。

そのため、パスワードなどの秘密情報をPayloadに含めてはいけない。

また、署名によって改ざんを検知できても、トークンの盗難や不正利用を完全に防げるわけではない。

#### ⑤ JWTを使った認証の流れ

1. ユーザーがID・パスワードでログインする
2. サーバーが認証情報を確認する
3. 認証に成功すると、サーバーがJWTを発行する
4. クライアントがJWTを保存する
5. APIにアクセスするとき、JWTを送信する
6. サーバーがJWTの署名や有効期限などを検証する
7. 問題がなければAPIへのアクセスを許可する


### 3.6 OAuth 2.0とは

#### ① OAuth 2.0とは？

OAuth 2.0（オーオース2.0）とは、ユーザーのパスワードを共有せずに、別のサービスに対して必要な範囲のアクセス権限を与えるための仕組み。

例えば、あるWebサービスにGoogleアカウントを使ってアクセスする場面を考えてみる。

Googleのパスワードを利用先のサービスに教えることなく、Googleアカウントの情報や許可したデータへのアクセス権限を与えられる。

#### ② OAuth 2.0の仕組み

1. ユーザーが利用したいサービスにアクセスする
2. サービスが認可サーバー（例：Google）にアクセスを要求する
3. ユーザーがアクセス権限を許可する
4. 認可サーバーがアクセストークンを発行する
5. サービスがアクセストークンを使ってAPIにアクセスする
6. APIがトークンを確認し、許可された範囲のデータを返す

#### ③ アクセストークンとは？

アクセストークンとは、APIにアクセスするための権限を示すトークン。

OAuth 2.0では、このアクセストークンを使って、許可された範囲のデータにアクセスする。

例えば、

- プロフィール情報の閲覧だけ許可する
- カレンダー情報の閲覧だけ許可する
- ファイルの閲覧と編集を許可する

といったように、アクセスできる範囲を制限できる。

このアクセス範囲をスコープ（Scope）と呼ぶ。

#### ④ OAuth 2.0のメリット

- 利用先のサービスにパスワードを渡さずに済む
- 必要な範囲だけアクセス権限を与えられる
- アクセストークンを使ってAPIへのアクセスを管理できる
- トークンの有効期限や権限を管理できる

#### ⑤ OAuth 2.0と認証の関係

OAuth 2.0は、基本的には認証ではなく認可のための仕組み。

「このユーザーは誰なのか」を確認することよりも、「このサービスに何を許可するのか」を管理することが目的。

なお、Googleアカウントなどでログインする仕組みには、OAuth 2.0を利用したOpenID Connect（OIDC）が使われることがある。


### 3.7 第3章のまとめ

#### ① 認証と認可

- 認証（Authentication）：誰なのかを確認すること
- 認可（Authorization）：何ができるのかを判断すること

#### ② Basic認証

- ユーザー名とパスワードを使って認証する方式
- 認証情報をBase64でエンコードして送信する
- Base64は暗号化ではないため、HTTPSの利用が必要

#### ③ トークン認証

- 認証後に発行されたトークンを使ってAPIへのアクセスを認証する仕組み
- リクエストごとにパスワードを送る必要がない
- トークンの有効期限や保存方法に注意する必要がある

#### ④ Bearer認証

- トークンを持っていることを証明としてAPIにアクセスする方式
- AuthorizationヘッダーにBearerとトークンを指定する

例：

```http
Authorization: Bearer abc123xyz
```

#### ⑤ JWT

- JSON Web Tokenの略
- Header・Payload・Signatureの3つで構成される
- PayloadにはユーザーIDや有効期限などの情報を含められる
- 一般的な署名付きJWTのPayloadは暗号化されていない
- Signatureによって改ざんを検知できる

#### ⑥ OAuth 2.0

- 必要な範囲のアクセス権限を別のサービスに与えるための仕組み
- アクセストークンを使ってAPIにアクセスする
- アクセスできる範囲をスコープ（Scope）で制限できる
- 基本的には認証ではなく認可のための仕組み

#### ⑦ 第3章で覚えておきたいこと

| 用語 | 主な役割 |
|---|---|
| 認証 | 誰なのかを確認する |
| 認可 | 何ができるのかを判断する |
| Basic認証 | ID・パスワードで認証する |
| トークン認証 | トークンを使って認証する |
| Bearer認証 | Bearer方式でトークンを送信する |
| JWT | 情報を含められるトークン形式 |
| OAuth 2.0 | アクセス権限を委任する仕組み |
