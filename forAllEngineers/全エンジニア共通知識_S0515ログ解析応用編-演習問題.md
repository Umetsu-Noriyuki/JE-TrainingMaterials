## 第1問：大規模システムのログ調査

### 問題

ある大規模システムで、複数のサービスからエラーログが出力されている。

しかし、サービスごとにログの形式や項目名が異なっており、障害発生時に関連するログを検索することが難しい状態になっている。

この問題を改善する方法として、最も適切なものはどれか。

### 選択肢

① 各サービスで自由にログを出力できるようにし、ログの形式は統一しない

② エラーログだけを保存し、INFOやWARNなどのログはすべて削除する

③ ログの出力形式や項目名、ログレベルなどのルールを統一し、検索・分析しやすい構造化ログを導入する

④ ログの保存期間を短くすれば、障害調査が簡単になる

### 正解

**③ ログの出力形式や項目名、ログレベルなどのルールを統一し、検索・分析しやすい構造化ログを導入する**

### 解説

大規模システムでは、多くのサービスから大量のログが出力される。

サービスごとにログの形式や項目名が異なると、関連するログを横断的に検索・分析することが難しくなる。

そのため、ログの出力形式や項目名、ログレベルなどのルールを統一することが重要。

また、構造化ログを導入することで、ログの検索・集計・分析がしやすくなる。

**重要ポイント：**
ログは出力するだけでなく、後から効率よく調査・分析できるように設計する。

## 第2問：分散システムの障害調査

### 問題

ある注文システムで、注文処理が失敗する障害が発生した。

Trace IDを使ってログを調査したところ、次の情報が確認できた。

| サービス | ログ内容 | 結果 |
|---|---|---|
| API Gateway | 注文リクエスト受信 | 成功 |
| Order Service | 注文処理開始 | 成功 |
| Payment Service | 決済API呼び出し | タイムアウト |
| Order Service | 注文処理失敗 | エラー |
| API Gateway | HTTP 500 | エラー |

この場合、最も適切な調査方法はどれか。

### 選択肢

① API GatewayのHTTP 500だけを確認し、調査を終了する

② Payment Serviceと決済APIの通信状況を調査し、決済が実際に完了していないかも確認する

③ Order Serviceのログをすべて削除して、注文処理を再実行する

④ API Gatewayを再起動すれば、必ず問題が解決すると判断する

### 正解

**② Payment Serviceと決済APIの通信状況を調査し、決済が実際に完了していないかも確認する**

### 解説

Trace IDを使って複数サービスのログを追跡することで、障害発生までの処理の流れを確認できる。

今回のケースでは、Payment Serviceで決済APIのタイムアウトが発生し、その後Order ServiceとAPI Gatewayでもエラーが記録されている。

そのため、Payment Serviceと決済APIの通信状況を重点的に調査する必要がある。

また、タイムアウトが発生していても、実際には決済が完了している可能性がある。

その状態で再実行すると、二重決済につながる可能性があるため注意する。

**重要ポイント：**
Trace IDで処理全体を追跡し、エラーが発生した箇所だけでなく、その前後の処理も確認する。

## 第3問：パフォーマンス低下の原因分析

### 問題

あるAPIのレスポンスが遅くなったため、処理時間を調査した。

| 処理 | 通常時 | 障害発生時 |
|---|---:|---:|
| API受付 | 100ms | 100ms |
| アプリ処理 | 200ms | 200ms |
| DB検索 | 300ms | 400ms |
| 外部API通信 | 200ms | 3000ms |
| 合計 | 800ms | 3700ms |

この結果から、最も適切な調査対象はどれか。

### 選択肢

① API受付処理のログ出力方法

② DBのテーブル名やカラム名

③ アプリケーションの画面デザイン

④ 外部APIの応答時間や通信状況、タイムアウト・リトライの発生状況

### 正解

**④ 外部APIの応答時間や通信状況、タイムアウト・リトライの発生状況**

### 解説

通常時は外部API通信に200msかかっていたが、障害発生時には3000msまで増加している。

API全体の処理時間3700msのうち、3000msを外部API通信が占めている。

そのため、外部APIとの通信がボトルネックになっている可能性が高い。

外部APIの応答時間や通信状況、タイムアウト・リトライの発生状況などを詳しく調査する必要がある。

**重要ポイント：**
処理ごとの所要時間を比較し、システム全体の処理速度を低下させているボトルネックを特定する。

## 第4問：本番障害の初動対応

### 問題

本番環境で障害が発生し、多くのユーザーが注文できない状態になった。

調査には時間がかかることが予想されるが、ユーザーへの影響をできるだけ早く抑える必要がある。

この場合の初動対応として、最も適切なものはどれか。

### 選択肢

① まず影響範囲と障害状況を確認し、必要に応じて一時的な負荷軽減や機能制限などを行いながら、並行して原因調査を進める

② 根本原因が完全に分かるまで、ユーザーへの対応や復旧作業は行わない

③ 原因が分からないため、すべてのDBデータを削除して初期化する

④ 障害の発生を隠すため、エラーログの出力を停止する

### 正解

**① まず影響範囲と障害状況を確認し、必要に応じて一時的な負荷軽減や機能制限などを行いながら、並行して原因調査を進める**

### 解説

本番環境で障害が発生した場合、最優先で考えるべきことはユーザーへの影響を抑えること。

根本原因の特定に時間がかかる場合でも、一時的な負荷軽減や機能制限などによって、サービスへの影響を小さくできる可能性がある。

そのため、初動対応と原因調査を並行して進めることが重要。

**重要ポイント：**
本番障害では、原因調査だけでなく、ユーザーへの影響を最小限に抑え、早期にサービスを復旧させることが重要。

## 第5問：複合障害の総合分析

### 問題

あるECサイトで、注文APIの遅延とHTTP 500エラーが増加した。

調査した結果、次の情報が確認できた。

**APIログ**

```text
11:00:01 INFO  /orders requestId=req-001
11:00:05 ERROR /orders HTTP 500
```

**アプリケーションログ**

```text
11:00:02 INFO  DB接続取得開始
11:00:04 ERROR DB connection timeout
11:00:04 ERROR 注文登録失敗
```

**DBメトリクス**

| 項目 | 通常時 | 障害発生時 |
|---|---:|---:|
| CPU使用率 | 30% | 80% |
| DB接続数 | 20 | 100 |
| 最大接続数 | 100 | 100 |

さらに調査したところ、アクセス数は通常時とほぼ変わらない一方、アプリケーション側でDB接続が適切に解放されていない可能性が見つかった。

この状況で最も適切な対応はどれか。

### 選択肢

① DBの最大接続数を無制限に変更し、原因調査は行わない

② HTTP 500が出ているAPIだけを修正し、DB側は確認しない

③ DB接続の解放処理や接続プールの設定を調査・修正し、接続数やAPIのレスポンスが正常に戻ったか確認したうえで再発防止策を検討する

④ エラーログを削除し、障害が解決したと判断する

### 正解

**③ DB接続の解放処理や接続プールの設定を調査・修正し、接続数やAPIのレスポンスが正常に戻ったか確認したうえで再発防止策を検討する**

### 解説

アクセス数が通常時とほぼ変わらないにもかかわらず、DB接続数が最大接続数の100に達している。

また、アプリケーション側でDB接続が適切に解放されていない可能性が見つかっている。

そのため、DB接続の解放処理や接続プールの設定を調査する必要がある。

修正後は、DB接続数やAPIのレスポンスタイム、エラー率などを確認し、正常な状態に戻ったことを検証する。

さらに、接続数の監視やアラート設定などを見直し、再発防止につなげる。

**重要ポイント：**
目に見えているエラーだけでなく、根本原因を特定し、復旧確認と再発防止まで行うことが重要。
