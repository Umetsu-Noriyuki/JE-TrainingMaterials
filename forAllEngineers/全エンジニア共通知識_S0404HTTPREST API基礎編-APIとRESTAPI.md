# 4. APIとREST API

## 4.1 APIとは

APIとは、**Application Programming Interface**の略です。

簡単にいうと、**異なるプログラム同士がやり取りするための窓口**です。

例えば、Webサイトからユーザー情報を取得したい場合、Webサイトが直接データベースにアクセスするのではなく、APIを通してサーバーに「ユーザー情報をください」と要求します。

イメージすると、次のようになります。

```text
[クライアント]
     ↓
 「ユーザー情報をください」
     ↓
   [API]
     ↓
   [サーバー]
     ↓
 「ユーザー情報です」
     ↓
[クライアント]
```

APIは、プログラム同士が決められた方法でデータをやり取りするための仕組みです。

---

## 4.2 HTTP APIとは

APIにはさまざまな種類があります。

その中でも、**HTTPを使って通信するAPI**をHTTP APIと呼びます。

これまで学習してきたHTTPの仕組みを使って、クライアントとサーバーの間でデータをやり取りします。

```text
クライアント
    ↓ HTTPリクエスト
   API
    ↓
 サーバー
    ↓ HTTPレスポンス
クライアント
```

例えば、ユーザー情報を取得するAPIがあるとします。

```http
GET /users/123
```

サーバーから次のようなレスポンスが返ってくるとします。

```json
{
  "id": 123,
  "name": "山田太郎"
}
```

このように、HTTPのリクエストとレスポンスを利用してデータをやり取りするAPIをHTTP APIと呼びます。

---

## 4.3 REST APIとは

REST APIとは、**RESTの考え方に沿って設計されたHTTP API**です。

RESTは、**Representational State Transfer**の略です。

RESTでは、データを「リソース」として考え、HTTPの仕組みを利用してリソースを操作します。

例えば、ユーザーをリソースとして考える場合、

```text
/users
```

がユーザーというリソースを表します。

特定のユーザーを表す場合は、

```text
/users/123
```

のように表します。

---

## 4.4 リソースとは

REST APIでは、操作する対象を**リソース**として考えます。

例えば、次のようなデータがあるとします。

* ユーザー
* 商品
* 注文
* 記事

これらをそれぞれリソースとして扱います。

URLでは、リソースを名詞として表すことが一般的です。

```text
/users
/products
/orders
/articles
```

特定のリソースを指定する場合は、IDなどを使用します。

```text
/users/123
/products/456
/orders/789
```

このように、URLから「何を操作するのか」が分かるように設計します。

---

## 4.5 HTTPメソッドとREST API

REST APIでは、HTTPメソッドを使ってリソースに対する操作を表します。

代表的なHTTPメソッドは次のとおりです。

| メソッド   | 主な用途        |
| ------ | ----------- |
| GET    | データを取得する    |
| POST   | データを新しく作成する |
| PUT    | データを置き換える   |
| PATCH  | データの一部を更新する |
| DELETE | データを削除する    |

例えば、ユーザーを操作するAPIの場合、次のようになります。

### ユーザー一覧を取得する

```http
GET /users
```

### ユーザーを1件取得する

```http
GET /users/123
```

### ユーザーを新しく作成する

```http
POST /users
```

### ユーザーを更新する

```http
PATCH /users/123
```

### ユーザーを削除する

```http
DELETE /users/123
```

同じ `/users` というリソースに対して、HTTPメソッドを使い分けることで操作の意味を表現できます。

---

## 4.6 REST APIのURL設計

REST APIでは、URLを**リソースを表す名前**として設計することが一般的です。

例えば、ユーザーを取得する場合、

```http
GET /users/123
```

とします。

一方で、

```http
GET /getUser?id=123
```

のように、URLに「get」という操作名を含める設計は、RESTの考え方とは異なります。

REST APIでは、

```text
URL      → 何を操作するか
HTTPメソッド → どう操作するか
```

という考え方をします。

例えば、

```http
GET /users/123
```

なら、

```text
/users/123 → ユーザー123というリソース
GET        → 取得する
```

となります。

---

## 4.7 REST APIの通信例

ここまでの内容を使って、実際の通信を見てみましょう。

ユーザーID「123」の情報を取得する場合を考えます。

### リクエスト

```http
GET /users/123 HTTP/1.1
Host: example.com
Accept: application/json
```

サーバーはリクエストを受け取り、ユーザー情報を返します。

### レスポンス

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "id": 123,
  "name": "山田太郎",
  "email": "yamada@example.com"
}
```

この通信では、

```text
GET /users/123
       ↓
ユーザー123を取得
       ↓
HTTP 200 OK
       ↓
JSON形式でユーザー情報を返す
```

という流れになっています。

---

## 4.8 HTTP APIとREST APIの違い

HTTP APIとREST APIは似ていますが、意味する範囲が異なります。

### HTTP API

HTTPを使って通信するAPI全般を指します。

```text
HTTP API
├─ REST API
├─ REST以外の設計のAPI
└─ その他のHTTPベースのAPI
```

つまり、

> **REST APIはHTTP APIの一種**

と考えると分かりやすいです。

ただし、実際の開発現場では「API」とだけ呼んでいる場合でも、HTTP APIやREST APIを指していることがあります。

そのため、APIの仕様を確認するときは、どのような通信方式・設計になっているのかを確認することが重要です。

---

## 4.9 API通信の全体像

これまで学習した内容をまとめると、API通信は次のような流れになります。

```text
クライアント
    │
    │ HTTPリクエスト
    │ GET /users/123
    ↓
   API
    │
    ↓
  サーバー
    │
    │ HTTPレスポンス
    │ 200 OK
    │ JSON
    ↓
クライアント
```

REST APIの場合は、

```text
URL
  ↓
リソースを表す

HTTPメソッド
  ↓
リソースに対する操作を表す

HTTPステータスコード
  ↓
処理結果を表す

JSON
  ↓
データを表す
```

という形で、それぞれの役割を分けて考えることができます。

---

## 4.10 4章のまとめ

この章では、APIとREST APIについて学びました。

重要なポイントは次のとおりです。

* **API**は、プログラム同士がやり取りするための窓口
* **HTTP API**は、HTTPを使って通信するAPI
* **REST API**は、RESTの考え方に沿って設計されたHTTP API
* REST APIでは、データを**リソース**として考える
* URLでは、操作対象となるリソースを表す
* HTTPメソッドによって、取得・作成・更新・削除などの操作を表す
* REST APIでは「URLで何を操作するか」「HTTPメソッドでどう操作するか」を表現する
* **REST APIはHTTP APIの一種**

ここまで理解できれば、API通信の基本的な構造を理解したことになります。
