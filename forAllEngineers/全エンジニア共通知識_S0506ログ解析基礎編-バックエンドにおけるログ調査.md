### 6.1 バックエンドの処理とログ

#### ① バックエンドとは？

バックエンドとは、ユーザーから直接見えない場所で、アプリケーションのデータ処理やビジネスロジックなどを実行する仕組みのこと。

例えば、ユーザーがアプリでユーザー情報を表示するとき、バックエンドでは次のような処理が行われる。

1. アプリからAPIリクエストを受け取る
2. リクエストの内容を確認する
3. データベースから必要な情報を取得する
4. 取得したデータを加工する
5. APIレスポンスとしてアプリに返す

このように、バックエンドはアプリとデータベースなどの間に入り、さまざまな処理を担当する。

#### ② バックエンドでログを出力する理由

バックエンドでは、画面から直接確認できない処理が多いため、ログが重要な役割を持つ。

主な目的は次のとおり。

- 処理が正常に実行されたか確認する
- エラーが発生した箇所を特定する
- APIの処理時間を確認する
- DBや外部サービスとの通信状況を確認する
- 不正なアクセスや不審な操作を調査する

例えば、アプリに「データを取得できませんでした」と表示された場合、画面だけでは原因を特定できない。

バックエンドのログを確認することで、API処理・DB接続・データ変換など、どの段階で問題が発生したのか調査できる。

#### ③ バックエンドで記録する主なログ

バックエンドでは、処理の種類に応じてさまざまな情報を記録する。

| ログの種類 | 記録する内容 |
|---|---|
| リクエストログ | リクエスト日時、HTTPメソッド、URL、ステータスコード |
| 処理ログ | 処理の開始・終了、実行した処理の内容 |
| DBログ | SQL実行結果、DB接続エラー、処理時間 |
| エラーログ | 例外の内容、エラー発生箇所、スタックトレース |
| 外部連携ログ | 外部APIへのリクエスト結果、通信時間、エラー内容 |

これらのログを組み合わせることで、バックエンド内部の処理状況を把握しやすくなる。

#### ④ APIリクエストからレスポンスまでのログ

バックエンドでは、APIのリクエストを受け取ってからレスポンスを返すまでの流れを記録すると、調査に役立つ。

例えば、ユーザー情報を取得するAPIでは次のようなログが考えられる。

```text
2026-11-05 10:00:00 INFO UserController
GET /api/users/123 リクエスト受信

2026-11-05 10:00:01 INFO UserService
ユーザー情報の取得処理を開始

2026-11-05 10:00:02 INFO UserRepository
DBからユーザー情報を取得

2026-11-05 10:00:03 INFO UserController
HTTP 200 レスポンス返却
```

このログから、リクエストを受け取ってからDB検索を行い、正常にレスポンスを返したことが分かる。

一方、途中でERRORログが出力されていれば、その前後のログを確認することで問題が発生した箇所を絞り込める。

#### ⑤ バックエンドのログ調査で意識すること

バックエンドのログを調査するときは、次のポイントを意識する。

- リクエストからレスポンスまでの処理の流れを確認する
- ERRORログだけでなく、その前後のログも確認する
- DBや外部サービスのログも関連付けて確認する
- Request IDやTrace IDを使って関連するログを探す
- パスワードやアクセストークンなどの機密情報を記録しない
バックエンドでは複数の処理やサービスが連携するため、一つのログだけで判断せず、関連するログを組み合わせて調査することが重要。

### 6.2 API処理のログ調査

#### ① API処理のログ調査とは？

API処理のログ調査とは、APIのリクエストを受け取ってからレスポンスを返すまでの処理状況を、ログを使って確認すること。

APIでエラーが発生した場合、次のような原因が考えられる。

- リクエストの内容が正しくない
- 認証や認可に失敗している
- バックエンドの処理でエラーが発生している
- DBからデータを取得できない
- レスポンスの生成に失敗している

ログを確認することで、どの段階で問題が発生したのかを特定しやすくなる。

#### ② リクエストログを確認する

APIの調査では、まずリクエストログを確認する。

リクエストログには、一般的に次のような情報が記録される。

| 項目 | 内容 |
|---|---|
| 日時 | リクエストを受け取った日時 |
| HTTPメソッド | GET、POST、PUT、DELETEなど |
| URL | 呼び出されたAPIのURL |
| ステータスコード | APIの処理結果 |
| 処理時間 | リクエストからレスポンスまでの時間 |
| Request ID | 個々のリクエストを識別するID |

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 INFO ApiAccess
GET /api/users/123
Status: 200
Duration: 120ms
RequestId: req-001
```

このログから、ユーザー情報取得APIがHTTP 200で正常に処理され、120ミリ秒でレスポンスを返したことが分かる。

なお、リクエストログには認証情報やパスワードなどの機密情報を記録しないようにする。

#### ③ HTTPステータスコードを確認する

APIの処理結果を調査するときは、HTTPステータスコードも重要な手掛かりになる。

| ステータスコード | 主な意味 | 調査する内容 |
|---|---|---|
| 200 OK | 正常終了 | 期待したデータが返っているか |
| 201 Created | リソース作成成功 | データが正しく登録されたか |
| 400 Bad Request | リクエスト不正 | 入力値やリクエスト形式 |
| 401 Unauthorized | 認証失敗 | 認証情報やトークン |
| 403 Forbidden | アクセス拒否 | ユーザーの権限 |
| 404 Not Found | 対象が存在しない | URLや対象データ |
| 500 Internal Server Error | サーバー内部エラー | バックエンドの処理や例外 |
| 503 Service Unavailable | サービス利用不可 | サーバーの稼働状況や負荷 |

例えば、HTTP 500が返っている場合は、バックエンド側のログを確認して、どの処理で例外が発生したのか調査する。

ただし、ステータスコードだけで原因を断定せず、リクエスト内容や関連ログも確認することが大切。

#### ④ APIの処理時間を確認する

APIのログには、処理にかかった時間を記録することもある。

処理時間を確認することで、APIの動作が遅くなっている原因を調査できる。

例えば、次のようなログがある。

```text
INFO UserController
GET /api/users/123
Duration: 1500ms
```

この場合、APIの処理に1,500ミリ秒（1.5秒）かかっていることが分かる。

処理時間が長い場合は、次のような原因が考えられる。

- DBのSQL実行に時間がかかっている
- 外部APIからのレスポンスが遅い
- バックエンド内部の処理に時間がかかっている
- サーバーの負荷が高くなっている

API全体の処理時間だけでなく、DB検索や外部API通信など、処理ごとの時間も記録すると原因を絞り込みやすくなる。

#### ⑤ Request IDを使って関連ログを調査する

APIの処理では、Request IDを使って関連するログを検索すると便利。

Request IDとは、個々のリクエストを識別するためのIDのこと。

例えば、次のようなログがある。

```text
INFO ApiController
Request received
RequestId: req-001

INFO UserService
User lookup started
RequestId: req-001

ERROR UserRepository
Database query failed
RequestId: req-001
```

この例では、すべてのログに同じRequest IDが記録されている。

そのため、req-001で検索すると、同じリクエストに関係するログをまとめて確認できる。

これにより、APIの受付からDB処理まで、どの段階で問題が発生したのかを追跡しやすくなる。

#### ⑥ API処理のログ調査で意識すること

APIのログを調査するときは、次のポイントを意識する。

- リクエストの日時・URL・HTTPメソッドを確認する
- HTTPステータスコードを確認する
- APIの処理時間を確認する
- ERRORログとその前後のログを確認する
- Request IDを使って関連ログを検索する
- 機密情報をログに出力しない
APIのログを確認することで、リクエストの受付からレスポンスまでのどこに問題があるのかを把握しやすくなる。

### 6.3 データベース処理のログ調査

#### ① データベース処理のログ調査とは？

データベース処理のログ調査とは、DBへの接続やSQLの実行、データの登録・更新・取得などが正常に行われているか、ログを使って確認すること。

バックエンドでは、ユーザー情報や試合記録など、さまざまなデータをDBに保存・取得する。

そのため、DB処理に問題が発生すると、アプリ全体の機能に影響する可能性がある。

例えば、ユーザー情報を取得できない場合、次のような原因が考えられる。

- DBに接続できていない
- SQLの構文や条件が間違っている
- 対象のデータが存在しない
- DBの処理に時間がかかっている
- DBへのアクセス権限が不足している

ログを確認することで、どのような問題が発生しているのか調査できる。

#### ② DB接続に関するログを確認する

まずは、バックエンドからDBへ正常に接続できているか確認する。

主な確認ポイントは次のとおり。

- DBサーバーが起動しているか
- 接続先のホスト名やポート番号が正しいか
- DB名やユーザー名などの設定が正しいか
- 認証情報に問題がないか
- 接続数の上限に達していないか

例えば、次のようなログが出力されていた場合を考える。

```text
2026-11-05 10:00:00 ERROR DatabaseConnection
Connection refused
```

Connection refused は、接続先から接続を拒否されたことを示すエラー。

DBサーバーが起動していない、接続先の設定が間違っているなどの可能性がある。

#### ③ SQLの実行ログを確認する

DBでは、SQLを使ってデータの取得・登録・更新・削除を行う。

そのため、SQLの実行結果や処理時間を確認することも重要。

例えば、次のようなSQLを実行したとする。

```spl
SELECT * FROM players WHERE id = 1;
```

このSQLは、IDが1のプレーヤー情報を取得する処理。

調査では、次のような内容を確認する。

- SQLが正常に実行されたか
- SQLの構文に間違いがないか
- WHERE句の条件が正しいか
- 対象のデータが存在しているか
- 実行に時間がかかっていないか

SQLが正常に実行されても、条件に一致するデータが存在しなければ、期待した結果は取得できない。

また、本番環境ではSQLログに個人情報や機密情報が含まれないよう注意する。

#### ④ DB処理の時間を確認する

SQLの実行に時間がかかっている場合、アプリ全体のレスポンスが遅くなる可能性がある。

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 WARN DatabaseQuery
Query duration: 3500ms
```

この場合、SQLの実行に3,500ミリ秒（3.5秒）かかっていることが分かる。

処理時間が長い場合は、次のような原因が考えられる。

- SQLの検索条件が適切でない
- インデックスが不足している
- 大量のデータを取得している
- DBサーバーの負荷が高い
- 他の処理によってDBがロックされている

特に、インデックスが適切に設定されていない場合、検索対象のデータを大量に調べる必要があり、処理が遅くなることがある。

#### ⑤ トランザクションに関するログを確認する

トランザクションとは、複数のDB操作を一つのまとまりとして扱う仕組みのこと。

例えば、注文データの登録と在庫数の更新を行う場合、両方の処理をまとめて実行することがある。

トランザクションでは、次のような操作が重要になる。

| 操作 | 意味 |
|---|---|
| BEGIN | トランザクション開始 |
| COMMIT | 変更内容を確定する |
| ROLLBACK | 変更内容を取り消す |

例えば、注文データの登録に成功した後、在庫数の更新に失敗した場合、ROLLBACKによって注文データの登録も取り消すことができる。

ログを確認することで、トランザクションが正常に完了したのか、途中で失敗して取り消されたのかを調査できる。

#### ⑥ DB処理のログ調査で意識すること

DBのログを調査するときは、次のポイントを意識する。

- DBへの接続が正常に行われているか
- SQLが正常に実行されているか
- 検索条件や対象データに問題がないか
- SQLの実行時間が長くなっていないか
- トランザクションが正常に完了しているか
- DBのログとバックエンドのログを関連付けて確認する

DB処理のログを調査することで、データの取得・登録・更新などが正常に行われているか確認できる。

バックエンドのログとDBのログを組み合わせることで、エラーの発生箇所をより正確に特定しやすくなる。

### 6.4 外部サービスとの連携ログ

#### ① 外部サービスとの連携とは？

外部サービスとの連携とは、自分たちのアプリやバックエンドから、別のシステムが提供する機能やデータを利用すること。

例えば、次のようなものがある。

- 決済サービスとの連携
- メール送信サービスとの連携
- 外部の認証サービスとの連携
- 天気情報や地図情報を提供するAPIとの連携
- 他社システムとのデータ連携

バックエンドでは、HTTP通信などを使って外部サービスにリクエストを送り、その結果を受け取る。

このとき、通信に失敗したり、外部サービス側でエラーが発生したりすることがある。

そのため、外部サービスとの通信内容や結果をログで確認できるようにしておくことが重要。

#### ② 外部サービスとの通信ログを確認する

外部サービスとの通信で問題が発生した場合、まずはリクエストとレスポンスに関するログを確認する。

主な確認項目は次のとおり。

| 確認項目 | 内容 |
|---|---|
| リクエスト先 | どの外部サービスに通信したか |
| HTTPメソッド | GET、POSTなど、どの方法で通信したか |
| ステータスコード | 通信結果が成功か失敗か |
| 通信時間 | レスポンスが返るまでにかかった時間 |
| エラー内容 | どのような理由で失敗したか |
| Request ID | 関連するログを特定するための識別子 |

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 ERROR PaymentService
External API request failed
Status: 500
Error: Internal Server Error
Duration: 2500ms
```

このログから、決済サービスへのリクエストが失敗し、外部サービス側から500エラーが返されたことが分かる。

ただし、500エラーが発生したからといって、必ず外部サービスだけに原因があるとは限らない。

リクエスト内容や自分たちのバックエンド側の処理にも問題がないか確認する必要がある。

#### ③ タイムアウトに関するログを確認する

外部サービスとの通信では、一定時間待ってもレスポンスが返ってこない場合がある。

これをタイムアウトという。

例えば、次のようなログがある。

```text
2026-11-05 10:00:00 ERROR MailService
Connection timeout
Timeout: 5000ms
```

この場合、メール送信サービスとの通信が5秒以内に完了せず、タイムアウトしたことが分かる。

主な原因として、次のようなものが考えられる。

- 外部サービスの応答が遅い
- ネットワークに問題がある
- 外部サービスにアクセスが集中している
- タイムアウト時間の設定が短すぎる

調査するときは、外部サービスの稼働状況や通信時間、タイムアウトの設定などを確認する。

#### ④ リトライに関するログを確認する

リトライとは、通信や処理に失敗したときに、もう一度同じ処理を実行する仕組みのこと。

例えば、一時的なネットワーク障害によって通信に失敗しても、再試行することで正常に完了する場合がある。

次のようなログが出力されていたとする。

```text
2026-11-05 10:00:00 WARN ApiClient
Request failed. Retrying... (1/3)

2026-11-05 10:00:02 WARN ApiClient
Request failed. Retrying... (2/3)

2026-11-05 10:00:04 INFO ApiClient
Request succeeded after retry
```

このログから、最初の2回は失敗したものの、3回目の通信で成功したことが分かる。

リトライに関するログでは、次の点を確認する。

- 何回リトライしたか
- どのタイミングでリトライしたか
- 最終的に成功したか
- リトライ回数の上限に達していないか

ただし、すべての処理を無条件にリトライしてよいわけではない。

例えば、決済処理などを安易に再実行すると、二重決済が発生する可能性がある。

そのため、処理の性質に応じてリトライの可否を判断する必要がある。

#### ⑤ 外部サービス側と自分たちのシステムを切り分ける

外部サービスとの連携でエラーが発生した場合、原因がどちらにあるのか切り分けることが重要。

例えば、次のような観点で確認する。

| 調査対象 | 確認する内容 |
|---|---|
| 自分たちのシステム | リクエスト内容や送信処理に問題がないか |
| ネットワーク | 通信が正常に行われているか |
| 外部サービス | サービス側で障害が発生していないか |
| 認証情報 | APIキーやトークンなどに問題がないか |
| 設定 | 接続先URLやタイムアウト時間が正しいか |

例えば、外部サービスから401エラーが返された場合、認証情報の設定や有効期限などを確認する。

一方、503エラーの場合は、外部サービスのメンテナンスや一時的な負荷などが考えられる。

エラーの種類だけで原因を決めつけず、関連するログや外部サービスの稼働状況も確認することが大切。

#### ⑥ 外部サービスとの連携ログで注意すること

外部サービスとの通信ログを出力するときは、次の点に注意する。

- APIキーやアクセストークンを出力しない
- パスワードなどの認証情報を出力しない
- 個人情報や機密情報を必要以上に出力しない
- リクエストとレスポンスを追跡できる情報を残す
- 通信時間やエラー内容を記録する
- リトライの回数や最終結果を記録する

特に、リクエストやレスポンスの内容をそのままログに出力すると、機密情報が漏れる可能性がある。

必要な情報だけを記録し、機密情報はマスキングするなどの対策が必要。

外部サービスとの連携ログを確認することで、自分たちのシステム・ネットワーク・外部サービスのどこに問題があるのか、原因を切り分けやすくなる。

### 6.5 バックエンドの例外処理とログ

#### ① 例外処理とは？

例外処理とは、プログラムの実行中に予期しないエラーが発生した場合に、そのエラーを受け取り、適切に対応する仕組みのこと。

バックエンドでは、次のような場面で例外が発生する可能性がある。

- DBへの接続に失敗した
- SQLの実行中にエラーが発生した
- 外部APIとの通信に失敗した
- JSONの解析に失敗した
- 必要なデータが存在しなかった
- 想定していない値が渡された

例外処理を適切に実装しておくことで、エラーが発生してもプログラムが突然終了することを防ぎ、利用者に適切なエラーを返せるようになる。

#### ② try-catchによる例外処理

Dartでは、`try-catch`を使って例外を処理できる。

- `try`：例外が発生する可能性のある処理を書く
- `catch`：例外が発生した場合の処理を書く
- `finally`：例外の有無にかかわらず実行したい処理を書く

例えば、次のように記述する。

```dart
try {
  final user = await userRepository.fetchUser();

  print('ユーザー情報を取得しました');
} catch (e, stackTrace) {
  print('ユーザー情報の取得に失敗しました');
  print(e);
  print(stackTrace);
} finally {
  print('処理が終了しました');
}
```

このコードでは、ユーザー情報の取得中に例外が発生すると、`catch`の処理が実行される。

また、`catch (e, stackTrace)`とすることで、例外の内容とスタックトレースを取得できる。

#### ③ 例外発生時にログを出力する

例外が発生した場合、エラーの内容をログに記録しておくことが重要。

ログを出力しておけば、後からエラーが発生した原因や場所を調査しやすくなる。

例えば、次のように記述する。

```dart
import 'dart:developer' as developer;

try {
  await userRepository.fetchUser();
} catch (e, stackTrace) {
  developer.log(
    'ユーザー情報の取得に失敗しました',
    name: 'UserService',
    level: 1000,
    error: e,
    stackTrace: stackTrace,
  );
}
```

このログでは、次の情報を記録している。

| 項目 | 内容 |
|---|---|
| メッセージ | ユーザー情報の取得に失敗したこと |
| name | エラーが発生した処理やクラス |
| level | ログの重要度 |
| error | 発生した例外の内容 |
| stackTrace | エラーが発生するまでの呼び出し経路 |

特に、例外の内容とスタックトレースを記録しておくことで、エラーの原因を特定しやすくなる。

#### ④ 例外を握りつぶさない

例外を握りつぶすとは、例外が発生したにもかかわらず、何も記録せずに無視してしまうこと。

例えば、次のようなコードは問題がある。

```dart
try {
  await userRepository.fetchUser();
} catch (e) {
  // 何も処理しない
}
```

このコードでは、例外が発生してもログが出力されず、エラーの原因を調査することが難しくなる。

また、呼び出し元にもエラーが伝わらないため、処理が失敗したことに気づけない可能性がある。

例外を捕まえた場合は、次のような対応を検討する。

- エラー内容をログに記録する
- 必要に応じて呼び出し元に例外を再送出する
- 利用者に適切なエラーメッセージを返す
- 復旧できる場合はリトライなどを行う

#### ⑤ 例外を再送出する

例外を再送出するとは、catchで受け取った例外を、さらに呼び出し元へ伝えること。

Dartでは、`rethrow`を使うことで、捕まえた例外を再送出できる。

```dart
try {
  await userRepository.fetchUser();
} catch (e, stackTrace) {
  developer.log(
    'ユーザー情報の取得に失敗しました',
    name: 'UserService',
    level: 1000,
    error: e,
    stackTrace: stackTrace,
  );

  rethrow;
}
```

この場合、ログを出力した後に例外を再送出する。

呼び出し元でも例外を受け取り、必要な処理を行えるようになる。

ただし、同じ例外を複数の場所でログ出力すると、同じエラーが重複して記録される可能性がある。

そのため、どの階層でログを記録するのか、役割を決めておくことが大切。

#### ⑥ 利用者向けのエラーと内部ログを分ける

例外が発生した場合、利用者に返すエラーメッセージと、開発者が調査するためのログは分けて考える必要がある。

例えば、DB接続エラーが発生した場合を考える。

| 種類 | 内容 |
|---|---|
| 利用者向け | データの取得に失敗しました。時間をおいて再度お試しください。 |
| 内部ログ | DatabaseConnectionException、接続先、発生箇所、スタックトレースなど |

内部ログには、原因を調査するための詳しい情報を記録する。

一方、利用者向けのメッセージには、DBの接続情報や内部の構造などを表示しないようにする。

内部情報をそのまま利用者に返してしまうと、システムの構造や機密情報が漏れる可能性があるため注意が必要。

#### ⑦ 例外処理とログ出力で意識すること

バックエンドで例外処理を実装するときは、次のポイントを意識する。

- 例外を適切にcatchする
- エラー内容をログに記録する
- 必要に応じてスタックトレースを記録する
- 例外を何もせずに握りつぶさない
- 必要に応じて例外を再送出する
- 利用者向けのメッセージと内部ログを分ける
- パスワードやトークンなどの機密情報をログに出力しない
- 同じ例外を何度も記録しないようにする

例外処理とログ出力を適切に組み合わせることで、エラー発生時の影響を抑えながら、原因を調査しやすいバックエンドを実現できる。

### 6.6 第6章まとめ

#### ① バックエンドの処理とログ

バックエンドとは、アプリケーションの裏側で動作するサーバー側の処理のこと。

バックエンドでは、APIリクエストの受信、入力値の検証、DBへのアクセス、データ加工、レスポンスの返却などを行う。

ログを確認することで、次のような情報を調査できる。

- APIリクエストが正常に届いているか
- DBへの接続やSQLの実行に問題がないか
- 外部サービスとの通信が成功しているか
- 処理にどのくらい時間がかかっているか
- エラーがどの処理で発生したか

また、Request IDやTrace IDを利用すると、複数の処理やサービスにまたがるログを関連付けて調査しやすくなる。

#### ② API処理のログ調査

APIのログを調査するときは、リクエストからレスポンスまでの流れを確認する。

主な確認項目は次のとおり。

- HTTPメソッドやリクエスト先URL
- HTTPステータスコード
- リクエストやレスポンスの内容
- APIの処理時間
- Request IDなどの識別子
- エラー内容

特に、HTTPステータスコードを確認すると、問題の種類を絞り込みやすくなる。

| ステータスコード | 主な意味 |
|---|---|
| 200 OK | 正常終了 |
| 400 Bad Request | リクエスト不正 |
| 401 Unauthorized | 認証失敗 |
| 403 Forbidden | アクセス拒否 |
| 404 Not Found | 対象が存在しない |
| 500 Internal Server Error | サーバー内部エラー |
| 503 Service Unavailable | サービス利用不可 |

#### ③ データベース処理のログ調査

DB処理のログでは、接続・SQL実行・処理時間・トランザクションなどを確認する。

主な確認項目は次のとおり。

- DBへの接続が正常に行われているか
- SQLが正常に実行されているか
- 検索条件や対象データに問題がないか
- SQLの実行時間が長くなっていないか
- トランザクションが正常に完了しているか

トランザクションでは、次の3つの操作が重要。

| 操作 | 意味 |
|---|---|
| BEGIN | トランザクション開始 |
| COMMIT | 変更内容を確定する |
| ROLLBACK | 変更内容を取り消す |

SQLの実行に時間がかかっている場合は、インデックスや検索条件、DBの負荷などを確認する。

#### ④ 外部サービスとの連携ログ

外部サービスとの連携では、HTTP通信の結果やタイムアウト、リトライなどを確認する。

主な確認項目は次のとおり。

- リクエスト先やHTTPメソッド
- ステータスコード
- 通信にかかった時間
- タイムアウトの発生状況
- リトライの回数と最終結果
- 外部サービスの稼働状況

エラーが発生した場合は、自分たちのシステム・ネットワーク・外部サービスのどこに原因があるのか切り分けることが重要。

また、決済処理などでは、無条件にリトライすると二重処理が発生する可能性があるため注意する。

#### ⑤ バックエンドの例外処理とログ

例外処理とは、プログラムの実行中にエラーが発生した場合に、そのエラーを受け取り、適切に対応する仕組みのこと。

Dartでは、`try-catch`を使って例外を処理できる。

- `try`：例外が発生する可能性のある処理
- `catch`：例外が発生した場合の処理
- `finally`：例外の有無にかかわらず実行する処理
- `rethrow`：catchした例外を呼び出し元へ再送出する

例外が発生した場合は、エラー内容やスタックトレースをログに記録する。

また、例外を何もせずに握りつぶさないことが重要。

利用者向けのエラーメッセージと、開発者が調査するための内部ログは分けて管理する。

#### ⑥ 第6章の重要ポイント

バックエンドのログ調査では、次の流れを意識する。

1. APIリクエストが正常に届いているか確認する
2. バックエンドの処理内容やエラーを確認する
3. DBへの接続やSQLの実行状況を確認する
4. 外部サービスとの通信状況を確認する
5. 例外の内容やスタックトレースを確認する
6. 関連するログを時系列で追い、原因を特定する

バックエンドのログ調査では、一つのログだけで原因を判断するのではなく、API・DB・外部サービスなど、複数のログを関連付けて確認することが重要。

また、ログにはパスワードやAPIキー、アクセストークンなどの機密情報を出力しないように注意する。
