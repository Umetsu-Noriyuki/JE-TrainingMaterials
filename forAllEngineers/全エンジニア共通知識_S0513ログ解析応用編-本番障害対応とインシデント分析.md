### 4.1 本番障害とインシデントとは？

#### ① 本番環境とは？

本番環境とは、実際のユーザーが利用するシステムが稼働している環境のこと。

開発環境やテスト環境とは異なり、実際の業務やサービス提供に使用される。

そのため、本番環境で問題が発生すると、ユーザーや業務に直接影響する可能性がある。

#### ② 本番障害とは？

本番障害とは、本番環境でシステムが正常に動作しなくなること。

例えば、次のような状態がある。

- Webサイトにアクセスできない
- APIがエラーを返す
- データの登録や更新ができない
- 処理に異常な時間がかかる
- 一部の機能だけ利用できない

障害の規模によって、影響するユーザー数や業務範囲は異なる。

#### ③ インシデントとは？

インシデントとは、サービスの正常な提供に影響する、または影響する可能性がある出来事のこと。

本番環境での障害だけでなく、情報漏えいやセキュリティ上の問題などもインシデントに含まれる。

障害はシステムに発生した問題そのものを指すことが多く、インシデントは対応が必要な事象全体を指す。

#### ④ インシデント対応の目的

インシデント対応では、次のことが重要になる。

- ユーザーへの影響を最小限にする
- サービスをできるだけ早く復旧する
- 障害の原因を特定する
- 同じ問題が再発しないようにする

特に本番障害では、最初から原因を完全に特定することよりも、まず影響を抑えてサービスを復旧させることが重要になる。

#### ⑤ まとめ

本番環境で障害が発生すると、ユーザーや業務に直接影響する可能性がある。

そのため、インシデント対応では、影響の最小化と迅速な復旧を優先し、その後に原因分析や再発防止を行う。

### 4.2 障害発生時の初動対応

#### ① 初動対応とは？

初動対応とは、本番環境で障害が発生した直後に行う最初の対応のこと。

障害発生時は、原因が分からないまま時間が経過すると、ユーザーへの影響がさらに広がる可能性がある。

そのため、まず状況を把握し、影響を抑えるための対応を行うことが重要。

#### ② 初動対応の基本的な流れ

障害発生時は、次のような流れで対応する。

1. 障害の発生を確認する。
2. 発生時刻やエラー内容を確認する。
3. 影響範囲や緊急度を把握する。
4. 関係者へ障害を共有する。
5. 必要に応じて暫定対応や復旧作業を行う。
6. 対応内容や状況を記録する。

原因調査と並行して、サービスの復旧に向けた対応を進めることもある。

#### ③ ログを使った状況確認

初動対応では、ログを確認して現在の状況を把握する。

例えば、次のようなログが出力されていたとする。

```text
2026-11-06 10:00:01 INFO  API /orders 開始
2026-11-06 10:00:02 ERROR DB接続失敗
2026-11-06 10:00:03 ERROR API /orders HTTP 500
2026-11-06 10:00:05 ERROR DB接続失敗
```

このログから、次のことが分かる。

- 10:00頃からDB接続に失敗している
- 注文APIでHTTP 500が発生している
- DB接続の問題が複数回発生している可能性がある

このように、ログから発生時刻やエラー内容、発生頻度を確認する。

#### ④ 暫定対応と恒久対応

障害対応では、暫定対応と恒久対応を区別することが重要。

| 種類 | 内容 | 例 |
|---|---|---|
| 暫定対応 | まず障害を抑えてサービスを復旧させる対応 | ロールバック、サーバー再起動 |
| 恒久対応 | 根本原因を解消して再発を防ぐ対応 | プログラム修正、DB設計の改善 |

例えば、DB接続障害が発生した場合、DBサーバーの再起動によって一時的に復旧することがある。

しかし、接続数の上限が原因だった場合、根本原因を解消しなければ再び障害が発生する可能性がある。

そのため、暫定対応で復旧した後も原因調査を続ける必要がある。

#### ⑤ 対応状況の共有と記録

障害対応では、関係者への情報共有も重要。

次のような情報を記録・共有する。

- 障害の発生時刻
- 発生している現象
- 影響を受けている機能やユーザー
- 現在の調査状況
- 実施した暫定対応
- サービスの復旧状況

情報を共有することで、複数の担当者が同じ状況を把握し、連携して対応できる。

#### ⑥ まとめ

障害発生時は、まず状況を把握し、影響を抑えてサービスの復旧を目指す。

その後、暫定対応だけで終わらせず、根本原因を調査して恒久対応につなげることが重要。

初動対応では、ログによる状況確認、関係者への共有、対応内容の記録を意識する。

### 4.3 影響範囲の特定

#### ① 影響範囲とは？

影響範囲とは、障害によって影響を受けているユーザーや機能、システムの範囲のこと。

本番障害が発生した場合、原因を調査するだけでなく、どこまで影響が広がっているかを把握する必要がある。

例えば、次のようなケースがある。

- 全ユーザーがログインできない
- 特定のユーザーだけログインできない
- 注文機能だけ利用できない
- 決済機能で一部の処理が失敗している

障害の内容によって、対応の優先順位や必要な作業が変わる。

#### ② 影響範囲を調査する観点

影響範囲を特定するときは、次のような観点で確認する。

| 調査対象 | 確認する内容 |
|---|---|
| ユーザー | 何人のユーザーに影響しているか |
| 機能 | どの機能が利用できないか |
| API | どのAPIでエラーが発生しているか |
| サービス | どのサービスに問題が発生しているか |
| データ | データの登録・更新に失敗していないか |
| 時間 | いつから障害が発生しているか |

これらを確認することで、障害の規模や緊急度を判断しやすくなる。

#### ③ ログから影響範囲を特定する

ログには、エラーが発生した時刻やAPI、ユーザーIDなどの情報が記録されている場合がある。

例えば、次のログを確認する。

```text
10:00:01 ERROR userId=101 API=/orders HTTP=500
10:00:02 ERROR userId=102 API=/orders HTTP=500
10:00:03 ERROR userId=103 API=/orders HTTP=500
10:00:04 INFO  userId=104 API=/login HTTP=200
```

このログから、次のことが分かる。

- 複数のユーザーで注文APIが失敗している
- 注文APIではHTTP 500が発生している
- ログインAPIは正常に動作している

つまり、システム全体が停止しているのではなく、注文機能に影響が集中している可能性がある。

#### ④ 時系列で影響範囲を確認する

障害がいつから発生し、どのように広がったのかを確認することも重要。

例えば、次のような時系列で調査する。

| 時刻 | 状況 |
|---|---|
| 10:00 | 注文APIでエラーが発生 |
| 10:05 | 注文APIのエラーが増加 |
| 10:10 | 決済処理にも影響が発生 |
| 10:15 | 障害対応を開始 |

時系列で整理することで、最初に問題が発生した箇所や、影響が広がった順序を把握しやすくなる。

#### ⑤ 影響範囲を特定する際の注意点

ログにエラーが記録されていないからといって、必ずしも正常とは限らない。

例えば、次のようなケースも考えられる。

- ログが正しく出力されていない
- 一部のサービスだけログを取得できていない
- エラーにはなっていないが処理時間が極端に長い
- データの登録は成功したが、後続処理に失敗している

そのため、ログだけで判断せず、メトリクスやデータベースの状態、ユーザーからの問い合わせなども組み合わせて確認する。

#### ⑥ まとめ

影響範囲の特定では、障害が発生しているユーザー・機能・API・サービス・データなどを確認する。

また、ログを時系列で調査することで、障害の発生時刻や影響の広がりを把握できる。

影響範囲を正確に把握することは、適切な障害対応や復旧の優先順位を決めるために重要。

### 4.4 ログを使った原因分析

#### ① 原因分析とは？

原因分析とは、発生した障害について、なぜ問題が起きたのかを調査すること。

障害が発生したとき、ログに記録されたエラーだけを確認しても、根本原因まで分からない場合がある。

例えば、APIでHTTP 500が発生していても、その原因は次のように複数考えられる。

- データベースへの接続失敗
- SQLの実行エラー
- 外部APIとの通信失敗
- アプリケーション内部の例外
- サーバーのリソース不足

そのため、エラーが発生した前後のログを確認し、原因を絞り込む必要がある。

#### ② エラー発生前後のログを確認する

原因分析では、エラーが発生した瞬間だけでなく、その前後のログも確認する。

例えば、次のログが出力されていたとする。

```text
10:00:01 INFO  API /orders 開始
10:00:02 INFO  OrderService 注文情報取得完了
10:00:03 INFO  PaymentService 決済処理開始
10:00:04 ERROR PaymentService 外部決済API通信失敗
10:00:05 ERROR API /orders HTTP 500
```

このログから、次の流れが分かる。

1. 注文APIが開始された。
2. 注文情報の取得は正常に完了した。
3. 決済処理が開始された。
4. 外部決済APIとの通信に失敗した。
5. 注文APIがHTTP 500を返した。

この場合、外部決済APIとの通信が障害の原因である可能性が高い。

#### ③ エラーの連鎖を調査する

1つの障害が原因となり、別のサービスや機能でもエラーが発生することがある。

例えば、外部決済APIとの通信に失敗すると、次のようなエラーが連鎖する可能性がある。

```text
PaymentService：外部決済API通信失敗
OrderService：決済処理失敗
OrderAPI：HTTP 500
```

この場合、最初に発生したエラーと、その後に発生したエラーを区別することが重要。

後から発生したエラーだけを調査すると、本当の原因を見落とす可能性がある。

#### ④ Trace IDを使った原因分析

複数のサービスをまたぐ処理では、Trace IDを使うと関連するログをまとめて確認できる。

例えば、次のようなログがある。

```text
10:00:01 INFO  OrderService  TraceID=abc123 注文処理開始
10:00:02 INFO  PaymentService TraceID=abc123 決済処理開始
10:00:03 ERROR PaymentService TraceID=abc123 外部API通信失敗
10:00:04 ERROR OrderService  TraceID=abc123 注文処理失敗
```

すべて同じTrace IDが付いているため、1つの注文処理に関係するログだと分かる。

このように、Trace IDを使って複数サービスの処理を追跡することで、障害の発生箇所を特定しやすくなる。

#### ⑤ 根本原因と直接的なエラーを区別する

ログに表示されたエラーが、必ずしも根本原因とは限らない。

例えば、次のケースを考える。

- 表面的なエラー：注文APIがHTTP 500を返した
- 直接的な原因：決済サービスの処理が失敗した
- 根本原因：外部決済APIの接続先設定が誤っていた

このように、エラーが発生した理由をさらに掘り下げることで、根本原因にたどり着ける。

#### ⑥ まとめ

ログを使った原因分析では、エラー発生前後のログや、関連するサービスのログを確認する。

また、Trace IDを利用して処理の流れを追跡し、最初に発生した問題を特定することが重要。

表面的なエラーだけで判断せず、根本原因まで掘り下げて調査する。

### 4.5 再発防止と事後分析

#### ① 事後分析とは？

事後分析とは、障害が発生して復旧した後に、発生原因や対応内容を振り返ること。

障害を復旧させて終わりにするのではなく、何が起きたのか、なぜ起きたのかを整理することが重要。

主に次の内容を確認する。

- 障害が発生した原因
- 障害による影響範囲
- 障害発生から復旧までの経緯
- 実施した対応内容
- 対応が適切だったか
- 今後改善すべき点

#### ② 障害の発生から復旧までを時系列で整理する

事後分析では、障害発生から復旧までの出来事を時系列で整理する。

例えば、次のような記録を作成する。

| 時刻 | 発生した出来事 |
|---|---|
| 10:00 | 注文APIでエラーが発生 |
| 10:05 | 障害を検知 |
| 10:10 | DB接続エラーを確認 |
| 10:15 | DBサーバーを再起動 |
| 10:20 | サービスの復旧を確認 |
| 11:00 | 接続数の上限が原因と判明 |

このように時系列で整理することで、障害の発生状況や対応の流れを把握しやすくなる。

#### ③ 根本原因を特定する

再発防止のためには、表面的なエラーだけでなく、根本原因を特定する必要がある。

例えば、DB接続障害が発生した場合を考える。

| 項目 | 内容 |
|---|---|
| 発生した現象 | APIがHTTP 500を返した |
| 直接的な原因 | DBへの接続に失敗した |
| 根本原因 | DB接続数が上限に達していた |

この場合、単にDBを再起動するだけでは、再び同じ障害が発生する可能性がある。

なぜ接続数が上限に達したのか、さらに調査する必要がある。

#### ④ 再発防止策を考える

根本原因が分かったら、同じ障害が再び発生しないように対策を考える。

例えば、DB接続数が上限に達した場合は、次のような対策が考えられる。

- DB接続の管理方法を見直す
- 不要なDB接続を適切に解放する
- DB接続数の上限を適切に設定する
- 接続数が増加したときに検知できる監視を追加する

再発防止策は、プログラムの修正だけでなく、監視や運用ルールの改善も含まれる。

#### ⑤ ポストモーテムとは？

ポストモーテムとは、障害発生後に原因や対応内容、改善策などをまとめた振り返りの記録のこと。

主に次のような内容を記載する。

- 障害の概要
- 発生日時と復旧日時
- 影響範囲
- 障害の原因
- 対応内容
- 再発防止策

ポストモーテムは、個人を責めるためではなく、組織やシステム全体の改善につなげるために作成する。

#### ⑥ まとめ

障害対応は、サービスが復旧した時点で完了ではない。

障害の経緯や根本原因を分析し、再発防止策を実施することが重要。

また、ポストモーテムとして記録を残すことで、同じ問題への対応力を組織全体で高めることができる。

### 4.6 第4章まとめ

#### ① 本番障害とインシデントとは？

本番障害とは、実際のユーザーが利用する本番環境で、システムが正常に動作しなくなること。

インシデントとは、サービスの正常な提供に影響する、または影響する可能性がある出来事のこと。

インシデント対応では、次のことが重要になる。

- ユーザーへの影響を最小限にする
- サービスを迅速に復旧する
- 障害の原因を特定する
- 再発を防止する

#### ② 障害発生時の初動対応

障害が発生したら、まず状況を把握して影響を抑える。

基本的な対応の流れは次のとおり。

1. 障害の発生を確認する。
2. 発生時刻やエラー内容を確認する。
3. 影響範囲や緊急度を把握する。
4. 関係者へ情報を共有する。
5. 必要に応じて暫定対応を行う。
6. 対応内容や復旧状況を記録する。

暫定対応でサービスが復旧しても、根本原因の調査は継続する。

#### ③ 影響範囲の特定

影響範囲とは、障害によって影響を受けているユーザーや機能、システムの範囲のこと。

次のような観点で調査する。

- 何人のユーザーに影響しているか
- どの機能で問題が発生しているか
- どのAPIやサービスに問題があるか
- データの登録や更新に失敗していないか
- いつから障害が発生しているか

ログやメトリクスなどを組み合わせて、正確な影響範囲を把握する。

#### ④ ログを使った原因分析

原因分析では、エラーが発生した瞬間だけでなく、その前後のログも確認する。

また、複数サービスにまたがる処理では、Trace IDを利用して関連するログを追跡する。

重要なポイントは次のとおり。

- エラー発生前後のログを確認する
- エラーの連鎖を調査する
- Trace IDで関連する処理を追跡する
- 表面的なエラーと根本原因を区別する

#### ⑤ 再発防止と事後分析

障害が復旧した後は、発生原因や対応内容を振り返る。

再発防止では、根本原因を解消するための改善を行う。

例えば、次のような対策がある。

- プログラムの修正
- DB設計や接続管理の改善
- サーバー構成の見直し
- 監視やアラートの追加
- 障害対応手順の改善

また、ポストモーテムを作成して、障害の経緯や原因、改善策を組織全体で共有する。

#### ⑥ 第4章の重要ポイント

本番障害対応では、次の流れを意識する。

1. **初動対応：** 障害の発生を確認し、状況を把握する。
2. **影響範囲の特定：** ユーザーや機能への影響を確認する。
3. **暫定対応：** 影響を抑え、サービスの復旧を目指す。
4. **原因分析：** ログやメトリクスを使って根本原因を調査する。
5. **再発防止：** 原因を解消し、同じ障害が起きないように改善する。
6. **事後分析：** ポストモーテムなどに記録し、組織全体で共有する。

本番障害対応では、単にエラーを解消するだけでは不十分。

迅速な復旧と根本原因の解消、そして再発防止まで行うことが重要。
